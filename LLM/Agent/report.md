# LLM Agent 架构与工具使用研究报告

> 初稿日期：2026-06-06；证据修订：2026-10-22。
> 范围：推理与行动循环、反思、多 Agent 协作、工具接口、记忆与评测。本文是有原文锚点的专题综述，尚不是每篇论文的完整精读分册，也不提供框架的实时排行榜。

## 1. 执行摘要

Agent 的关键是让模型的行动进入可观察、可反馈的执行循环。ReAct 将语言推理与环境动作交错；Reflexion 将任务反馈变成供后续尝试使用的文字记忆；AutoGen 则提供可编排的多角色对话。这三项分别改变控制流、经验利用和协作方式，不能仅凭名称或模块数量判断哪一种更可靠。[R1–R3]

原稿把 ReAct 写成“相比 CoT 提升 34%”，混淆了任务、基线和单位。原文的 34 是 ALFWorld 中最佳 ReAct 提示配置与 BUTLER 的成功率之差，单位是**百分点**；不是对 CoT 的通用增益。工具协议也不直接决定任务成功率或延迟：MCP 规定连接、能力交换与消息交互，执行成本仍取决于工具、网络、模型及宿主实现。[R1, R5]

实践上应先固定任务、环境版本、模型和预算，再比较单循环、规划、反思或协作。本文下列工程建议均是据这些机制提出的设计判断，需在目标任务中验证。

## 3. ReAct：可观察的推理与行动循环

典型步骤是“读取目标与历史 → 生成思考或行动 → 环境执行 → 加入观察 → 继续或停止”。思考是文本，行动必须映射到任务支持的操作；环境返回结果不自动成为可信事实。[R1 §2]

| 任务 | 模型、协议与指标 | ReAct | 对照 | 可支持的结论 |
|---|---|---:|---:|---|
| ALFWorld | PaLM-540B，few-shot prompting，表 3 的最佳提示配置，成功率 | 71%（best of 6） | BUTLER 37%（best of 8） | 相差 34 **个百分点**；配置筛选预算也不同，不是平均部署收益 |
| ALFWorld | 同表，ReAct 跨配置平均成功率 | 57% | 上行是最佳配置，不能混作同一统计口径 | 报告最佳值时应同时交代提示选择 |
| WebShop | PaLM-540B，one-shot，表 4 的成功率 SR | 40.0% | Act 30.1%；IL+RL 28.7% | 分别相差 9.9、11.3 个百分点，任务与基线均不同 |

这组结果不能用于证明“ReAct 总是优于 CoT”。问答实验中 ReAct 与 CoT 各有失效面，论文还研究了二者组合；闭环交互收益也依赖检索是否取回有效信息。[R1 §3.3]

## 4. 规划、反思与多 Agent

| 方法 | 改变什么 | 必须保留的边界 |
|---|---|---|
| 显式规划 | 先拆任务，再执行并更新计划 | 本文作为设计模式讨论；计划是否可执行要由环境反馈检验 |
| Reflexion | evaluator 提供反馈，self-reflection 写入文字记忆，actor 再试 | 不等于参数学习；任务成功依赖反馈质量与试验次数，须按相同总预算比较 [R2] |
| Self-Refine | 生成 → 自反馈 → 修改 | 反馈与修改可同源地出错；多轮增加计算，不能把改写流畅等同于答案正确 [R4] |
| AutoGen | 对话程序组织可定制 Agent、工具及人类输入 | 论文展示多个应用，并未证明增加 Agent 数目必然提高准确率；需控制模型、工具和交互预算 [R3] |

**综合判断**：多角色可以分离生产与检查职责，但若共享同一错误资料或没有可验证的检查信号，角色分工本身不能构成独立证据。建议将“初稿—检查—修订”的增益与“单 Agent 使用同等 token/工具预算”的基线比较。

## 5. 工具接口与协议

模型输出工具调用描述，应用负责校验、实际执行并把结果交回模型。结构正确只说明调用描述可解析；工具选择、参数语义和权限仍需分别处理。

MCP 的固定版本架构将 host 作为连接与授权协调者；host 创建 client，每个 client 与特定 server 保持独立会话；server 暴露 resources、tools、prompts 等能力。[R5] 因而应区分：

- **模型层**：如何决定要调用哪个工具，如何表达参数。
- **协议层**：如何发现能力、建立会话和传递消息。
- **执行层**：如何执行调用、记录副作用、超时并恢复。

MCP 与模型的工具调用能力可以一起使用。不能按二选一来推断“MCP 一定更慢”或“function calling 一定适合实时”，也不能把服务总数等同于工具质量。原稿未提供可回溯样本与统计方法的“4000+ servers”“97.1% 描述有问题”已撤下。

## 6. 记忆：内容、写入与读取都需要评价

下表是工程分类，不是文献已确立的统一四级标准。

| 存储形态 | 作用 | 需要验证什么 |
|---|---|---|
| 当前上下文 | 保存当前目标、观察与状态 | 是否丢失约束；上下文增长后的错误率 |
| 摘要或会话记录 | 跨轮保留任务进度 | 摘要是否保留证据与未决事项 |
| 检索式持久记忆 | 跨任务检索历史经验 | 检索相关性、陈旧信息、错误经验污染 |
| 文件或数据库 | 保存可寻址的原始产物与事实 | 来源、版本、写入权限、冲突处理 |

Reflexion 的 episodic memory 是特定实例：保存失败后的语言反思，影响随后尝试。[R2 §3] 把记忆读写暴露为工具是一种可行接口设计；本报告不再将它无来源地归功于某位 2026 年作者。

## 7. 如何比较 Agent 系统

| 维度 | 最少记录项 | 为什么需要 |
|---|---|---|
| 任务 | 数据集版本、划分、样本数、成功判定 | 防止把不同任务的数字排成榜单 |
| 模型 | 名称、固定版本、采样设置 | 模型差异可能覆盖控制流增益 |
| 环境 | 工具/API 版本、初始状态、允许动作 | 环境变化可能改变成功率 |
| 预算 | 最大步数、重试、token、耗时、费用 | 区分架构收益与额外采样收益 |
| 统计 | 多次运行、均值/区间、失败类型 | 最佳提示或一次成功不能代表稳定性 |
| 副作用 | 执行记录、授权状态、是否可回滚 | 任务成功与操作合规是不同指标 |

软件工程可用测试验证修复，购物或多应用任务还需检查最终状态。选择 SWE-bench、AppWorld 等外部基准前，应核对其官方任务定义；本轮没有重新审定这些基准的所有版本、分数及发布时间，故不保留原稿带有统一时长或难度排名的比较表。

## 8. 共识、不确定性与研究偏差

上述工作共同说明控制流、反馈与外部环境值得单独建模；它们并未形成“最好的通用 Agent 架构”的共识。反思与多角色的有效性取决于反馈信号、任务和预算，工具协议的互操作性也不能替代语义正确性评价。

本轮聚焦早期机制论文，覆盖不了截至 2026 年的完整生态；文献选择偏向英语与可公开取得的原文。主张复核尚不等于独立复现，宿主框架源码、实时生态指标及新兴系统仍待另行按固定 commit 深读。原稿中无法确定身份的 HarnessAPI、SwarmHarness、STEM Agent、Skill1、RocketSmith 等不再承担研究结论；这不构成对这些名称是否存在的否定。
