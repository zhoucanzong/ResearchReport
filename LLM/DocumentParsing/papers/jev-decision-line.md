# JEV 判别线：把“判断”做成一次前向的分类分布

> 对象：AutoTrust 的 **JEV**（System 1 decision model）系列，主证据为[官方模型卡 `autotrust/JEV-35B`](https://huggingface.co/autotrust/JEV-35B)（Apache-2.0，2026-10-14 更新）与其[官方 blog《One Decision Model Instead of a Ranking Team》](https://huggingface.co/blog/autotrust/one-decision-model-instead-of-a-ranking-team-short)，家族清单来自 Hugging Face 模型列表 API（`autotrust`）。**这套东西没有可确证的 arXiv 论文**——见文末“来源与未能确证”。

全文用三种标记：**官方发布稿**（模型卡、blog、API 列表）、**我们的判断**、**未能确证**。本文不引任何媒体转述数字。

## 它解决的问题：判别不是一个生成任务

搜索排序、推荐、质量评估的常见做法是“生成候选 + 再排序”：让模型写一段评价，再解析成分数。代价是每一步都要把判断塞进文本，格式一错就丢样本，多候选就要多次调用。

JEV 换了个方向：**把判断做成一次前向的输出分布**。输入是“问题 + 至多 256 个选项”，输出是每个选项的概率；取 argmax 即可，判断过程没有自由文本，也就没有格式解析损耗。模型卡自己在 ERQA 一节写明这一点：答案取最可能的选项，**“所以没有一道题因答案格式而丢失”**（模型卡 ERQA 段）。

## 输入、输出、训练信号

**三种判定类型**（模型卡 API 段，`/v1/decide`）：

| `kind` | 输入 | 输出 |
|---|---|---|
| `noul` | 一个是非问题 | `["false","true"]` 上的概率 |
| `score` | 一个待评对象 | 0–5 分 |
| `choice` | 问题 + 2–256 个候选项 | 各候选概率、`choice`、`choice_index` |

**实现方式**：候选选项被映射到一组 **slot token**（`A`–`JU` 这一类的单 token 位），判定头合并进 `lm_head` 的对应行，因此一次前向就能同时给出全部候选的 logits；**每种 `kind` 另有一个温度参数**写在 `calibration.json` 里，用于把 logits 校准成概率（模型卡“Head”与“calibration.json”段）。响应字段固定为 `options` / `probabilities` / `choice` / `choice_index` / `usage`。

**训练信号**：卡里只说明决策训练用的是**纯文本决策数据**（ERQA 一段注明 “no robot or embodied data … text only”），并未公开数据规模、损失或是否含 RL/偏好阶段 → **未能确证**。可确证的是产品形态：它是一个**判别头 + 校准表**的组合，而不是“会写理由的评审模型”。

## 家族与代际关系

Hugging Face 上 `autotrust` 名下同时存在：`JEV-9B`、`JEV-27B`、`JEV-27B-VL`（多模态档）、`JEV-35B`、`JEV-35B-NVFP4`、`JEV-Gemma4-26B-A4B`、`GEV-26B-Decide`，以及若干 Qwen/GLM 量化与 DGX-Spark 适配变体。**JEV-35B 与 JEV-27B-VL 的关系**（模型卡开篇）：

- `JEV-35B` 建在 **Qwen3.5-35B-A3B** 上——35B 总参、**约 3B 激活/token** 的 MoE，一次前向最多 256 个候选；
- `JEV-27B-VL` 是更早的 27B 多模态档；
- 卡里给的两组对照：**Decision Index 0.3 公共套件 59.73 vs 53.64**；**视觉部分约 71.94 vs 71.67**（作者自称“自己重建的视觉基准”，并写明“同一重建下在噪声内打平”）；**单请求中位延迟 204 ms vs 271 ms**（单卡 B200）。
- 量化版：NVFP4 = 25.6 GB 下载 / 23 GiB 显存，bf16 = 72 GB / 66 GiB。

**这里有个必须挑明的口径问题**：59.73 一行作者自己标注为 *“our scoring with the kit, not a board entry”*，而 53.64 是“board 上的分”。**两者不是同一个计分面板**，所以不能写成“35B 比 27B-VL 高 6 分”。能说的是：作者用自家工具测得 59.73；在视觉重建上两代基本持平；延迟明显更低。

## 与 MiniCPM-OCR Jev（2B）的差别

`openbmb` 名下确实有 `MiniCPM-OCR-Jev`（含 gguf / AWQ / GPTQ 变体，来自 Hugging Face 模型列表 API），团队任务说明里描述其为 **2B 的 OCR 正确性判别模型**（输入图 + OCR 结果，输出 0–1 质量分）。**但我没有取到它的一手模型卡，机制细节（打分头、训练信号、校准）未能确证**；下面只写可由两边形态推出的差别：

| 维度 | JEV-35B（AutoTrust） | MiniCPM-OCR Jev（2B，未核一手） |
|---|---|---|
| 判定对象 | 通用 typed decision：是非 / 0–5 分 / 2–256 选一 | 专项：一份 OCR 结果的质量（0–1） |
| 输出 | 各候选概率 + argmax | 单一标量质量分 |
| 规模 | 35B 总参 / ~3B 激活 | 2B 稠密（按公开简介） |
| 定位 | 替代“排序团队”的通用判定层 | 文档解析流水线末端的质检/仲裁 |

**我们的判断**：两者不是同一产品的两个尺寸，而是**通用判别底模**与**垂域判别头**的关系。JEV 那条线的论点是“一次前向 + 校准概率可以替代多模型排序”，MiniCPM-OCR Jev 则是把这个论点收窄到“只判 OCR 对不对”，用 2B 换部署成本。**若两者真有权重血缘（蒸馏/同源数据），我未能确证。**

## 这条线为什么值得单独看

在文档解析这条链上，判别模型的位置是**解析之后**：同一个页面可以用多个解析器出结果，用判别模型给每份结果打分再选，而不是重新训练一个更强的解析器。这恰好与库里的解析器分册互补——[PaddleOCR-VL](2510.14528-paddleocr-vl.md)、[HunyuanOCR](2511.19575-hunyuan-ocr.md)、[Qianfan-OCR](2603.13398-qianfan-ocr.md) 在比“谁的 Markdown 更准”，判别线在问“**怎么在不换解析器的前提下，知道这次准不准**”。

它对 agent/harness 一类的工程更有直接价值：判别输出是概率，可以直接进阈值策略（低于阈值就升级到更强模型或人工），而生成式评审要先解析文本再定阈值。**代价同样清楚**：判定面越宽（256 选项），校准越难；温度是**按 kind 静态标定**的，遇到分布外输入（新领域、新解析器风格）是否还准，卡里没有报告 → **未能确证**。
