# MinerU2.5-Pro：不动架构，把分数从数据里榨出来——顺手重写了 v1.6 的尺子

> Yuan Qu, Mengzhang Cai, Wenzheng Zhang 等（上海人工智能实验室 / 北大 / 上交），*MinerU2.5-Pro: Pushing the Limits of Data-Centric Document Parsing at Scale*，arXiv:2604.04771v2（2026-04-09）。依据[官方完整 HTML 原文 v2](https://arxiv.org/html/2604.04771v2)精读，重点参照 §1、§3–6、§7 讨论，尤其是 Figure 1、4 与 Tables 1–5。文中数字均为论文报告结果，标注了基准版本与子集；本文未独立运行、未重算指标。

## 一句话：它既是选手，也是记分员

MinerU2.5-Pro 保留 MinerU2.5 的 **1.2B 解耦式粗到细架构**（NaViT-675M 视觉编码器 + Qwen2-0.5B 语言模型）完全不变，从 MinerU2.5 的 Stage 0 checkpoint 初始化，所有改动都落在**数据引擎与训练策略**上（§4 开头）。结果：OmniDocBench v1.6 Full **95.69**，同架构基线 92.98，**+2.71**；论文称超过所有现有方法，包括参数量大 200 倍以上的通用 VLM（§1、Figure 1）。

**它被当作基准引用的三个理由**（这比"分数高"重要）：

1. **它是"同架构对照"的模板**。同一套 1.2B 权重、同一分辨率设置，只换数据与训练阶段，增益可归因到数据。别人引用它是为了说"这个量级的模型能到多少"。
2. **它是 OmniDocBench v1.6 协议的定义者**。v1.6 不是官方仓库自动升级的版本，而是这篇论文提出的：多粒度自适应匹配（MGAM）+ Hard 子集 + Base/Hard/Full 三层（§5），并在其数据集页发布。引用"v1.6 分数"的人，实际上用的是它定义的尺子。
3. **它统一重跑了对手**。§6.1 明写"所有对比模型在同一环境下用同一份评测代码重评"，所以它的表是少数"单一 harness 内"的比较，而非各家自报数字的拼盘。

我们库里已有 **8 个文件**引用 MinerU（`2412.07626`、`2510.18234`、`2510.14528`、`2603.24326`、`2510.21603`、`2605.27978`、`2606.23050`、`20261027-minicpm-ocr`），正好说明它作为"被引基准"的位置。

## 数据引擎：三个零件解决三件事

论文的前提是一次观察：不同架构、不同参数量的 SOTA 模型**在同一批困难样本上以高度一致的方式失败**，说明瓶颈是训练数据而不是架构（§1）。

- **覆盖**（§3.1）：多样性 + 难度感知的两级采样，先页级再元素级，把训练数据从 **不足 10M 扩到 65.5M** 样本，同时压制分布漂移。
- **信息量**（§3.2）：**CMCV**（Cross-Model Consistency Verification）用多个异构模型对同一区域的输出共识来估难度并直接生成标注——共识高的当易样本自动标，分歧大的留给人工。这是"用模型投票造标注"的路线，省的是标注费，风险是共识偏差会被一并学进去。
- **标注准确度**（§3.3）：难样本走 **Judge-and-Refine**（先渲染再核对的迭代纠正），另有定向专家标注。最终难样本 **192K** 专家标注。

分层结果是：65.5M 易/中样本供 Stage 1 预训练，192K 难样本供 Stage 2 微调与 Stage 3 GRPO 对齐（§3 末）。

## 三阶段训练：每阶段各自的增益

| 阶段 | 数据 | 增益（v1.6 Full） | 主要来源 |
|---|---|---|---|
| Stage 1 大规模预训练 | 65.5M 易/中（CMCV 标注） | **+1.31** | 数据覆盖与标注质量 |
| Stage 2 难样本 SFT | 192K 专家标注 | **+0.96** | 表格 TEDS 90.37 → 92.87（+2.50） |
| Stage 3 GRPO 对齐 | 同上，RL | **+0.45** | 公式 CDM 96.48 → 97.29（+0.81） |

（§4.3、Table 3 及正文分解。）GRPO 直接拿任务指标当奖励，不另训奖励模型；阶段三只买到 +0.45，说明**格式/指标对齐的空间已经不大**，主要收益在数据量与难样本质量上。Hard 子集累计 +2.43、Base +2.89，两条差不多——这是作者用来论证"难样本训练没有牺牲常规场景"的证据。

## OmniDocBench v1.6 改了什么（这是全文对我们最有用的一段）

v1.5 的两个毛病（§5.1）：

- **匹配偏差**：v1.5 用固定粒度的一对一元素匹配。一段跨 k 行的多行公式，模型输出同样的 LaTeX 但切成 k−1 块或 k 块，**分数从满分掉到近零**；密集文本被逐行输出、或整块被识别成表格，v1.5 直接给零（没有文本元素可匹配）。这惩罚的是输出粒度，不是内容对错。
- **难样本缺失**：v1.5 评测集里被数据引擎标为 Hard 的页面**几乎不存在**，头部模型挤在一起，区分度低。

v1.6 的补法是 **MGAM**（§5.2），原则是 **GT 不动，只在预测侧搜索最优粒度**：

1. 原粒度做匈牙利最优二分匹配，得候选分 S₁；
2. 把每条预测按 LaTeX 换行符（`\\`、`\newline` 等）切开，再匹配，得 S₂；
3. 对切细后的 n′ 个元素枚举 **2^(n′−1)** 种相邻合并方案，逐种匹配取最优，得 S₃；
4. 取三者最高分为最终匹配，再按该匹配算 CDM / 编辑距离。

密集文本同样复用该算法（相似度用编辑距离）；若某区域被识别成表格而非文本，**把表格转回纯文本放进同一条匹配管线**，避免格式偏好扣分。

**Hard 子集**（§5.3）：296 页，从数据引擎标为 Hard 的池子里挑，覆盖嵌套表格、密集多行公式、非常规版式；**从 MinerU2.5-Pro 的所有训练阶段（含 Judge-and-Refine 数据）中排除**，由专业团队标注并做标注者交叉校验。

**三层协议**：Base **1,355** 页（沿用 v1.5 集，保持历史可比）+ Hard **296** 页 = Full **1,651** 页。

## 口径：这个 95.69 到底怎么读

- **综合分定义**：Overall = 文本（编辑距离）、表格（TEDS）、公式（CDM）三项的平均（§6.1），并附 Text Edit↓、CDM↑、TEDS↑、TEDS-S↑、Read Order Edit↓。**不含读序**，读序单独列（本模型 0.120）。
- **层必须写**：v1.6 已经是三层结构，**95.69 是 Full（1,651 页）**。同一次消融里 Base 层 **96.12**、Hard 层 **94.08**（Table 3），三层差 2 分，只说"v1.6 上 95.69"在跨论文引用时极易与 Base 层数字混为一谈。
- **与库内数字的差**：`20261027-minicpm-ocr` 那张 OpenBMB 汇总表里 MinerU2.5-Pro 是 **95.75**，论文自报 **95.69**，差 0.06；两边都没写层。少量差异可来自匹配实现、GT 版本细节或评测运行次数——**这正是"跨来源不并表"的理由**，不是谁错了。
- **与 v1.5 不可相减**：v1.5 的 92.98（MinerU2.5 自报，见 `2510.14528` 引用的 90.67 是另一种口径）与 v1.6 不同尺；协议已变（MGAM 宽松化了匹配、加入了更难样本），方向相反的两股力量叠在一起，**"提了 2.71 分"里有多少是数据、多少是尺子，论文没有拆开给**。这是本文最需要警惕的一处，也是我们引用时应写"新协议下的 95.69，旧协议基线 92.98"而不是"提升 2.71 分"的原因。
- **对手列可信度**：单一 harness、同一评测代码重跑（§6.1），比各家自报的拼盘强；但作者同时是协议作者，仍有"出题人自评"的成分。表 2 里 GLM-OCR 0.9B 95.15、PaddleOCR-VL-1.5 94.87、Youtu-Parsing 2.5B 93.68 都来自这次统一重跑。

## 与库内其他分册的关系

- **PaddleOCR-VL（`2510.14528`）**：0.9B 解耦 + 三线程异步流水线，v1.5 口径综合分 92.86；本论文的统一重跑里 PaddleOCR-VL-1.5 在 v1.6 Full 是 94.87。两者同属"解耦/粗到细"路线，差别在 MinerU 把 layout 与识别放进**同一个 1.2B 模型**（原生分辨率），Paddle 用独立版面模型 + 区域识别。
- **GLM-OCR / Xiaomi-OCR-0**：本论文把 GLM-OCR 列在 0.9B、95.15（同一 harness），这是引用 GLM 数字时最干净的一行——但注意它评测的是 GLM 发布时的版本。
- **HunyuanOCR / Unlimited OCR / MiniCPM-OCR**：它们的 v1.6 数字（94.74 / 94.02 / 96.51）**不在本论文表内**，来自各自或第三方，层与 harness 都不同；比较只能在"同表同层"内做。

## 边界（作者自述 + 我们的判断）

- **"数据 > 架构"是受控结论**：论文固定架构只动数据，证明了在 1.2B 解耦架构内数据工程有大空间；**不能外推**成"任何架构上数据都比架构重要"（我们的判断）。
- **Hard 子集是自建自评**：296 页由作者按自家难度分层挑、自家团队标注；即便排除了训练集，难度定义仍掌握在作者手里。外部复现难在拿到同一批页（我们的判断）。
- **MGAM 的方向性**：论文的动机是"消除对语义正确输出的惩罚"，但更宽松的匹配同样可能抬高一部分系统的分。**放宽尺度后旧数字不再可比**——这是评测协议升级的固有代价，论文自述在 §7"Fundamental challenges in evaluation"里也承认：同内容可以有多种等价写法（HTML vs Markdown 表格、不同 LaTeX 命令），同一版面也可合法地表示成文本对或两列表格，连人工标注者都会分歧；**语义等价感知的评测仍是公开问题**。
- **未覆盖**：垂直领域（金融/法律/医疗）需自建集（§7）；结构理解（标题层级、图表与正文的指代、跨页连续性）不在本文范围（§7）；`third_party` 之外的推理成本、部署形态未展开。

## 读法

先读 §3 的数据引擎三件套，理解 65.5M / 192K 两个数字怎么来的；再读 §5.1 的两个动机与 Figure 4（多行公式被切块的例子），这段改写了整个社区引用的尺子；然后读 §5.2 的三个匹配阶段与 §5.3 的三层协议，最后看 Table 2（Full 层横评）、Table 3（阶段消融）与 Table 5（公式跨基准）。任何时候引用它的分数，先把"层 + 协议版本 + 是否统一重跑"三件事写出来。
