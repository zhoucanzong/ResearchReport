# Unlimited OCR：把解码缓存钉成常数，从长时程走向“不限页数”

> Youyang Yin 等，*Unlimited OCR Works*，arXiv:2606.23050v1（2026-06-22，署名 Baidu Inc.）。依据[官方完整 HTML 原文 v1](https://arxiv.org/html/2606.23050v1)精读，重点参照 §1、§3.2–3.4、§5–7，特别是 Figures 1–3 与 Tables 1–4。**Unlimited OCR 2 目前没有 arXiv 版本**：arXiv 检索 `ti:"Unlimited OCR"` 只返回 2606.23050v1 一条，v2 的一手材料是[仓库内技术报告 PDF](https://github.com/baidu/Unlimited-OCR/blob/Unlimited-OCR-2/Unlimited-OCR-2.pdf)（15 页，文件名与 README 的「arXiv」徽标并列，但不在 arXiv 上）、[README](https://github.com/baidu/Unlimited-OCR/blob/main/README.md) 的 release 记录、[Hugging Face 模型卡](https://huggingface.co/baidu/Unlimited-OCR-2)与发布稿。两类材料证据等级不同，下文分别标注。

全文用四种标记：**论文报告**（v1 的 arXiv 原文）、**官方发布稿**（v2 技术报告、README/release、模型卡、发布会通稿）、**媒体报道**（新华网、量子位等转述与自测）、**我们的判断**。

## 先把问题定在解码器上

端到端 OCR 把“检测 + 识别 + 排序”压成一次序列生成。v1 的出发点不是识别精度，而是这条生成链的账：标准注意力下，KV cache 随输出长度 $T$ 线性增长，注意力计算同步变贵，于是“越往后写越慢”，长文档只能退回逐页 for 循环，每翻一页把记忆清零（§1）。论文给了一组量级估计：视觉/文本 token 按 1:10 压缩，10K 视觉 token（约 20–30 页 1024×1024）需要 100k+ 输出 token，而常见最大长度是 32K（§3.4）。

这里要区分两个“稀疏”：DeepSeek-OCR 的稀疏发生在**编码器**——DeepEncoder 用 SAM-ViT 的窗口注意力处理原图 token，再在 16× 压缩后的 token 上做全局注意力，使高分辨率输入不炸激活值（v1 §2.2.1、§3.3）；而它的**解码器仍是标准多头注意力**，v1 明确称 baseline 为 MHA 并以此算 cache 上界（§3.4.2）。Unlimited OCR 改的是解码器，不动编码器。把两处混为一谈会读错对手。

## R-SWA：钉住“参考”，只滚“草稿”

R-SWA（Reference Sliding Window Attention）把注意力限制在一个两段窗口里（§3.4.1，式 1–3；Fig. 1–2）：

- **参考段 $\mathcal{P}$**：长度 $L_m$ 的前缀，包含全部视觉 token 和 prompt。它对之后**每一个** token 永久可见，且在单次推理中固定不变。
- **解码段 $\mathcal{D}_n(t)$**：输出侧宽 $n=128$ 的因果滑窗，只覆盖最近 128 个已生成 token，随生成滚动。

每个 token 只在这两段的并集上做 softmax。写成 cache 账本就是论文的式 5–9：标准 MHA 为 $C_{\mathrm{MHA}}(T)=L_m+T$，R-SWA 为 $C_{\mathrm{R\text{-}SWA}}(T)=L_m+\min(n,T)\le L_m+n$，比值 $\rho(T)\to 0$。模型权重侧另有一层压缩：沿用 DeepSeek-OCR 的 MoE 解码器，3B 总参数、每 token 激活 0.5B（§3.2）。

**与标准滑窗的差别**不在窗口，而在**谁允许被丢**。常规 SWA 一视同仁地滚过全部历史：当视觉 token 被滚出窗口，它们就再也进不来，模型只能靠文本隐状态“记住”页面内容，而隐状态会随层与步不断重写。v1 的 Fig. 1 把这写成“把视觉 token 排除在状态转移之外，避免渐进模糊”，并顺带否掉了线性注意力/循环状态这条替代路线——它会把参考 token 压进递推状态，同样模糊视觉特征（§1）。**与 DeepSeek-OCR 的差别**是作用位置：对手在编码器省激活，R-SWA 在解码器省 cache。

**“恒定”是严格的，但只对解码长度严格。** 缓存上界 $L_m+n$ 与输出长度无关，这是可证的严格结论；但 $L_m$ 本身随页数线性增长（一页 1024×1024 压成 256 token，§3.3），所以总 cache 对页数并不恒定，每步注意力仍要扫过全部视觉 token。代价落在三处：其一，模型看不到自己 128 token 以前的输出，跨页去重、页眉页脚、跨页指代只能靠视觉回看而非文本记忆；其二，每步成本随页数增长，v2 正是以“R-SWA 的视觉参考仍随页数膨胀”为升级理由（v2 §1、§2.1，Fig. 1）；其三，v1 自己在 §7 承认：有限上下文（32K）下做不到真正 unlimited，瓶颈在 prefill 长度，计划扩到 128K 并做“prefill 池”。

静态配置能对上论文：v1 模型 `config.json` 的 `sliding_window_size=128`，v2 模型 `config.json` 的 `sliding_window_size=128`、`sparse_topk_blocks=16`、`sparse_block_size=32`、`page_token_id=128827`（本页核对模型卡文件）。16×32=512 正对上 README 所说的“固定 512 token 工作参考”。

## v1 的实验条件与同基准数字

训练是从 DeepSeek-OCR checkpoint 续训：约 200 万条文档 OCR 数据（9:1 单页/多页，多页 2–50 页，`<page>` 分隔，32K 打包），4000 步、全局 batch 256、8×16 A800，冻结 DeepEncoder 只训 LLM（§4.1–4.2）。**这意味着任何与 baseline 的分数差都混了“改注意力”和“多训 200 万数据”两个变量**，论文没有做同数据、同步数的架构消融（我们通读 §5–6 未见 ablation），所以“R-SWA 免费午餐”的说法只能算作者解释。

|---|---|---|---|---|---|---|

## v2 改了什么：逐条与来源分级

v2 的技术报告把升级写成两步：**SR-SWA**（Sparse Reference Sliding Window Attention）把“参考”从“全部视觉 token”换成“固定预算的工作参考”，再用 **Unlimited-Horizon Decoding** 把显存压到“一个块”的规模。

SR-SWA 分两层（v2 §3.3，式 2–7）：Page Gate 把每个 query 的视觉范围从整份文档收窄到相关页，并把位置坐标分解成“有界页级坐标（0–1 交替）+ 页内单调坐标”以防长文档位置爆炸；Token Sieve 在候选块上算相关性，用 α-entmax 得到稀疏分布后取 top-k 块，路由概率转成 mean-centered log-prior 直接加进注意力 logits，因此路由可端到端训练、不需要 KL 蒸馏式的辅助损失。被选中的块是**真实的 token**，不是摘要。README 说工作参考约 512 token（L57）；config 里 `dash_router=entmax_topk_perlayer`、`dash_topk_blocks=12`、`sparse_topk_blocks=16`、`sparse_block_size=32` 与这个量级一致（我们的判断：这是静态配置核对，不是运行验证）。

Unlimited-Horizon Decoding（v2 §3.4、Algorithm 1）把文档切成有 1 页重叠的块，块间复用重叠页的视觉 KV 和上一块末尾的文本 KV，块外的视觉缓存直接释放。因此“不限页数”不是靠更长上下文，而是靠**有限窗口 + 分块 + 边界复用**。

| 维度 | v1（2026-06） | v2（2026-10-27） | 来源分级与条件 |
|---|---|---|---|
| 注意力机制 | R-SWA：前缀永久可见 + 128 token 滑窗 | SR-SWA：Page Gate + Token Sieve 稀疏路由 + 局部窗 | 论文报告 / 官方发布稿（v2 §3.3、README L57） |
| 视觉参考量 | 全部视觉 token（随页数线性增长） | 固定 top-k 块（16×32≈512 token） | 官方发布稿 + 模型 config 静态核对 |
| 位置编码 | 未特别处理 | 页级有界坐标 + 页内单调坐标 | 官方发布稿（v2 §3.3.1 式 3；config `page2d`） |
| 长文档推理 | 单次前向，受 prefill 限制 | 分块解码 + 边界页/文本 KV 复用 | 官方发布稿（v2 §3.4、Alg. 1） |
| 训练序列 | 32K | 64K | 官方发布稿（v2 §4.2） |
| 训练数据 | 2M，9:1 单页/多页，2–50 页 | 2M 多页 + 10M 单页，伪标签来自 MinerU2.5-Pro 与 PaddleOCR-VL-1.6 | 官方发布稿（v2 §4.1） |
| 训练配置 | 4000 步，8×16 A800，Megatron | 1 epoch，25×8 H800，MS-Swift，冻结 encoder+aligner | 官方发布稿（v2 §4.2） |
| 页数上限 | 实测 40+；32K 上下文（§7 承认有限） | 基准 100–300 页；声称“任意页数” | 论文报告（v1）／官方发布稿（v2）／3600+ 页只在通稿与媒体里 |
| 峰值显存 | 未给绝对值（只给 cache 比值） | KV cache 47.00 GB → 1.77 GB（$B=1$，MarathonDocBench） | 官方发布稿（v2 Table 4、§5.3.1） |
| 单页精度 | 93.23（v1.5）/ 93.92（v1.6） | 94.02（v1.6） | 论文报告 / 官方发布稿，条件见上表 |
| 多页精度 | MPDocBench 61.89 | MPDocBench 84.59；MarathonDocBench 77.06 | 官方发布稿（v2 Tables 1–2） |

速度与显存的口径要分开读。7.0×/5.6× 是**单步解码延迟**，条件是 Gundam 模式、batch 3、每页固定生成 1024 token，横轴到 100 页（§5.3.3、Fig. 6b）；360→1315 TPS 是**16 路并发的端到端吞吐**，条件和 $B=1$ 的显存那栏不是同一件事（Table 4）。47.00→1.77 GB 降幅约 96%，也只算 KV cache，不含权重与激活（**媒体报道**量子位同样强调这一点，与报告一致）。至于“一口气 3600+ 页《哈利·波特》”，出自发布会通稿与媒体报道，v2 报告里没有这个实验；报告能支撑的上限是 300 页基准与 100 页级的延迟曲线（**媒体报道**：新华网、量子位；量子位另自测了 884 页《指环王》，42 分 56 秒、平均约 2.9 秒/页——那是媒体的测试，不是作者报告）。

## 失效边界

作者明确承认的退化有四类。其一是**页数/上下文上限**：v1 §7 说有限 32K 上下文加 prefill 长度决定了做不到真正 unlimited；v2 于是把问题改写成“分块 + 固定块内缓存”，并在 §6 承认稀疏注意力不保留全局文档信息，限制了标题层级等文档级结构理解。其二是**小字与低分辨率**：v1 §5.4 把 40+ 页的重复错误归因于多页时 DeepEncoder 只能用 Base 模式（1024×1024），而非 R-SWA 迷失方向；这条归因是作者自查，没有分离页数与分辨率两个因素（我们的判断）。其三是**随页数下降的精度**：Table 3 的 0.0362→0.1069 与 96.90% Distinct-35 是可复查的退化曲线。其四是**分块窗口太小**：v2 README 的推理说明承认较小的页窗口能降显存，但跨窗口边界的块会丢上下文、损害跨页合并（L163）。

作者**没有讨论**的情形需要点名：手写、竖排/东亚竖排、拍摄畸变与低质扫描、超长或跨页表格的单元格关系。v1 的 Table 2 按 9 类版面拆了编辑距离，其中报纸（文本 0.081、阅读顺序 0.134）与笔记（文本 0.066）是表内相对高的两项，但论文没有说明这些类别是否含手写或竖排样本，因此**未能确证**；跨页表格在 v2 有间接信号——MarathonDocBench 上 T-TextEdit 0.123、T-TableTEDS 71.11 都差于页内同类指标（0.104、74.81），说明跨页续接确实是更难的子问题，但这是我们的读表判断，作者未把它列为失效边界。

还有一处只能算半承认：v2 的稀疏路由默认只对图像 token 生效（config `dash_image_only=true`），文本走局部窗；当页面内容与“当前正在抄的那一页”关系很弱（例如跨章节引用、图谱式版面），固定预算的参考集可能漏掉关键证据。报告没有做这方面的失败案例分析（我们的判断）。

## 怎么读这条路线

两篇的分工很清楚：v1 给出了一个**可证的解码侧内存上界**，并把它变成一个能力主张——单次前向读几十页；v2 发现这个上界没解决“每步还要扫全部视觉 token”，于是把参考集也做成固定预算，并用分块解码把“页数”从显存里彻底摘出去。机制上，这是把“工作记忆”从“全文 + 最近 128 字”改成“最近一页 + 少量被检索到的页”，与人类抄书的类比是自洽的，也是这条线最有解释力的部分。

但证据强度要分层。**严格成立**的是式 6 的 cache 上界和 v2 的分块显存账（Table 4）；**依赖作者测量**的是精度与速度的所有数字；**尚未被控制变量支持**的是“R-SWA/SR-SWA 带来了精度提升”——v1 续训了 2M 数据、v2 又在 12M 量级数据上重训并扩到 64K 上下文，两代都缺少“同数据、同预算、只换注意力”的消融。窗口宽度 $n=128$ 也从未做敏感性分析：它同时决定了成本上界和模型能记住多少自己刚写的内容，128 这个数目前只有“跑得通”的证据。

真正值得追的问题是**跨页一致性如何度量**。两篇都用编辑距离、TEDS 和 Distinct-n，这些指标能抓到重复与漏字，却抓不到“第 3 页的表头在第 5 页被写错”“跨页表格的行列关系错位”这类错误；MarathonDocBench 引入 T-TextEdit/T-TEDS 是朝这个方向的进展，但作者报告里没有给跨页错误的分类统计。若要判断“不限页数”在真实年报、手册、书籍上是否可用，需要按页数分档的跨页结构错误率，而不只是平均编辑距离。
