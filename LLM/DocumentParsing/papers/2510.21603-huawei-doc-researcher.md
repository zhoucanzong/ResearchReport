# Doc-Researcher：把文档解析接到多轮证据检索

> Kuicai Dong et al., *Doc-Researcher: A Unified System for Multimodal Document Parsing and Deep Research*, arXiv:2510.21603v1（2025-10-24，作者单位 Huawei Technologies Co., Ltd.）。依据[官方完整 HTML 原文](https://arxiv.org/html/2510.21603v1)精读，重点参照 §1、§3–5、Appendix A–C。原文头部含有未替换的会议模板字段（如 `Conference: xxx`、虚构的 2018 会议行及 2009 收稿日期），因此本文只按 arXiv 预印本引用，不推断会议录用或同行评审状态。

## 它不是一个新的 OCR 模型

多数 OCR 评测问“一页里的字和结构解析得怎样”；Doc-Researcher 问的是：如果读者要跨几十份报告寻找证据、比较表格和图示，再多轮提出追问，系统能否保留足够的视觉与结构线索来完成研究？因此它更像把解析、索引和研究型检索组合起来的系统论文，而不是一个替代 PaddleOCR 或端到端 OCR 的识别器。

它的关键观察是两种常见简化各有损失：只保留 OCR 文本，图表与页面布局容易消失；只把整页截图交给 VLM，细粒度定位和密集文字访问困难。Doc-Researcher 选择把页面拆成结构化元素，同时保留原始页面/图像入口，让后续检索按问题需要选择粒度和模态。（§1、§3.1）

## 解析输出怎样变成可检索的多粒度证据

系统调用 MinerU 对文档做布局感知解析，提取带类别、阅读顺序和边界框的文本、表格、图和公式；表格与图片用 Qwen2.5-VL 生成粗摘要和细描述，公式由 UniMERNet 转成 LaTeX。随后把内容组织成四种粒度：按章节合并的 chunk、整页内容或页面截图、全文，以及由全文生成的文档摘要。页码和框坐标保留在表示中，生成报告时可用于回链到原页面位置。（§3.1）

研究流程由 planner、searcher、refiner、reporter 协作：planner 根据问题和历史挑相关文档、选择 summary/page/chunk/full 粒度并拆子查询；searcher 支持文本、视觉和混合检索；refiner 去重、筛相关内容并判断证据是否充足；reporter 再组合证据并输出带页面/框位置的引用。（§3.2–3.3）

这里最重要的设计不是“多 Agent”标签，而是解析结果要能随问题切换粒度。宽泛背景问题可以从摘要开始，查某个表格数值时则转向页或局部元素；迭代检索可把相似但无答案的文档作为硬负例排除。代价是系统前处理和索引更复杂；如果提取器漏掉图表语义或生成了错误描述，这些错误会进入后续检索和答案链。

## M4DocBench 把“研究型问题”拆成可检查的链

作者提出 M4DocBench，包含 158 个专家标注问题和 304 份文档，覆盖研究、保险、教育和金融四类。平均问题需要处理 12.7 份文档、306.4 页；最长实例涉及 42 份文件和 836 页。标注不只给最终答案，还包括相关文档、证据页与区域框、最佳检索粒度、子问题拆分及答案核对清单；58 个问题处于多轮对话中。（§4.2–4.4）

这让系统评测超越了单文档 VQA：答对一句话仍不够，系统还要找到正确资料、定位到能支撑答案的区域，并覆盖清单中的原子事实。答案评分用带 checklist 的 LLM judge，必须所有检查项通过才算正确；检索 Recall@k 按文档、页面、版面区域三个层次计算。（§5.1）这能揭示检索和综合各自的瓶颈，但 judge 评分仍依赖模型判断，且 158 题的四领域 benchmark 不代表所有企业文档和研究任务。

## 结果说明解析、检索和规划须合看

论文在 M4DocBench 上报告，结合深度解析、混合检索和 DeepSeek-R1 的配置达到 50.6% 的答案准确率；对应消融中移除 planner 后降至 42.9%。（§5.4、Table 3）这支持 planner 与粒度选择对该系统设定有贡献，但不能把 50.6% 归功于 OCR 单个组件：配置还包括 MinerU 解析、Jina 多模态检索、Search-Refine 循环和 DeepSeek-R1 Reporter。

作者比较 text-only、vision-only 与 hybrid 检索，发现混合检索在若干页面/布局召回指标上表现较强；但多向量检索和跨模态 late-interaction 会增加索引与存储开销。论文报告预解析有较高一次性成本，换来多问题复用时的检索效率；这属于其 304 文档、特定模型和实验硬件下的作者测量，不是通用服务时延承诺。（§5.2、§5.6）

## 证据边界与阅读判断

- **解析器来自现有工具组合。** 主要版面解析调用 MinerU，图表解释和摘要调用 Qwen2.5-VL，公式识别调用 UniMERNet。研究贡献在多粒度表示和自适应研究循环，而非发明新的 OCR 编码器。
- **多组件效果难拆因。** 50.6% 反映一个完整系统，benchmark 同时测检索、规划、证据收集和答案综合；需要结合去 planner、不同检索路径等消融，不能直接外推成某 OCR 方法的优势。
- **数据范围有界。** M4DocBench 覆盖四类文档和 158 个问题，证据链详细但规模有限；各领域、语言和用户问题分布不能代表生产文档库。
- **报告元信息有明显模板残留。** arXiv 页面正文显示 Huawei 作者署名，但会议名、日期等字段没有正确填充；因此本精读只称其为 arXiv 预印本技术系统论文，不把格式残留补猜成正式会议出处。

这篇工作把 OCR/文档解析的下游目标从“把页面转成 Markdown”推进到“保持可定位证据，支持多轮跨文档研究”。它适合与 OmniDocBench、MDPBench 的页面级评测互补阅读：前两者关注解析组件和输入条件，Doc-Researcher 关注这些结构能否支撑后续证据检索与综合；三类指标不能混成一个总分比较。
