# Xiaomi-OCR-0：0.8B 两阶段，一套权重同时干解析与理解

> 小米，*Xiaomi-OCR-0 Technical Report*，arXiv:2609.36136v1（2026-09-28）。依据[官方完整 HTML 原文](https://arxiv.org/html/2609.36136)精读，重点参照 §2–3、§4.1–4.3、§5.2/§5.4，尤其是 Figure 3 与 Tables 1–3。数字均标注基准版本；本文未独立运行模型、未重算指标。

## 一句话：把"解析 + 理解"塞进同一套 0.8B 权重，版面仍然外置

Xiaomi-OCR-0 从 **Qwen3.5-0.8B** 初始化，是一个同时支持文档解析与**以 OCR 为中心的理解任务**（VQA / KIE）的 0.8B 模型（§1）。它没有换成端到端整页生成：正文比较里用的是**两阶段推理**——**PP-DocLayoutV3 检测区域 → Xiaomi-OCR-0 逐块识别 → 拼回整页**，并且明确写着"**报告的 0.8B 参数量不含外部版面检测器**"（§4.1）。

所以它的卖点不是架构新，而是**训练侧三件事的组合**：约 **170M** 样本的 OCR 语料（自动数据引擎造）、**Q-Mask 文本锚定**预训练、以及**混合任务强化学习（Mix-RL）**。这三件事凑起来，让 0.8B 的身板在解析上进入第一梯队，同时还能答 DocVQA / ChartQA 这类题。

## 与 MiniCPM-OCR 同路线，差在"分工"

这是你点名要讲清的地方。两者共享同一骨架（Qwen3.5 系底座 + 外置 PP-DocLayoutV3 + 区域级 prompt），差别在**产品形态与训练分工**：

| 维度 | Xiaomi-OCR-0 | MiniCPM-OCR（`20261027-minicpm-ocr`） |
|---|---|---|
| 参数 | 0.8B（不含版面模型） | 1.3B（不含版面模型） |
| 解析与理解 | **同一套权重**同训（解析 + VQA + KIE） | 解析交给 1.0，**判断题交给独立的 Jev 2B** |
| 质量判别 | 无独立判别模型 | 有（Jev 输出 0–1 分，可路由人审） |
| 加速 | 沿用基座自带的**单 MTP 头** | **DSpark** 外挂配套草稿模型 |
| 训练配方 | **公开**：Q-Mask 文本锚定 → CPT → Mix-RL | **未披露**（官方明说不据架构名反推） |
| 数据 | **公开**：约 170M 样本 + 三件套自动标注 | 未披露 |

一句话：**MiniCPM 走"解析器 + 判别器"的双模型分工，Xiaomi 走"一个模型两种任务"的统一路线**。前者在流程上多了"要不要复核"这一环，后者省一个模型但拿不到质量分。两条路线不冲突，选型取决于你是要"更省人审"还是"更少部署件"。

## 数据引擎：共识、渲染校验、定向合成

规模上，语料约 **170M** 样本，四条自动流水线（§2）：

- **专家三元组共识**（§2.1.1）：从模型池里取三个模型对同一区域互为参照，按两两一致度分档决定"直接采信 / 进入校正 / 转人工"。这是把"多模型投票"制度化的做法，比单模型自标更稳，但**共识偏差会被放大**——三个模型一起错的样本会被当成正样本。
- **渲染引导的 Refine-and-Judge**（§2.1.2）：把候选文本渲染回图像，与原始裁剪比对，迭代纠正（与 MiniCPM 的 Jev 输入思路同源，但这里用于**造标注**而非**打分**）。
- **多因子样本挖掘**（§2.2）：聚类采样保证覆盖，另做难样本挖掘。
- **定向合成**（§2.3）：一路按覆盖缺口补常规结构与低资源场景（书法、特殊字体用字体文件 + 参考作品 + 真实背景做视觉先验，注意"在各自授权范围内"），一路按**错误诊断**驱动生成难样本。

## Q-Mask 文本锚定：把"文字在哪"变成预训练目标

第一阶段不是普通图文对齐，而是 **Q-Mask** 式文本锚定（§3.1、Figure 3）：给模型加一个 **query-conditioned mask decoder**，同时监督**空间掩码**与答案 token，目标函数是 Q-Mask 的 **SSA**（Spatial Supervision Alignment），即**下一 token 预测 + 掩码预测联合优化**。训练数据是 TextAnchor-26M 加上用同一构造方案转换过来的文档解析样本——**把空间监督从场景文字扩展到文档区域**。

第二阶段 CPT：**移除 mask decoder、保留主干**，用标准 NTP 训练多任务 OCR 输出，同时**保留基座已带的单个 MTP 头**一起训（§3.2）。第三阶段 **Mix-RL**：在挖出的难样本上，用**可验证的任务奖励**同时优化解析与理解，理由是 token 级交叉熵不直接惩罚结构错误、漏字段、读序问题（§3.3）。

§5.4 还做了一个有价值的对照：**Mix-RL 与多教师 on-policy 蒸馏（MOPD）**——MOPD 用更少算力就能到可竞争的解析水平，而更长的 Mix-RL 在两个能力上最终更高。这条对做同类模型的人有用：**预算有限时蒸馏更划算，预算充足时 RL 的天花板更高**。

## 口径：三个数字，两种来源

| 数字 | 基准 | Xiaomi 自报 | OpenBMB 汇总表（`20261027-minicpm-ocr`） | 差 |
|---|---|---|---|---|
| **96.83** | OmniDocBench **v1.6** | 96.83（§4.2.1、Table 1） | **96.83** | 0（转引，同值） |
| **95.24** | Real5-OmniDocBench | 95.24（§4.2.2、Table 2） | **92.73** | **−2.51** |
| **87.94** | Wild-OmniDocBench | 87.94（§4.2.2、Table 3） | **92.06** | **+4.12** |

三行数字合起来说明一件事：**OpenBMB 那张表的对手列来源不统一**。v1.6 一列与该模型自报完全一致（转引）；Real5 与 Wild 两列与之明显不同，说明是**第三方重跑**。而重跑的方向不一致（Real5 更低、Wild 更高），最可能的原因是 **Wild 列做了旋转/去斜校正**——OpenBMB 的复现文档明写"本项目的 Wild 分数是经 SDK 旋转校正后的结果"（`docs/benchmark_reproduction_en.md:51`），而 Xiaomi 报的 87.94 是原始图。Real5 的 2.51 分差则更可能来自版面模型版本或匹配实现，**我们无法从公开材料确定，记为未能确证**。

**引用的正确姿势**：说 Wild 时写"Xiaomi-OCR-0 87.94（原始图）／92.06（旋转校正后，第三方重跑）"，别只挑一个数；说 Real5 时写"95.24（自报，PP-DocLayoutV3 两阶段）"，并注明版面模型外置。Real5 的集子本身是 **6,775 张重拍图 = OmniDocBench v1.5 的 1,355 页 × 5 种采集条件**（§4.2.2），与 MinerU 描述的"每场景 1355 页"一致。

其他指标各说各的：Wild 上读序编辑距离 **0.1931**（对比中最优），但总分 87.94 低于 TeleOCR 的 88.53；v1.6 上公式 CDM **98.50** 为对比最高，文本与读序编辑距离不如 OvisOCR2、表格不如 TeleOCR（§4.2.1）。理解侧五个基准（DocVQA / InfoVQA / ChartQA / OCRBench / TextVQA）平均 **83.2**，自建 KIE 基准 **59.09%**（§4.3）——KIE 是自建集，不能与别家 KIE 数字并表。

## 为什么它的强项是公式（一条判据）

作者自己给了一个解释：公式 CDM 最高（98.50），与数据引擎用 **CDM 做专家一致性判据**、并对争议标注做**渲染引导校正**直接相关；他们把这称为可能的"任务偏向"——**标注方案会塑造模型的相对强项**（§4.2.1）。这条判断比"公式能力强"有用得多：它提醒我们，一个模型的强项分布可以反推出它的数据管线偏好。

## 边界

- **解析的强项与弱项都很具体**：公式第一，但 Wild 总分落后 TeleOCR（88.53）、表格重建仍有空间（§4.2.2）；也就是说"最强"是分项的，不是全科。
- **判别能力缺失**：它不给"这段对不对"的分，若要人审路由，仍需外接判别模型（如 MiniCPM 的 Jev）。
- **共识式标注的固有风险**：专家三元组共识会放大共同偏差；渲染校验只能抓"渲染后明显不一致"的错误，抓不到"三个模型一致地错"（我们的判断）。
- **理解能力是自建口径**：83.2 是五个公开基准的平均、59.09% 是自建 KIE 集，**不能与 HunyuanOCR 的 MORE 149 语种或 MiniCPM 的 KIE 示例对比**。
- **训练配方公开但复现成本高**：170M 样本 + 三阶段 + 4B 教师模型对照，外部很难从零复算；论文给的是配方，不是可复现产物。
- **未能确证**：Real5 与第三方重跑差 2.51 分的具体成因；0.8B 参数量在不同框架下的实际显存占用。
