# HunyuanOCR-1.5：用短板驱动的数据和并行草稿加快文档生成

> Gengluo Li et al., *HunyuanOCR-1.5: Making Lightweight OCR VLMs Faster and Better*, arXiv:2607.04884v3（2026-09-17）。依据[官方完整 HTML 原文 v3](https://arxiv.org/html/2607.04884v3)阅读，重点参照 §3–7、附录 C–D，尤其是 Figure 1–4、Tables 2–3、6–14。`paper-fetcher` 获取题录；arXiv 当前版本页显示 v3。文中数字为论文报告结果，并注明基准、解码框架或并发条件；本文未独立核验数字、重算指标或复现实验。

## 1.5 沿用端到端模型，把改进放在两个瓶颈上

HunyuanOCR 已把文字定位、文档解析、字段抽取、视觉问答和翻译放进一个约 1B 参数的 OCR 专用 VLM。1.5 没有重新设计这个主干，而是处理两类瓶颈：一类是能力边界，尤其是低资源语言、古文字、复杂表格/图表和跨页理解；另一类是输出效率，整页结构解析常常要连续生成很长的 Markdown、HTML 或 LaTeX，逐 token 解码使页面延迟变高（§1、§3.1–3.2）。

模型仍采用原生分辨率视觉编码器、Adaptive MLP Connector 和 Hunyuan-0.5B 语言模型；视觉输入上限从 2K 提到 4K，上下文扩至 128K。它保留端到端输入到结构化输出的路径，不显式切成布局检测、区域识别、结果合并几个模型阶段。更高分辨率让细小结构有机会进入视觉表示，更长上下文容纳多页、多图和长输出；代价是视觉输入和上下文计算更大。论文的策略是保留已验证的紧凑骨干，把新增成本投到分辨率、数据和解码改造上（§3.1、§5.1）。

## DFlash 为什么适合表格、公式和长页面

普通自回归解码每生成一个 token，都要再运行一次目标模型。推测解码先由较小草稿模型提出多个候选，再由目标模型并行验证；若候选前缀通过，就一次接受多个 token，否则从拒绝处按目标分布继续，因此目标模型的输出分布得以保持（§3.2）。HunyuanOCR-1.5 使用 DFlash：一个约 90.7M 参数的 block-diffusion 草稿模型，以目标模型此前的隐藏状态为条件，在一次并行前向中预测长度为 16 的候选块；目标模型随后验证并接受最长有效前缀。论文用 16 个 anchor、5 层 Transformer 草稿模型训练该预测器（§3.2，Figure 2）。

它针对的是局部高度可预测的输出：HTML 表格标签、公式片段以及结构化 Markdown 有较强的连续规律，草稿块更可能被整体接受。输出越长，少做的目标模型解码轮次越有价值。论文在 OmniDocBench 上报告的有效接受长度约为 8–10 token（§7.1，Table 2）；这个量描述每轮推测中被接受的长度，不是模型一次生成整页的 token 数，也不直接等于端到端加速倍数。短输出、草稿预测不准或 GPU 已被并发请求占满时，草稿计算未必能换来相同比例的延迟收益。

## Agentic Data Flow：先找到能力缺口，再让 Agent 建生产线

1.5 的能力扩展不是把训练数据一味做大，而是先列出模型短板，再把它转成可以执行的数据需求。Agent 可调用网页搜索、OCR/VLM 服务、PDF 与图像处理脚本、清洗和生成工具；它搜索素材、验证字体或图像、构造合成样本、开发数据流水线，并在算法工程师检查样例和反馈后迭代（§4.1，Figure 3）。这是一个“短板—素材—质量检查—数据管线—训练”的闭环，Agent 负责数据生产步骤，人类工程师仍参与中间样本审核和约束修订。

论文具体展示三种用法：针对低资源语言收集语料和字体，构建覆盖 331 种语言的解析数据；为七种汉字历史书体搜集字体和古籍风格背景并合成古文字样本；从多页 PDF 提取逐页文本和结构，再生成跨页检索、比较和证据汇总问题（§4.2）。新数据进入重新规划的 Stage 3，同时混入旧版 OCR 数据以保留原能力；SFT 和 RL 使用拆分的数据，困难样本主要留给 RL。作者报告最高输入分辨率 4K 和 128K 上下文（§5.1–5.2）。这使新增能力与旧版数据混训，但“覆盖 331 语言”表示训练数据覆盖设计，并非每种语言有同等样本量，也不能自动证明每种语言的实用准确率。

这套工作流最有启发性的部分是把 Agent 用在长尾数据工程，而不是把“Agent”当作模型推理时的 OCR 功能。论文详细讲了素材搜索、工具校验和管线迭代，却没有完整给出 Agent 在各任务上的人工工时节省、自动样本通过率、流水线失败率或与纯人工/脚本基线的对照。因此，原文支持“Agentic Data Flow 可组织并产出作者需要的数据”，但不能单凭这些实验断言任意研究团队都能以更低成本复制该流程。

## reward 也从文本相似度走向结构和视觉忠实

1.0 已为定位、解析、问答和翻译配置不同 reward。1.5 进一步指出，单一字符编辑距离无法公平评价 HTML 表格的行列/合并关系，也无法充分描述图表元素关系；它把全文拆为普通文本和表格/图表等特殊元素，分别计算文字与结构化元素 reward，再组合（§5.3.2）。表格 reward 结合内容与结构：作者指出标准 TEDS-S 对错误部位不够可诊断、字符级内容距离也会误罚等价表达，于是加入 1D probe 结构分和 anchor-guided 去格式化的内容分。图表 reward 则尽量降低仅仅改变行列顺序对语义等价图表的误罚（§5.3.2）。

另外两类 reward 分别处理开放式问答与生成稳定性：VQA judge 比较参考答案的事实和语义一致性，翻译 judge 使用源文本等辅助信息给软分；重复片段、循环生成和过长输出会被 degeneration-suppression 惩罚（§5.3.3–5.3.4）。论文把这些奖励放在同一强化学习体系中，并采用 IcePop 处理训练与推理分布不一致。这里的设计取舍是：结构任务用专用可计算信号提高粒度，开放任务借助 judge 扩大覆盖，稳定性惩罚压制明显退化。judge 的标注质量、结构解析器自身误差和各项 reward 权重仍会影响优化目标；论文结果不等于这些 reward 对真实文档错误已经形成无偏度量。

## 能力覆盖的证据比单一 OCR 分数更宽

论文用一组不同类型的基准刻画能力边界：OmniDocBench v1.6 测整页打印/扫描文档的文本、公式、表格和阅读顺序；OCRBench 测 OCR 感知问答；MORE 测 149 种语言的解析；Chronicles-OCR 测古文字；TableVerse-5K 和 ChartArena 测复杂表格、图表结构；DUDE 测多页文档问答；CHAOS-Bench 刻意扰动页面上的词，测模型是否忠实保留图像里实际可见的词（§6，Table 1）。其中 spotting、信息抽取和视频字幕使用内部测试，其余能力评测主要采用公开基准（§6.1，Table 1）。

在公开基准的论文报告中，HunyuanOCR-1.5 于 OmniDocBench v1.6 获 94.74 总体分，比较组中端到端 OCR 专用模型的分数范围从 DeepSeek-OCR 2 的 90.25 到 Unlimited-OCR 的 93.92（§7.3，Table 12）。总体分由多种指标合成；同表也分列文本编辑距离、公式 CDM、表格 TEDS/TEDS-S 和阅读顺序编辑距离，不能把 94.74 当作字符识别准确率。作者特别指出，OmniDocBench 对多行公式按单行切分匹配，与模型将整组公式作为一个 LaTeX 结构输出不完全一致，可能低估某些公式结果（§7.3，Table 12 后讨论）。

长尾能力也用各自指标报告：MORE 上 149 语言总体分为 91.90，Chronicles-OCR 的古文字/成熟书体平均分别为 0.54/0.79，DUDE 验证集得分 54.64；CHAOS-Bench 的页面平均被扰动词召回为 14.15（§7.2，Tables 7、10–11）。这些分数属于不同任务，量纲和难度都不一样。CHAOS-Bench 的值尤其不应误读为常见文档的 OCR 准确率：它测的是人为把词改成无意义拼写后，模型会不会照视觉内容原样输出，旨在暴露语言先验覆盖图像证据的倾向。作者在内部无文字图像集上还报告“无文字时不生成框”的准确率由 1.0 的 78.1% 提升至 1.5 的 99.8%（§7.3）；这仍是内部负样本集合上的结果。

## 分清解码延迟与系统吞吐

**单请求延迟**回答一张文档在给定推理栈上要等多久。论文在 OmniDocBench、batch size 1 下比较自回归与 DFlash：vLLM 下平均每页延迟由 3.032 秒降到 1.408 秒，作者报告加速 2.14 倍；Transformers 下报告 6.37 倍（§7.1，Table 2）。这些是推理端到端论文数据，包含目标模型、草稿模型、框架和页面输出长度的共同影响。原文还指出，短输出的收益较小、长输出收益更大（§7.1，Table 4）。

**并发系统吞吐**回答多个请求同时进入 vLLM 时，系统每秒能处理多少 token 或页面。论文让并发数从 1 增到 32，DFlash 的 TPS/页吞吐随批处理利用率上升；相对自回归的速度优势在并发 4 时达到 2.26 倍，在并发 32 时为 1.80 倍（§7.1，Table 6）。优势随 GPU 饱和而缩小，因为高负载下推测解码可利用的空闲计算更少。故 2.14 倍单请求加速不能直接替代 2.26 倍并发加速，也不能只凭 TPS 推断用户的 p95 延迟或生产 SLO。

论文还把 DFlash 与其他 OCR 系统在同一 OmniDocBench 测试集上比较，报告单请求、每系统一份计算能力相近的加速器实例；对于 GLM-OCR 和 PaddleOCR-VL-1.6 两阶段系统，计入版面分析、区域推理和合并的整页流水线延迟。作者称 DFlash 版每页 1.408 秒、0.706 页/秒，快于这些对照（§7.1，Table 3）。跨系统 token/s 不可直接比较，因为 tokenizer、prompt 和输出格式各异；论文因此主要比较页延迟和页吞吐。原文没有在该表的说明中给出足以完整复刻的硬件型号、软件配置和逐项功耗信息；“同等计算能力”也不等于所有系统底层实现完全一致。这里的数字是论文运行结果，不是本项目测量或独立复现。

## 与 HunyuanOCR 的关系、局限和下一步问题

1.5 的改进可以理解为三条互补路径：Agentic Data Flow 把模型弱项变成数据工程任务；高分辨率与长上下文扩大可接收输入；分任务 reward 与 DFlash 分别改善输出忠实性和生成效率。这些变化共同服务于能力扩展，因此不能把新旧模型差异归为单一因素。相较 [HunyuanOCR v2 精读](2511.19575-hunyuan-ocr.md)，1.5 新增针对复杂表格/图表结构的 reward、长尾能力基准和块扩散式推测解码；它延续了小语言模型加高分辨率视觉输入的端到端主干。

比较数字时要留意基准版本：1.0 论文在 Table 4 报告的 OmniDocBench 总分没有注明子版本，1.5 则明确报告 OmniDocBench v1.6；分数不能直接相减成“模型提升了多少”。同理，训练语料覆盖语言数不等于均衡语言能力，内部 spotting/字幕/负样本结果需要独立外部集合验证；Agent 数据生产还缺少人工基线、成本与错误通过率对照。DFlash 保持目标模型分布的主张来自推测解码机制，但实际速度优势会受输出长度、草稿接受长度、框架调度和并发饱和影响。

推荐先读 §3.2、Figure 2 理解一次草稿如何被目标模型批量验证，再读 §4–5 理解短板怎样转为数据与 reward；接着看 §6、Table 1 建立能力覆盖地图；最后分别读 §7.1 的 Tables 2、3、6 和 §7.2–7.3 的 Tables 7–14，始终把模型质量、单请求延迟、并发吞吐和内部可靠性测试分开理解。
