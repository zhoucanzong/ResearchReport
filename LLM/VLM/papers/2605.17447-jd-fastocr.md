# FastOCR：文档图像很稠密，但每一步只需看局部

> Zihan Tang et al., *FastOCR: Dynamic Visual Fixation via KV Cache Pruning for Efficient Document Parsing*, arXiv:2605.17447v1（2026-05-17；作者单位为清华大学与 JD.com）。依据[官方完整 HTML 原文](https://arxiv.org/html/2605.17447v1)精读，重点参照 §1、§3–4、Appendix B、G，特别是 Figures 1–5、Tables 1–4。所有性能数字均为论文报告结果；没有在本机运行模型或基准。

## 为什么普通 token 剪枝会伤 OCR

自然图像通常有冗余：删去一部分视觉 patch，模型仍可能看出“这是一只狗”。文档页不同，小字、符号和表格线几乎每个都承载信息；在解码前永久丢掉 patch，字符可能再也找不回来。已有一些剪枝方法在图像编码或 prefill 阶段固定删除 KV cache 项，对文档 OCR 可能造成不可逆损失。（§1–2）

FastOCR 的观察是：页面整体信息很密，但模型在**每个生成步骤**里注意力集中在局部区域，且连续步骤的关注位置缓慢移动。于是问题可以从“整页哪些 token 永远不重要”改成“这一 token 输出时，哪些视觉位置当前最相关”。它让完整 KV cache 留在内存中，只在注意力计算时动态选择子集。

## 两种焦点复用把局部选择延伸到深度和时间

FastOCR 有两个机制。**Focal-Guided Pruning** 先用前 (w) 个解码步骤作轻量 warm-up，统计各层图像注意力占比，挑出图像注意力集中的 focal layers；之后这些层仍可访问完整 cache，选择当前最相关的图像 token，再把选出的集合传给中间非 focal 层。焦点层之间留出最小间隔，避免相邻层全部承担昂贵的完整注意力。（§3.1）

**Cross-Step Fixation Reuse** 利用相邻生成步的注意区域变化较小这一观察，把上一步最深 focal layer 选出的图像 token 集合作为下一步开头的热启动；后续焦点层再重新刷新集合。（§3.2）类比阅读时眼睛从一个词移动到下一个词：保留整页信息在“缓存”里，但这一刻先查当前行附近。

这个设计与永久删除信息不同：全量 KV 仍可被 focal layers 重新访问。代价是它仍须存储完整 cache，而且 warm-up 后焦点层集合固定；方法针对计算与内存访问，不是 peak KV memory 的压缩方案。

## 结果中最容易混淆的“只看 5%”

论文用 Qwen2.5-VL（3B）和 dots.ocr（1.7B）作主比较，并在 DeepSeek-OCR、olmOCR、LLaVA-OneVision 上检查跨架构表现。对照的物理剪枝基线被调到相同的每步 self-attention FLOPs 预算；主要运行在 NVIDIA H800。（§4.1）

在 OmniDocBench 上，论文报告 Qwen2.5-VL 使用默认保留率 τ=0.05 时，总体分数为 71.34，相对未剪枝版本 72.76 保留 98.0%；此处的“5%”指每个解码步骤参与注意力的**图像 token 比例**，不是只保存 5% KV cache。相同 FLOPs 预算下，常见物理删除基线明显损伤文字、表格和阅读顺序分项。（§4.2，Table 1）

论文另报告 Qwen2.5-VL 在 batch 12、4096 输入/1024 输出配置下，自注意力延迟从 26.00ms 降到 8.69ms（2.99×）；但单步端到端解码延迟从 54.15ms 降到 38.69ms（1.40×）。（§4.1，Table 2）这一区别很重要：被优化的 attention kernel 不是整个生成步骤，FFN 等其余计算仍在，所以 3× attention 加速没有转化成 3×端到端速度。

## 消融解释它为什么需要两项机制

在 Qwen2.5-VL、OmniDocBench 上，作者报告完整 FastOCR 总体分数 71.34；关闭跨步复用、保留 focal-layer 选择后为 51.22；两项都关、只在解码时做简单裁剪则为 24.09；未剪枝基线为 72.76。（§4.3，Table 4）这支持作者的机制判断：先找出哪些层适合看图，再把上一生成步的局部焦点传下去，两者缺一会导致“当前看哪里”很不稳定。

小保留率也有边界。论文的 τ 消融显示，τ=0 时整体分数坍塌至 16.46；τ=0.05 起才恢复到接近未剪枝表现。作者把默认配置选在效率与准确率的折中处，而不是追求最高准确率。（§4.3）

## 适用范围与未解决点

- **计算提速不等于显存解放。** Appendix G 明确指出方法保留全量 KV cache，所以峰值内存仍接近原始模型；它不能在紧内存下自动支持更大 batch 或更长上下文。
- **焦点层会固定。** 一段 warm-up 后，层集合在生成期间不更新。不同页面阶段、长输出任务或跨页状态是否需要动态改选层，论文没有验证。
- **结论围绕密集文档解析。** 作者明确说场景文字、图表理解、GUI agent 等其他密集视觉任务是否也有同样的动态焦点模式，仍待研究。
- **论文报告的延迟是组件级与模型级测量。** 它不等于 HTTP 服务吞吐、并发能力或任意推理引擎中的实际加速；本文不进行服务端性能复现。

FastOCR 不是新的 OCR 识别器，而是在已有 VLM 解码过程中改变视觉 token 的访问策略。它与 DeepSeek-OCR 的视觉压缩路线不同：DeepSeek-OCR 先缩短进入解码器的视觉序列；FastOCR 保留全部视觉信息，只在每个解码步稀疏计算。前者改变表示预算，后者改变逐步访问预算，因此准确率、KV 内存与延迟的比较必须分别读。
