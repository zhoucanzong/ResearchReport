# PaddleOCR-VL：把文档解析拆成版面定位与元素识别

> Cheng Cui et al., *PaddleOCR-VL: Boosting Multilingual Document Parsing via a 0.9B Ultra-Compact Vision-Language Model*, arXiv:2510.14528v4（2025-11-25）。依据[官方完整 HTML 原文](https://arxiv.org/html/2510.14528v4)精读，重点参照 §2–4、附录 A、C，尤其是 Figure 2–5、Tables 1–13。题录由 `paper-fetcher` 确认，arXiv API 显示当前版本为 v4。下文性能数字均为论文报告结果，附原文位置和关键条件；本文没有重算指标或复现实验。

## 核心选择：不要让一个模型从整页图像里一次性“读完一切”

文档解析不只是认出字符。系统还得找出标题、段落、表格、公式和图表的位置，决定多栏页面的阅读顺序，并把复杂元素转成可用结构。整页端到端生成可以联合处理这些任务，但长页面会产生长视觉输入和长文本输出；论文指出，多栏和图文混排时，顺序不稳、漏读和幻觉也更明显。传统模块化流水线可以针对不同元素使用专用识别器，却要维护多个模型及接口，前一步的切分错误也会传给后一步（§1、§2.1，Figure 2）。

PaddleOCR-VL 采取中间路线：先由 PP-DocLayoutV2 找版面区域并预测阅读顺序；然后裁出单个元素，交给 PaddleOCR-VL-0.9B 识别文字、表格、公式或图表；最后把元素结果和版面信息合并成 Markdown 或 JSON。它保留了模块化系统“先确定结构、再专门处理局部”的可控性，同时用一个小型视觉语言模型覆盖多类元素（§2.1，Figure 2–3）。

这意味着它不是完全端到端。版面检测漏掉一个区域、边界切错或阅读顺序排错，后面的识别模型就拿不到正确输入；相反，独立识别器也不能自动修复上游结构。版面模型与识别模型可以分别诊断、训练和扩充类别，但系统准确性仍取决于它们交接处的裁剪、类别和顺序。

## 为什么是动态分辨率视觉编码器加小语言模型

文档图像里，小字和密集公式需要足够像素。把不同尺寸页面强行缩放到固定大小，可能抹掉细节；切成固定小块则会改变整页与局部之间的关系。PaddleOCR-VL 使用 NaViT 风格的原生动态分辨率视觉编码器，让输入按图像实际尺寸编码，减少缩放变形；视觉编码器与 ERNIE-4.5-0.3B 之间用两层 MLP 投影器连接，并加入 3D-RoPE 位置表示（§2.1.2，Figure 4）。

小语言模型的作用主要在生成侧：模型逐 token 输出，解码器越大，每一步计算通常越重。先把页面拆成元素，也能把一次“生成整页结构”的超长输出，变成多个短一些、类型明确的识别任务。动态高分辨率负责尽量看清字形，元素裁剪限制当前任务范围，小解码器降低逐 token 生成负担。这几项设计互相配合；单独把语言模型缩小，无法解决小字在视觉输入中被压没的问题。

布局分析器本身也拆成两步：RT-DETR 检测并分类元素，六层 pointer network 再根据元素位置、类别及成对几何关系预测相对阅读顺序，最后用确定性算法恢复顺序（§2.1.1，Figure 3）。这种顺序建模把“谁在谁前面”明确作为关系预测，而不是让识别模型从长文本生成中隐式猜测。

## 训练数据：规模来自多源组合与自动标注，也留下可见性问题

视觉编码器从 Keye-VL 初始化，语言模型从 ERNIE-4.5-0.3B 初始化；两阶段训练都更新全部组件。第一阶段用论文报告的 2,900 万图文样本做视觉—文本对齐，第二阶段用 270 万样本进行 OCR、表格、公式和图表识别指令微调。第二阶段提高最大输入分辨率，训练数据覆盖不同语言、书写系统、文档类型与视觉复杂度（§2.2.2，Table 1）。

数据构造把公开数据、合成数据、网络可访问文档和内部数据组合起来。自动标注先由 PP-StructureV3 等专家模型产生初始标签，再交给 ERNIE-4.5-VL、Qwen2.5-VL 等多模态模型修订，并做幻觉过滤；针对评测中发现的弱项，作者再用字体、CSS、语料和渲染器合成困难样本，少量边缘案例补充人工标注（§3.1–3.3，Figure 5）。例如文本数据在附录 A 中按行、块、页组织；公式数据结合 LaTeX 渲染与真实公式裁剪，图表则覆盖多种类别。

这样的数据方案有现实优势：收集孤立公式、表格或文字行的图像与标签，比给每一类都找完整页面并标注其全部结构容易；合成也能补自然数据中稀少的语言、字体和版式。但“高质量”仍是作者对筛选与标注流程的描述。论文没有完整公开网络数据来源、内部数据构成和各来源比例，也没有给自动标注全量误差率或人工复核覆盖率。自动流程还可能继承专家模型的识别偏差，再由后续模型在相同偏差上训练；渲染合成样本是否覆盖真实扫描噪声，也不能仅从样本量推断。支持 109 种语言是系统能力主张，论文自建多语评测覆盖面较广，但各语言的公开数据、任务分布和错误率并不等同。

## 页面级和元素级结果回答不同问题

页面级评测测试完整系统把页面解析成结构化文本的能力；元素级评测则尽量隔离 OCR、表格、公式或图表识别器。两者不可互相替代：单个裁剪区域认得准，不保证整页定位与排序正确；页面总分不错，也不能说明某种元素是否是主要短板。

在 OmniDocBench v1.5 上，论文报告 PaddleOCR-VL 的页面级综合分为 92.86，MinerU2.5 为 90.67；综合分由文本、公式和表格指标加权构成。相同表格中，文字编辑距离为 0.035，公式 CDM 为 91.22，表格 TEDS 为 90.89，表格结构 TEDS-S 为 94.76，阅读顺序编辑距离为 0.043（越低越好的是距离类指标；Table 2）。这些是该基准及其评测规则下的系统结果，不能单独归因为视觉编码器或 0.9B 参数规模。

一个更有诊断意义的例子是 OmniDocBench-OCR-block：作者从 v1.5 的页面标注中提取了 17,148 个文字区域图像，尽量排除版面检测影响。论文按文档类型报告结果；例如 Academic Literature 类的文字编辑距离，PaddleOCR-VL 为 0.021、MinerU2.5 为 0.089（§4.2.1，Table 5）。但这些块依赖已有布局标签裁出，因此回答的是“给定正确区域，识别器读得怎样”，不是完整系统在自然页面上的文字识别错误率。

其余元素任务呈现相似的“公开页面基准加自建细分集”结构：表格块测试从 OmniDocBench v1.5 裁出的 512 张表格（Table 8）；内部文字集覆盖 109 种语言及手写、竖排、古文字等类型（Table 6）；图表结果主要来自 1,801 张经过人工复核的中英文自建样本，因为作者认为公开测试集规模、类别平衡和标注质量不足以验证图表能力（§4.2.4，Table 12）。这些结果展示了作者着力覆盖的长尾能力，也意味着部分最强证据来自外部读者难以独立检查的内部数据；跨论文比较时，应先看测试样本、标签来源和指标，而不是把不同表中的分数当作同一尺度。

在 olmOCR-Bench 上，论文报告整体单元测试通过率为 80.0 ± 1.0；这个基准用文档抽取后的可机器检查问题衡量细节错误，和 OmniDocBench 的加权编辑/结构指标不同（1,402 份 PDF、7,010 个测试案例；§4.1，Table 4）。多套评测互补地说明了系统行为，但都不是对任意真实文档的准确率保证。

## 推理速度：报告的是完整系统吞吐，不是单独模型速度

论文将 PDF 渲染、版面分析与元素识别放进三个异步线程，以队列连接；多个页面的元素达到批量阈值或等待时间上限后合批送入 VLM。OmniDocBench v1.0 的端到端速度测量使用单张 NVIDIA A100、512 份 PDF 批次，计时从输入 PDF 路径开始，到生成完整 Markdown 为止（§4.3，Table 13）。

在这组条件下，论文报告 MinerU2.5 使用 vLLM 的吞吐为 1.0574 页/秒；PaddleOCR-VL 使用 vLLM 为 1.3453 页/秒，使用 FastDeploy 为 1.6184 页/秒。作者所称相对领先的 53.1% 是 PaddleOCR-VL/FastDeploy 对 MinerU2.5/vLLM 的端到端页吞吐差异。它同时包含模型、布局管线、批处理和不同后端的影响；同表中 PaddleOCR-VL 换用 vLLM 后吞吐也会改变。因此，这组数字支持“论文给出的整套部署配置能较快处理批量文档”，不能据此说同一推理后端下模型本身快 53.1%，也不能推断单页交互延迟。

## 阅读时保留的边界

这篇工作的主要思路不是用通用大模型吞下整份文档，而是把页面结构识别与局部语义识别分工，并针对小字保留动态分辨率。它与已有流水线的差别，在于将多类元素识别统一到紧凑视觉语言模型；与整页端到端 VLM 的差别，则是保留显式布局阶段和元素裁剪。其收益依赖布局阶段可靠、裁剪保留足够上下文、自动生成数据覆盖真实长尾，以及多任务输出格式能稳定合并。

若表格跨列、图注依赖正文、公式需要上下文消歧，孤立裁剪可能丢掉页面关系；若文档本身没有稳定的“先布局后识别”结构，流水线边界也可能让上游错误成为硬约束。论文报告大量结果，但没有给出控制视觉输入、语言模型规模、布局阶段和训练数据的完整因果消融，因此不能从总分直接判断各组件分别贡献多少。内部数据的来源与比例、类别级错误分析、跨页关系和真实文档工作流中的不确定性，是继续判断其泛化能力时值得追问的问题。
