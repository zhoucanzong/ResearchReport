# HunyuanOCR：把多类文字视觉任务统一到轻量端到端模型

> Tencent Hunyuan Vision Team et al., *HunyuanOCR Technical Report*, arXiv:2511.19575v2（2025-12-11）。依据[官方完整 HTML 原文 v2](https://arxiv.org/html/2511.19575v2)阅读，重点参照 §2–6、附录 C–D，尤其是 Figure 2–4、Tables 2–5、9–10。`paper-fetcher` 获取题录；arXiv 当前版本页显示 v2。下文数字均为论文报告结果，并保留对应基准与实验条件；本文未重算指标或复现实验。

## OCR 专用模型解决的是“读完并交付”，不只是认字

传统 OCR 往往把检测、文字识别、版面分析、信息抽取和翻译串成多个模块。每个模块可以单独替换和调试，但前面漏检一个框或排错阅读顺序，后面的模块就只能处理错误输入；系统还要维护多个模型及它们之间的格式接口。另一种做法是让通用 VLM 直接从图像回答问题，功能覆盖广，却通常带来更高的推理成本，也未必擅长长文本和结构化输出（§1、§2.1–2.2）。

HunyuanOCR 选择一个约 1B 参数的端到端 OCR 专用 VLM：输入图像和任务指令，单模型完成文本定位识别、文档解析、信息抽取、文字图像问答和翻译。这里的“端到端”指不再依赖外置布局检测器或专用后处理模块串起主流程；它不意味着各种任务都用同一个评价指标，也不意味着模型内部显式产出人类可检查的布局中间状态。收益是减少级联接口和误差传播，代价是错误更集中在一个模型内部，排查时较难像模块流水线那样直接定位是哪一阶段失效（§2.1–2.2、§3）。

## 保留高分辨率，再把视觉信息压到小语言模型能处理的长度

模型由原生分辨率视觉编码器、Adaptive MLP Connector 和轻量语言模型组成。图像编码器尽量保留页面原始尺寸和长宽比；Connector 用自适应空间压缩减少视觉 token，同时优先保留文字密集区域；语言部分基于 Hunyuan-0.5B，并以 XD-RoPE 分开表示文本、页面高度、宽度和时间位置。这个设计针对文档图像的两个互相牵制的要求：小字需要高分辨率，解码又需要控制序列长度。压缩因此不是无损保证，作者将“保留关键语义信息”作为设计目标，具体信息损失仍取决于页面结构与输入分辨率（§3，Figure 2）。

模型把差异很大的目标映射到统一的指令—生成接口：文本 spotting 输出文字和坐标；全文解析按阅读顺序生成 Markdown，表格用 HTML、公式用 LaTeX；图表可输出 Markdown 或 Mermaid；抽取任务按提示生成字段或 JSON；问答直接回答；翻译则先读取图中文字，再保留版式结构地翻译（§4.1，附录 A）。因此，“解析”包含识字以外的阅读顺序、元素结构和格式生成；信息抽取或问答还额外依赖语义判断。不能用其中一个任务的成绩代替全部 OCR 能力。

## 数据和奖励要教会模型什么算“读对”

论文把训练数据扩到九类真实场景、超过 130 种语言，并组合合成图文、真实图像、长文档、困难样本和人工标注数据。合成流程可控制语言、字体、方向、版式、光照和几何畸变；同一来源样本还会派生 spotting、解析与问答监督。此处的规模和覆盖范围是作者报告的训练资源描述，详细语料清单、来源占比和逐语言训练分布未完整公开（§4.2，Figure 3；§5.1，Table 2）。

监督微调之后，作者对轻量模型做 GRPO 强化学习。重点是奖励不应只看最终文本是否相似：spotting 用预测框与真值框的 IoU 做匹配，再按识别字符串的归一化编辑距离打分，未匹配框会被惩罚；文档解析按输出相对真值的编辑距离评分；VQA 使用语义正确性判断；翻译则由 LLM judge 给软分。超长输出和不符合结构 schema 的输出直接得零分（§5.2.1–5.2.3）。这样，坐标、内容、结构格式和开放式语义任务各自有相应反馈；相应风险是规则奖励可能偏向与其格式和距离度量一致的答案，而 judge 奖励又把训练质量部分交给评分模型。

论文在附录报告了 RL 前后改善：OmniDocBench 解析得分由 92.5 升到 94.1；spotting 的艺术字和屏幕场景分数提升超过 2；OCRBench 平均分提升 3.3（附录 C.3）。这些是论文报告的消融结果，支持“RL 配合任务化奖励后，多类能力进一步提升”；论文同时改变或筛选了 RL 数据，不能把总增益只归因于某个奖励公式。初版报告的 RL 配置为每个 prompt 采样 8 个回答、温度 0.85、无显式 KL 惩罚（附录 C.1，Table 9）。

## 读数时把识别、整页解析与内部评测分开

原文的文字 spotting 基准是作者自建的 900 张图像，覆盖九类场景、每类 100 张。Table 3 报告 HunyuanOCR 总分 70.92，并按艺术字、文档、游戏、手写、广告、票据、屏幕、街景和视频画面切分（§6.1，Table 3）。这衡量的是检测位置与识别内容的联合能力，不等于通用纯文本准确率；类别构成也是作者设定的固定测试集，不代表实际业务的场景比例。

文档解析使用公开 OmniDocBench，以及作者打印、折叠/弯曲并重拍的 Wild-OmniDocBench 和内部 DocML。arXiv v2 Table 4 报告 HunyuanOCR 在 OmniDocBench 的总体得分为 94.10，Wild 版本总体得分为 85.21；DocML 有 14 种非中英语言，包含数字/扫描和实拍文档，作者报告其总体编辑距离分数在各语言领先（§6.2，Table 4）。Wild-OmniDocBench 和 DocML 当时注明计划后续发布，因而这些多语言和实拍结论不能像公开基准那样由读者直接取得相同数据复核。原文没有在表题写清 OmniDocBench 子版本；这里保留其原文报告口径，不与其他版本分数直接相减。

信息抽取与 VQA 的评测也混合了公开与内部来源：卡证/票据集合为 768 个样本、30 类；视频字幕集合为 1,000 个样本；OCRBench 是公开的 1,000 样本基准。前两者按多字段 JSON 精确匹配，OCRBench 使用官方评测协议。Table 5 中 HunyuanOCR 的 OCRBench 得分是 860，而 Qwen3-VL-2B 为 858；这个接近的总分说明它们在该综合基准上相近，并不能说明每个能力切片相同（§6.3，Table 5）。卡证、票据与字幕结果属于作者自建测试；内部基准的样本选择和标注细节限制了独立核查范围。

## 论文之间的关系与开放问题

HunyuanOCR 的主要研究判断是：OCR 专用 VLM 可以用一个轻量生成模型覆盖定位、结构解析和语义任务；数据质量与细分奖励能让小模型获得多任务能力。后续的 [HunyuanOCR-1.5 精读](2607.04884-hunyuan-ocr-15.md) 沿用相同的端到端骨干，主要把改进转向能力短板的数据构造，以及长结构输出的推理加速。两篇不能只按总体分数比较：基准版本、测试集与任务范围会变化，1.5 也加入了新的长尾能力和不同的 reward 设计。

仍值得追问的是：一个统一模型遇到读序、表格合并单元格或模糊字形错误时，能否给出可靠的置信度并局部修正；自建数据与内部测试在不同语言、字体和拍摄环境上的代表性如何；RL 的收益在公开数据、独立团队复现和真实用户文件上能否保持；端到端省去外置模块后，能否仍提供生产系统所需的字段级可追溯性。论文给出了架构与多任务结果，但没有用控制实验拆出视觉分辨率、数据合成、各任务数据占比及不同 reward 对最终收益的独立贡献。

推荐按 §2.1–2.2 理解流水线与端到端的取舍，再看 §3 和 Figure 2 理解高分辨率编码与 token 压缩，随后读 §4–5 理解任务格式、数据和 reward；最后分别读 §6.1–6.3 与附录 C–D，把 spotting、整页解析、信息抽取和 RL 前后变化对应到各自评测协议。
