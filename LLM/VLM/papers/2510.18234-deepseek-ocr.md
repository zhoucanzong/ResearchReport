# DeepSeek-OCR：把文档文字映射成可压缩的视觉上下文

> Haoran Wei、Yaofeng Sun、Yukun Li，*DeepSeek-OCR: Contexts Optical Compression*，arXiv:2510.18234v1（2025-10-21）。arXiv 提交历史截至本次阅读仅列 v1。依据[官方完整 HTML 原文](https://arxiv.org/html/2510.18234v1)精读，重点参照 §1、§3.1–3.5、§4.1–4.3，特别是 Figure 3–6、Tables 1–4。下文数字均为论文报告结果，注明实验对象与条件；未独立重算或复现实验。

## 它问的不是“能否识字”，而是“多少视觉 token 还能保住文字”

LLM 处理长文本时，序列越长，注意力计算和缓存成本越高。DeepSeek-OCR 把一页文字渲染成图像，再用视觉编码器压缩为少量视觉 token，最后让语言模型从这些 token 中恢复文字。这是一条“文本 → 页面图像 → 视觉 token → 文本”的编码—解码链，作者把它作为长上下文的光学压缩（optical context compression）初步研究。

这里的压缩率定义为标注文本的 token 数除以视觉 token 数。视觉 token 不是被逐字保存的压缩码，而是从图像学习得到的表示；解码结果会丢失信息。因而问题不是压缩比能否无限增大，而是给定页面密度、渲染分辨率和视觉 token 预算，语言模型还能不能还原足够准确的文本。它与通常的文档 OCR 有关联，但研究目标更强调输入 LLM 时节省序列预算。

## DeepEncoder 如何把高分辨率感知与全局建模分开

DeepEncoder 串联两种视觉处理。前段用 SAM-base 的窗口注意力提取局部视觉特征；两层卷积把视觉 token 数压缩 16 倍；后段用 CLIP-large 的全局注意力整合压缩后的特征。设计动机是让高分辨率图像先由较轻的局部注意力处理，再让全局注意力只看较短序列。论文举例：1024×1024 图像先切成 4096 个 patch token，经卷积压缩到 256 个，再进入 CLIP 全局注意力（§3.2.1，Figure 3）。

不同分辨率模式把精度与预算变成可调选择：512×512 的 Tiny 输出 64 个视觉 token，640×640 的 Small 输出 100 个，1024×1024 的 Base 输出 256 个，1280×1280 的 Large 输出 400 个；Gundam 模式组合局部 tile 与全局视图，以便处理超高分辨率报纸等页面。小模式直接缩放；较大模式尽量保留宽高比并填充；动态模式再拼入局部视图（§3.2.2，Table 1）。这不仅调整 token 数，也改变小字经过缩放后还剩多少像素，因此低预算结果不能脱离输入分辨率解释。

解码器是 DeepSeek-3B-MoE，推理时激活参数约 570M。它根据视觉表示逐 token 生成文字或结构化输出。整个系统约 380M 参数的 DeepEncoder 和稀疏激活的 MoE 解码器配合：前者压短视觉序列，后者学习从压缩表示恢复语言（§3.1、§3.3）。

## 数据让模型同时学习识字、结构解析与一般视觉接口

论文把训练数据分为 OCR 1.0、OCR 2.0、一般视觉和纯文本。OCR 1.0 包括扫描/文档 OCR、场景文字以及带版面坐标的交错文本标签；作者报告收集约 3000 万页 PDF，覆盖约 100 种语言，其中中文和英文约 2500 万页，其他语言约 500 万页。精细标注由版面和 OCR 模型辅助生成；作者还从 Word 文档提取内容构造公式、HTML 表格训练对（§3.4.1）。这意味着多语覆盖既来自原始 PDF，也来自自动标注链，不等于每种语言都经过同等规模的人工核验。

OCR 2.0 专门扩展到图表、化学式和几何图形：论文报告用程序渲染 1000 万张图表，以 HTML 表格作为目标；用 SMILES 数据渲染 500 万对化学式图像与文本；几何解析数据为 100 万样本（§3.4.2）。这让模型可以输出图表数据或几何元素结构，但这些合成任务与真实扫描文档中的视觉噪声、语义推理并不等价。

训练先单独训练 DeepEncoder，再训练完整 DeepSeek-OCR。编码器预训练使用 next-token prediction，并混入 OCR 数据和抽样的一般视觉数据；完整模型训练时冻结 SAM 与卷积压缩器，更新 CLIP 部分和语言模型。作者报告完整模型的训练混合中约 70% 是 OCR、20% 是一般视觉、10% 是纯文本（§3.5，§3.4.4）。这种配比解释了它为什么兼具文档解析和一定的一般图像接口，也提醒读者不能把所有结果都视作纯 OCR 监督带来的能力。

## 压缩率实验说明了预算曲线，不是通用无损压缩保证

作者在 Fox 基准上选取 100 页英文文档，文本长度为 600–1300 个 DeepSeek-OCR tokenizer token，并用不要求版面标签的 “Free OCR” 提示测试 Tiny 与 Small 模式（§4.1，Table 2）。论文报告：Small 的 100 个视觉 token 在 600–700 文本 token 区间达到 98.5% precision，压缩率 6.7×；在 900–1000 区间为 96.8%、9.7×；在 1200–1300 区间为 87.1%、12.6×。Tiny 的 64 token 模式预算更低：在 600–700 区间为 96.5%、10.5×，而 1200–1300 区间为 59.1%、19.7×。这里 precision 是论文定义的 OCR 解码精度，不能简单理解为对任意长文本的逐字符无损率。

这条曲线把设计取舍说得很清楚：增加视觉 token 或提高分辨率，能保留更细的字形线索；在极高压缩下，小字会在缩放中变得模糊，复杂布局也更难按正确顺序恢复。作者将接近 20× 时仍有约 60% precision 视作进一步研究的动机，而非实用 OCR 可以接受的准确率门槛（§4.1）。实验只覆盖英语、100 页和所选 token 长度区间，因此不能外推到中文、手写体、跨页上下文或任意文档密度。

## 页面解析分数还包含版面、公式、表格和顺序

Fox 的压缩实验只看文字恢复；OmniDocBench 则测试真实文档解析，把文本、公式、表格和阅读顺序分开计分。论文报告在 OmniDocBench 上，Small 模式每页平均 100 个视觉 token 时，综合编辑距离为英文 0.221、中文 0.284；Gundam 模式平均约 795 token 时，分别降到 0.127 与 0.181（越低越好，§4.2，Table 3）。进一步提高输入分辨率的 Gundam-M 在其 200 dpi 条件下平均 1853 token，综合距离为英文 0.123、中文 0.157。结果支持“预算提高能改善该基准上的解析”，并显示低预算并非对所有页面类型都足够。

类别切片揭示了结构化文档的边界：论文 Table 4 报告，Gundam 的英文报纸编辑距离为 0.122，中文为 0.432；Gundam-M 条件下分别为 0.099 与 0.377。中文报纸在高密度文字下仍明显困难。公式、表格、阅读顺序也各有单独距离，不能由 overall 分数代替。表格尤其依赖视觉 token 是否保留单元格边界和跨行列关系；公式要求细小符号不被缩放抹掉；多栏阅读顺序则需要同时利用局部区域和全页布局。页面压缩成功并不自动意味着这些结构关系都被可靠保留。

论文摘要称在 OmniDocBench 上用 100 个视觉 token 超过 GOT-OCR2.0 的 256 token 配置、用少于 800 token 超过 MinerU2.0 的 6000+ token 平均预算。这是作者报告的对照结果；同一比较涉及不同模型和解析管线，不能解读为统一输入像素、同一系统接口下的纯压缩器因果比较。更可靠的读法是把它看作作者展示“视觉 token 预算—解析质量”折中的例子，再回到 Table 3 查看具体语言、类别与指标。

## 读这篇论文时应保留的研究边界

DeepSeek-OCR 的贡献是把视觉 token 数作为文档转文本的显式预算，并给出不同分辨率下的精度曲线。它证明视觉表示可以承载相当多的文本信息，但没有证明 OCR 视觉 token 是可任意检索、可稳定更新或具备普通文本同等语义访问能力的长期记忆。若生成压缩时遗漏一个数字，后续 LLM 无法仅凭压缩表示恢复原文；高压缩带来的“遗忘”可能是不可逆信息损失，而非可控记忆管理。

结构化解析也受数据和分辨率约束。训练中的精细版面标签部分来自现有模型自动标注，复杂图表、公式和几何大量依赖程序渲染数据；真实报纸、多语小字和跨区域逻辑关系仍是明显难点。论文的训练吞吐和生产页数属于作者给出的系统运行报告，不应与标准化 OCR 准确率混为一谈。

推荐阅读顺序：先看 §1 和 Figure 3 理解“视觉压缩上下文”的问题，再读 §3.2、Figure 4 与 Table 1 看编码器怎样将高分辨率输入映射到不同 token 预算；随后读 §3.4–3.5 理解监督来源；最后对照 §4.1 Table 2 的文字压缩曲线和 §4.2 Tables 3–4 的真实文档结构指标。论文数字均来自 v1 原文；本精读未重算或复现实验。
