# Learning to Discover at Test Time：为一个问题持续训练出一个更好解

来源：[arXiv v2](https://arxiv.org/html/2601.16175v2)，2026-02-05。重点阅读 §2–§4 与 §6；方法核心在 §3.1–§3.3，未来工作见 §6。

## 问题：固定模型做搜索，还是让模型在搜索中继续学习？

Test-time compute 常通过提示冻结模型采样多个候选、复用历史解、再选出高分结果。TTT-Discover 追问：如果一个问题有可验证或连续 reward，能否把同一问题上的试错轨迹回流训练当前模型，使之后候选更可能变好？

## 机制：搜索缓冲区与单问题在线 RL 共同更新

论文将每个科学/工程问题建成一个带奖励的环境。模型从空解或已有解开始提出程序/候选，环境执行并给奖励；状态、动作、结果、reward 写入问题内 buffer，后续通过 reuse 选择有希望的状态，再用本题轨迹更新策略参数。与 Best-of-N 或 evolutionary search 相比，搜索历史不仅作为文本提示，也改变后续策略分布。

但它优化的产物是**一个高 reward 解**，不是一个在新问题上泛化的平均策略。论文明确区分了 finding one best solution 与学习一个可重复部署的高期望策略；因此它处于 TTT 与 test-time search 的交界：搜索提供候选与奖励，TTT 则改变后续候选分布。若任务奖励稀疏、评测器不可靠或 reward 可被投机，测试时更新会更快地强化错误；若输出只需一次有效设计，其评估规则也不同于普通问答。[§2.1–§3.3](https://arxiv.org/html/2601.16175v2)

## 证据支持什么、还没有支持什么

论文报告数学、GPU kernel、算法设计与单细胞分析等尝试，结果覆盖专家或赛事组织者审核的不同任务；每一种环境的 reward、有效性检查和外部验证都不同。一个可执行 benchmark 的速度提升、一个数学不等式的证明检验和单细胞去噪分数不是同一成果等级。论文也把稀疏/二元 reward 与不可验证领域列为未解决情况。[§4、§6](https://arxiv.org/html/2601.16175v2)

## 与 test-time compute 的关系

TTT-Discover 同时使用采样、state reuse 和 RL 更新，所以它是 test-time search 与 learning 的组合案例。若只增加 rollout 并用 verifier 选答案，属于计算扩展；若利用问题内轨迹改变 \(\theta\)，后续生成分布就发生了模型更新。评测时要说明：更新面向哪个单题、使用何种 reward、是否跨题复用参数，以及最终解是否由独立专家/赛事组织者验证。
