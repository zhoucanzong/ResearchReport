# Moshi：用并行语音流取消预先分段的说话轮次

来源：[Moshi: a speech-text foundation model for real-time dialogue](https://arxiv.org/html/2410.00037v1)，固定版本 v1（2024-09-17）。重点读 §3.1、§3.3–§3.4、§5.3、§5.7。

## 研究问题：轮流说话的流水线为什么不是真正的全双工

传统语音助理常依次经过 VAD（语音活动检测）、ASR、文本对话模型和 TTS。每一段都等前一段切分完成，响应延迟会累积；把声音先转成文本再思考，也会丢掉语调、情绪和非语音声学信息。更根本的是，系统假设用户说完后助手才开始，难以建模重叠讲话、插话和犹豫。

Moshi 把问题改成连续的 speech-to-speech 序列建模：模型一边观察用户音频流，一边预测自己的语音流。论文把用户与助手音频分别放进对齐的并行流；每个时间步联合建模 Mimi codec 的语义 token 和声学 RVQ token。推理时用户侧的预测被真实输入音频替代，助手侧流则由模型生成。因为没有固定的 user-turn / assistant-turn 边界，助手可保持静音、开始说话，或在用户继续说话时与其重叠。[§3.1、§3.3.3](https://arxiv.org/html/2410.00037v1)

这不是简单地把 ASR 与 TTS 合并。Mimi 的较低帧率与分层语义/声学 token 使自回归模型可以逐块生成语音；Inner Monologue 再加入与生成语音对齐的文本流。论文观察到加入文本流可改善生成语音的语言质量，并能通过延迟文本与音频通道构造流式 ASR 或 TTS 模式。[§3.3.4、§5.3、Appendix C](https://arxiv.org/html/2410.00037v1)

## 机制取舍：并行流把轮次决定交给序列模型

联合序列把“我是否继续听”“何时开始说”和“我生成什么语音”融入同一时间展开的预测过程，而不由单独的端点检测器切分 turn。模型无需等待一句话完整结束再回答，但因果自回归仍意味着只能使用已到达的音频历史；早说与多听分别影响响应速度和对用户后续信息的利用。

语义 token 与声学 RVQ 层之间也有不同条件路径。论文给声学 token 加 delay pattern，使先产生的语义部分能够参与预测后续声学细节；Mimi 的 12.5 Hz token 帧率对应最小约 80 ms 的时间步。作者报告 Moshi 预训练使用 acoustic delay 2、再以 delay 1 微调，并将理论延迟设为 160 ms；摘要报告实际约 200 ms。这些是论文模型、codec 帧率和推理配置下的作者结果，不等价于自然对话体验或不同端侧部署的真实时延。[§3.3.2、§5.3](https://arxiv.org/html/2410.00037v1)

## 证据边界

- “没有预定义轮次”说明模型不需要外部硬切分用户与助手说话段；不代表它已解决所有打断礼仪、长时间沉默、多人重叠或语义抢话。
- Inner Monologue 有利于文本—语音对齐，但文本流是模型自己的中间通道，不是可验证的完整内部思维记录。
- 论文的分解消融发现 audio delay、Inner Monologue 和 tokenizer 设计都会改变生成结果；时延更低的配置也可能降低语言或声学质量。不能只凭摘要里的 160/200 ms 给实时语音模型排总榜。
- 语音安全、音频记忆和长期连续对话与全双工结构相关，但不是同一实验结论；具体评测见论文 §5–§6。

**带走的区别**：Moshi 把用户/助手语音作为并行流在统一自回归模型中联合推进；它的核心是表示与序列组织，不是一个外置轮次控制器。
