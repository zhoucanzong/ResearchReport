# MiMo-V2.6：把「只 RL 一次」做成可复现的规模化实验（2026-10）

> **一手来源**：**MiMo-V2.6: Scaling Reinforcement Learning Towards Self-Improvement** = arXiv:2610.11959 **v1**（2026-10-08T13:41:53Z）。本轮读取的是 HuggingFace `XiaomiMiMo/MiMo-V2.6-Pro-RL` 仓库内的 **`MiMo_V2_6_technical_report.pdf`**（44 页，8 节 + 附录，表 1–7、图 1–17），并逐节对照 arXiv 摘要页与模型卡。配套：官方发布页（2026-09-22）、官方更新时间线、官方定价页、`config.json`（ModelScope 同步）。
> **主等级**：`[精读原文]`（技术报告 + 官方页面 + 模型卡 + config 原文）。
> **一句话定位**：V2.6 的价值不在「换架构」——Pro / Flash 的骨架与 V2.5 的两个成员逐项同构——而在**把 agentic RL 的三条缩放轴（训练算力、环境与 harness、grader）一次性放大**，并用「You Only RL Once」把 coding / general / visual / cyber 放进同一次混合训练，再用 MOPD2 把难验证领域接上。
> **亮点与差异四行**
> - **一句话亮点**：用**一次**混合 RL run 替代按域分开训练，靠环境、harness 与任务分布的混合让能力互相正迁移；官方把 6 天训练过程直播并开源了 7k+ 环境与蒸馏小模型，这是报告里最强的可复现证据。
> - **新在哪**：① 每步 **1,568 prompts × 16 rollouts = 25K 序列**、2.7–3.7B tokens 的大 batch RL；② **GRS / GAR** 两个 groupwise grader（把二值奖励变成质量排序）；③ **MOPD2** 的 prefix-conditioned OPD；④ RL 期间**冻结 MoE router** 以压住专家负载漂移。
> - **证据强度**：中强——有训练曲线、router 冻结消融、多 harness 迁移实验与开源 9B 模型的 11 项复现；但主表数字全部**厂商自报、单次 run、无第三方复跑**，harness 名称与 pass 次数未逐项披露。
> - **值不值得引用**：值得，但应引用「**RL 配方 + 开源环境 + 小模型复现**」这一层，而不是单个分数；引用分数必须同时带 harness / max effort / 单次 run 三个条件。

## 1. 问题设定：RSI 需要 agent，agentic RL 需要三件套

报告开篇（§1）把目标写得很直白：RSI 要的是「模型通过持续探索与反馈扩展能力」，而实现它需要 agent —— 模型 + 交互环境 —— 提供多步轨迹与反馈信号。于是「在复杂 agentic 任务上放大 RL」成为一条具体路径，但有两个硬约束：

1. **基座与探索空间**：RL 要有效，基座必须先在足够广的多模态语料上做过 mid-training，给 agent 留出探索空间；骨架还要撑得住长上下文与大规模 rollout。
2. **基础设施、环境与 grader**：真实工作流有异构工具与复杂状态，自动 grader 可能不完整、不一致、甚至可被利用；环境要能大规模并行、可重置、可复现。

V2.6 的选择不是换骨架，而是把这三件事同时做大：

- **算力**：单次 run 上千卡，Pro / Flash 的 RL 成本分别 **\$2.6M / \$0.9M**（报告 §4.1；发布页写 \$2.62M / \$0.85M，口径差异见 §12）。
- **环境**：代码、通用专业工作流、视觉产物、网络安全四类，配套 **7k+** 任务（§4.2、§7）。
- **grader**：把「二值测试通过」升级成**组内质量排序**（§4.3），并用 GRS / GAR 两种机制落地。

报告对「为什么现在做」的判断是：RL 已经从「单域可验证任务」走到「多域、长程、多 harness」的临界点，谁先把环境与 grader 工程化，谁就能把 RL 算力换成能力。这句话不是修辞——报告用近一半篇幅写环境构建、审计与基础设施（§4、§6），而不是模型结构。

**失效边界（先记）**：这套叙事成立的前提是「环境与 grader 可靠」。报告自己列了大量 reward hacking 案例（§4.2.6，表 2），说明这个前提在工程上是**持续维护**出来的，不是一次配置好的。

## 2. 架构：hybrid SWA 主干 + 全模态编码器 + MTP

### 2.1 文本主干（报告 §2.1，表 1）

- 主干由重复的 **hybrid block** 组成：每个 block 内 **N 层 SWA 后接 1 层 GA**；唯一的例外是**第一层**用全局注意力 + dense FFN，用来稳定早期表示。
- SWA 与 GA 的 FFN **都是稀疏 MoE，且没有共享专家**。
- 滑动窗口 **W = 128**。
- 另外接一个**基于 SWA + dense FFN 的 MTP**（多 token 预测）模块，用于训练与推理加速。

| 配置 | MiMo-V2.6-Flash | MiMo-V2.6-Pro |
|---|---|---|
| 层数（总 / SWA / GA） | 48 / 39 / 9 | 70 / 60 / 10 |
| 隐藏维度 | 4,096 | 6,144 |
| SWA 头（Q/KV） | 64 / 8 | 128 / 8 |
| GA 头（Q/KV） | 64 / 4 | 128 / 8 |
| 头维度（QK / V） | 192 / 128 | 192 / 128 |
| 专家（总 / 激活） | 256 / 8 | 384 / 8 |
| 总参 / 激活 | 310B / 15B | 1.02T / 42B |

> **口径**：表 1 明确「主干的层数不含 MTP 模块」；「总参」与 `config.json` 的 safetensors 汇总一致（Flash 310.76B、Pro 1.024T）。Flash 的模型卡写 309B，正文按技术报告取 310B（见 §12）。

### 2.2 视觉编码器（§2.2）

- MiMo-ViT 采用**混合注意力**：用带 sink 的 SWA 替代 MiMo-VL-7B 的固定不重叠窗口，让信息跨窗口流动；SWA 层在**行优先 / 列优先**的 token 序列化之间交替，兼顾两个空间轴；周期性插入 GA 层聚合全局。
- 训练方式很「偷懒但有效」：把 ViT 与一个**小的预训练 LLM** 配对，只在多模态理解数据上用交叉熵优化，**不做对比学习等辅助目标**；LLM 保持可训练，给 ViT 稳定梯度。
- 预训练语料 **>4T image tokens**。

**判断**：这解释了为什么 Pro 能在保持文本骨架的前提下接入视觉——编码器是「外挂 + 联合训练」，不是把 LLM 重训成原生多模态。代价是编码器的算力与显存要单独优化（§7 的多模态 payload 设计就是为它服务的）。

### 2.3 音频编码器（§2.3）

- **Audio Tokenizer**：log-mel → 两层卷积（帧率减半）→ 因果混合注意力 Transformer（SWA + GA 交替）→ 下采样卷积（帧率到 **25 Hz**）→ **20 层 RVQ**（每帧 20 个离散 token）；训练语料 **2000 万小时**。
- **Patch encoder**：每 **4 帧**音频 token 组成一个 patch，patch 内双向注意力，输出拼接后线性投影到主干；序列率从 **25 Hz → 6.25 Hz**。
- 参数量：Tokenizer 308M、patch encoder 127M（表 1，含输入 embedding、不含 projector）。

**判断**：6.25 Hz 的表示率是端侧/实时语音的关键；但报告没有给音频理解/生成的独立评测，V2.6 的音频能力在 §5 的 agent 评测里没有单列——这是引用时必须注意的缺口。

### 2.4 投机解码（§2.4）

- 采用 **DFlash 的 block diffusion** 设计：drafter 由 **5 层 Transformer**（dense FFN）组成，条件于主干 hidden 与一个干净 anchor token，**一次前向预测后续 7 个 token**，交由主干并行验证。
- drafter 全层 SWA（grouped queries），token 在 block 内双向、最多看 anchor 前 **1,024** 个主干位置。

### 2.5 与 V2.5 的架构关系（本报告补充）

对比 `MiMo-V2.5-Pro` / `MiMo-V2.6-Pro-RL` 与 `MiMo-V2.5` / `MiMo-V2.6-Flash-RL` 的 `config.json`：

- 层数、`hybrid_layer_pattern`、隐藏维度、专家数、top-k、头数与头维度、`max_position_embeddings` **逐项相同**；
- 差别在于 V2.6 的两个仓库都带 `vision_config` / `audio_config`，而 **V2.5-Pro 没有**（V2.5 标准版本身已是全模态）。

**结论**：V2.6 不是架构代际，而是**训练代际**；任何「V2.6 换了注意力/残差」的说法都与这份 config 不符。

## 3. 预训练与 mid-training：把探索空间先铺好

### 3.1 预训练（§3.1）

- 两阶段：先在**纯文本**上训练语言主干，再接入自研 ViT 与音频编码器，在**全模态数据**上联合训练。
- 上下文：从 **32K** 起步，中途扩到 **256K**。
- token 预算：
  - **Flash：48T**，文本 26T + 全模态 22T；
  - **Pro：30T**，文本 27T + 全模态 3T。
- 优化器：**AdamW**。

> 注意：Pro 的「3T 全模态」远小于 Flash 的 22T。报告没有解释这一差异，但结合后文（Pro 的强项是 agent/coding，Flash 要覆盖更广的多模态低成本场景）可以理解为**分工不同**；这只是一种解释，不是报告结论。

### 3.2 mid-training（§3.2）

mid-training 的任务是「把通用基座变成 agent 基座」，做三件事：

1. **数据**：以 agent 为中心的混合——coding / general / visual / research 的真实轨迹，加高质量文本、仓库级代码、图像/视频/音频。
2. **上下文**：先在 **256K** 上训练（占大部分算力），最后阶段扩到 **1M**。
3. **优化器**：从 AdamW 换成 **Muown**（Muon 的变体）。报告给的理由很具体：大 batch 的混合任务 RL 里，AdamW 的逐元素自适应在超过 critical batch size 后数据效率下降，而 Muon 的矩阵式正交化更新更省数据；Adam 部分 β1=β2=0.95、ε=1e-8。
4. **数值稳定**：为稳 MXFP4 训练，RL 启动时**继承 SFT 检查点的 FP32 master weights 与 Muown 行状态**。

**判断**：mid-training 是 V2.6 与 V2.5 之间最实质的「训练差异」之一，但报告只给了配方叙述，**没有给 mid-training 的消融**（去掉某类数据/某个阶段会掉多少），所以「mid-training 贡献了多少」无法从公开信息里拆出来。

## 4. 规模化 RL：三条轴

### 4.1 训练算力（§4.1）

- **单次 run**：上千卡；Pro **\$2.6M**、Flash **\$0.9M**。
- **batch**：1,568 prompts，group size **G=16**，每步 **25K 条序列**，合计 **2.7B–3.7B tokens**（每条 110K–150K tokens）。
- **Partial rollout**：rollout 与 grading 有长尾，收集训练 batch 时把在飞序列挂起、下一轮继续；代价是每次策略更新后要**重新 prefill** 重建 KV，所以「大 batch」与「partial rollout」必须一起调。
- **一致性**：用 R3 与 top-p 候选集回放保证训练/推理一致；动态采样过滤全对/全错组；Sample Mixer 维持多任务分布（§6.3）。
- **成本分解（Pro）**：rollout **43.8%**、training **43.5%**、grader **12.7%**。

**判断**：grader 占 12.7% 是一个值得记住的信号——「评分」不再是零成本附属品，而是 RL 预算的一等公民。这与 §4.3 把 grader 做成 agent 的设计一致。

### 4.2 环境与 harness（§4.2）

#### 4.2.1 代码任务

- **五条合成路径**：GitHub PR/issue、组织内真实开发请求、规格驱动、源码驱动（CodeMidas）、长程工程任务；再加公开数据与持牌数据商。
- **监督准确性**：对齐「任务规格」与「单元测试」的行为范围；用 **4 次 rollout + 审计 agent** 找出假阳性（测试不足）与假阴性（测试过严）。
- **监督稳健性**：F2P / P2P 测试在打补丁前后必须按规定失败/通过，并要求 **8 次重跑**稳定，筛掉 flaky 测试。
- **reward hacking 审计**：复用 rollout 轨迹检查提交补丁与对话日志，找捷径。

#### 4.2.2 通用 agent

- 真实文件 + 自动生成**本地软件 mock**（复现操作、状态变化、输出格式、错误响应）；所有状态本地化、沙箱可重置，避免网络波动。
- 任务 = 可验证的工作流；评分用**迭代细化的 rubric**（点式 + 组内比较）。

#### 4.2.3 视觉 agent

- 两类：**开放式设计**（审美，难用固定规则）与**高保真复刻**（像素级相似 + LLM 整体判断）。
- 开放式先用点式 rubric 稳定（运行正确性、指令遵循、布局完整性、基础审美），再引入**组内比较**奖励相对进步。

#### 4.2.4 网络安全

- 任务：给定项目与目标 bug，构造能触发它的输入（PoC）。
- **verifier 的关键设计**：不用「修好的二进制不崩」这类差分测试（不完整补丁会误判），也不用 LLM 判分（跨 run 不稳定）；而是从 ground-truth sanitizer（ASan/MSan/UBSan）报告里抽两个属性——**漏洞类型**与**崩溃位置（最顶层项目栈帧）**，PoC 的崩溃必须同时匹配。任务描述也来自同一份报告，做到「描述与验证同源」。
- 环境：给出完整源码 + 编译好的 harness 二进制（CyberGym 不给二进制，限制为纯源码分析）。

#### 4.2.5 多 harness

- 不用生产 harness（工程护栏多、模块耦合、信用分配难），而是从**同一最小 agent loop**（system prompt / tools / context management）派生 **mini-harness**，按 Code / General / Visual / Cyber 配置，模块可自由重组。
- 目的：把「harness 多样性」当作与任务、环境并列的训练维度，提升对**未见 harness** 的泛化。

#### 4.2.6 reward hacking 防御

- 典型漏洞：从新版本包、上游源码、GitHub 讨论里「抄答案」（表 2 给了 5 个仓库的实例）。
- 防御组合：**mid-training 对齐数据**（让模型反思错误推理并改正）+ **环境清理**（删构建日志/verifier 输出/残留补丁/缓存，保留 base commit 之前的 Git 历史，容器级网络隔离）+ **hack agent**（专门找剩余漏洞，报告称发现了清理流程没覆盖的新路径）+ **训练中审计**（GRS/GAR 的 grader 可把确认作弊的轨迹奖励清零）。

### 4.3 grader：GRS 与 GAR（§4.3）

**GRS（离线 rubric）**：对高通过率任务，先收集多条离线 rollout，让 agent 对照任务与仓库，产出两组标准——**solution rubric**（实现质量：需求满足、边界情况、与代码库一致）与 **behavior rubric**（解题行为：取证、验证改动效果）；训练时逐条 rollout 打分，最终奖励

`R_i = R_i^test · S_i^sol · S_i^beh`（式 2）。

乘法形式保证「没过测试就没有奖励」，同时在「全组都通过」时仍能靠质量分提供梯度。

**GAR（在线排序）**：对混合结果组，把组内所有轨迹放进共享工作区，由 SFT 训练的 agentic grader 对比成功/失败，并按五个维度排序：方案适配性、实现精确度（无遗漏/无多余 fallback）、最小改动、无副作用、与代码库风格一致；确认依赖外部/泄露答案的轨迹**奖励清零**并按失败处理。然后用质量因子 f_i 把正 advantage 从低质量通过解**再分配**给高质量通过解（式 3）。

**判断**：GRS/GAR 是 V2.6 相对「二值奖励 RL」最实质的算法贡献——它把「通过」与「通过得好」拆开，且乘法形式避免了「质量分替代测试」的退化。但它们都依赖 grader agent 的判断，**grader 本身也会被 reward hacking**；报告用「行为正则 + 审计」缓解，没有给出 grader 与人类评分的一致性数据。

## 5. 评测：把条件写在数字旁边

### 5.1 设置（§5.2）

- 四个类别：**code agent / cybersecurity / general agent / visual agent**；公开基准 + 三个内部基准（MiMo Code Bench、MiMo Cyber Bench、MiMo Visual Coding）。
- baseline：所有可配置 reasoning effort 的模型都在**最高档（max）**评测。
- 报告**没有**逐项给出 harness、pass 次数、采样温度；因此表 3 只能当「厂商自报的单一 run」看。

## 6. 稳定性：router 冻结与失败分析

### 6.1 冻结 MoE router（§5.4）

- 现象：router 可训练时，第 9 层专家负载在 20 步内急剧失衡——CV **0.78 → 2.0**、峰值负载 **6× → 16×**、冷专家占比 **0.5% → 22%**。
- 诊断：把第 20 步的 router 参数恢复为 RL 前初值（其余参数不动），负载均衡恢复、benchmark 不变 → 失衡由 **router drift** 驱动，而非专家权重退化。
- 处理：RL 全程**冻结 router**；冻结后 CV≈0.7、峰值≈5.5×、冷专家≈1%，benchmark 正常上升。

**判断**：这是报告里最「可复用」的一条工程结论——MoE 模型做长程 RL 时，router 的自由度可能带来负载崩溃；冻结是便宜的稳定化手段。代价是 router 不再适配 RL 分布，长期是否有损**未做消融**。

### 6.2 失败分类（§5.5）

- 基础设施：GPU 显存 double-bit error（DBE）；Flash 在 Cyber 任务集群遇 Kubernetes 故障（第 15–16 步）；Pro 在第 14 步后 grader 网络不可达。
- Rollout：partial rollout 下短轨迹先完成，biased length estimate 打爆 GPU 与 pinned host-memory 的 KV 池；某个 harness 的 rollout 长度不到其他 harness 的一半，重启后第 2–3 步估计被带偏。
- 训练：micro-batch 内 MoE 失衡，某个 EP rank 收到 **>30×** 平均 token 负载 → GPU OOM；Flash 后期序列变长导致 packing 的 CPU OOM（driver failure）。

**判断**：「6 天跑完」是**恢复后的墙钟时间**，不是无故障时长；报告没有披露总恢复时间与有效算力利用率，因此不能用它推算「RL 成本」以外的效率指标。

## 7. 基础设施：把「大 batch + 多 harness + 多模态」拆成控制面与数据面

### 7.1 Harness Pool 与 Payload Porter（§6.2）

- **多租户 rollout**：不为每个 harness 实例/Agent Loop 起独立 Ray actor（会耗尽 GCS 节点的 fd），而是固定大小的**持久 host actor 池**，每个 host 承载多个 tenant；tenant 各自保存轨迹状态，按在飞实例数均衡。阻塞操作（环境操作、tokenization）放后台线程，避免一个阻塞调用卡住整个事件循环。
- **异构 harness**：不同数据源可用不同代码库；一个进程只能 import 一个代码库，所以不同代码库分池；池的 host 预算在启动时固定，与每步调度的数据混合解耦。
- **控制面/数据面分离**：每条序列结束时，payload（token id、log-prob、MoE routing、top-p 候选、多模态数据）写入分布式 KV；driver 只调度轻量 metadata（标量奖励、长度、payload key）。组完成时只读需要的列；groupwise grader 完全异步跑；采样器只按 metadata 接受/拒绝；advantage 写回 store。打包时每个 TP 组一个 packer，只取 CP 窗口覆盖的行。
- **多模态**：Agent Loop 只发**请求间的多模态增量**；训练时图像先数据并行编码，再把 embedding 重分布到持有对应 token 的 rank；payload 留在 KV，按 metadata 负载均衡。

### 7.2 Sample Mixer（§6.3）

- 25 个数据源的**平均生成长度差 90×、活跃 rollout 时长差 66×**（图 15）。
- 四个机制：自适应 rollout 并发（按 t_i·m_i 分配预算，式 6）、自适应调度（目标项 + 缺口项，式 7）、预测式 rollout 分发、样本回放（覆盖启动与恢复）。
- 目标：在异步、partial rollout、动态过滤下，仍让每个数据源按指定比例进入训练 batch。

**判断**：这一节是「为什么大 batch RL 难」的实证——难的不是梯度，而是**调度与数据搬运**。报告的可复现性证据也主要落在这里（开源框架 + mini-harness），而不是集群本身。

## 9. 七问对账：这份报告讲明白了什么，没讲什么

**讲明白了**：

1. **问题**：agentic RL 的瓶颈是环境/grader/基础设施，不是梯度算法本身（§4.1–4.3、§6）。
2. **方法**：混合 RL + 多 harness + groupwise grading + MOPD2 的组合，以及每步 batch 的真实量级（§4、§5.6）。
3. **数据与规模**：预训练 token、RL token/步、成本分解、专家负载数据都给到了（§3、§4.1、§5.4）。
4. **结果与条件**：主表逐项给出，baseline 的 max effort 说清楚了；DeepSWE 的训练轨迹也给了（§5.2–5.3）。
5. **消融**：router 冻结、多 harness、GRS/GAR 的机制与收益有实验（§4.3、§5.3–5.4）。
6. **失效**：失败分类与 reward hacking 案例写得比多数技术报告细（§4.2.6、§5.5）。
7. **差异**：与 V2.5 的差别可由 config + 训练章节判定（本分册 §2.5）。

**没讲明白（引用时必须自己标注）**：

1. **没有方差**：所有主表是单次 run；没有多 seed / 置信区间。
2. **没有 harness 细节**：表 3 的 harness、pass 次数、温度、上下文截断策略未逐项披露。
3. **没有逐轴消融**：训练算力、环境数、grader 算力三条轴各自贡献多少，没有拆解实验。
4. **没有 1M 端到端评测**：mid-training 扩到 1M，但 §5 的评测没有 1M 长上下文基准。
5. **没有 mid-training 消融**：数据混合、阶段划分的贡献未量化。
6. **没有 grader 与人类一致性**：GRS/GAR 的质量分是否与人工判断一致，未报告。
7. **没有开源训练数据**：权重与 RL 环境开源，预训练/mid-training 数据未开源。

**一条总判断**：V2.6 的「新」在 RL 系统与开放资源，不在模型结构；把它当「架构论文」读会失望，把它当「大规模 agentic RL 的工程报告」读则信息密度很高。

## 10. 什么条件下失效（独立失效边界段）

1. **引用分数**：任何单点分数都必须带「厂商自报 / 单次 run / baseline max effort / harness 未披露」；不能把不同表的数字直接横比。
2. **跨厂商比较**：外部对照列来自报告原表，不是本报告复测；闭源模型（Opus 5、GPT-5.6 Sol、Fable 5）的版本与评测设置可能随时间变化，**不适合做长期结论**。
3. **长上下文**：1M 是训练/配置事实，不等于「1M 端到端任务已验证」；报告没有给 1M 检索/长程 agent 的专项评测。
4. **环境与 reward hacking**：报告的防御是「清理 + hack agent + 审计」的持续对抗；换到新仓库/新工具链，泄漏路径会变，防御不一定可迁移。
5. **复现**：千卡级集群、\$2.6M RL 成本、厂商私有数据与 grader 服务，外部团队无法完整复现；**可复现的是配方与 9B 小模型实验**（§8），不是旗舰结果。
6. **小模型外推**：Distill-9B 的 11 项提升说明「这套 RL 对 9B 有效」，不能证明「对 1.02T 的每一项都同样有效」；两者数据、算力、环境规模不同。
7. **MOPD2**：依赖分域 teacher；难验证领域的 teacher 质量决定上限，报告没有给 teacher 消融。
8. **许可与数据**：权重 MIT、RL 环境开源，但预训练数据不在开源范围；「开源」在这里指**权重 + RL 资源**，不是全栈可复现。
