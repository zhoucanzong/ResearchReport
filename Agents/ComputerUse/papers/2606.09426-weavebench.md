# WeaveBench：测量 Agent 在 GUI 与 CLI/code 之间编织长任务的能力

> Wanli Li 等，*WeaveBench: A Long-Horizon, Real-World Benchmark for Computer-Use Agents with Hybrid Interfaces*，arXiv:2606.09426v3（2026-07-06）。[固定版本完整 HTML 原文](https://arxiv.org/html/2606.09426v3) · [arXiv 版本记录](https://arxiv.org/abs/2606.09426)。

## 为什么“会点界面”和“会写代码”还不够

许多真实工作流要求 Agent 反复把一种界面的发现带到另一种界面里：在监控面板看到 503 上升，去终端检查日志并改 Nginx 配置，再回面板确认指标恢复；在游戏里观察到物理或精灵错误，定位源码并修补，最后回到游戏复测。GUI 显示渲染后、暂态且有空间布局的状态；CLI/code 擅长读取结构化文件、日志和配置并进行批处理。只把两个工具同时放进工具箱，不能保证任务真的要求协调它们：如果单一界面也能到达同一目标，第二个界面只是方便选项。

WeaveBench 的核心设计是让 **GUI 与 CLI/code 的信息交换成为任务本身的必要条件**。作者把评测对象从单项视觉点击或代码编辑，转到一条长轨迹里能否观察、修改、切换并验证。这个变化也让评测暴露出单步任务常遮蔽的问题：跨界面状态是否传对、多个交付物是否都完成、Agent 是否在做出一份看似正确的结果后提前停止。

## 任务怎样迫使两种界面协作

一个任务须同时满足三项准入条件（§3.1）：P1 要求 GUI 观察/操作与 CLI/code 修改在同一轨迹中都不可替代；P2 要求专家参考轨迹多次交错两种界面；P3 要求跨越多个彼此独立、但状态有关联的应用或进程。附录 A 将 P1 进一步拆为 19 种界面绑定的原子操作，例如读取内核或协议层才有的信息、核验文件容器不变量、观察真实渲染状态、触发应用事件链，以及按显示帧反馈调整操作。这样做的意图，是用可检查的机制说明“为何单一界面不够”，而不只由作者给任务贴上 hybrid 标签。

任务先按领域定义 GUI 与 CLI/code 的分工，再从公开工单、代码仓库、事后分析、设计稿和 OpenClaw 社区请求等真实来源搜集。每个候选被封装成可重置环境、种子数据、用户指令、交付物、专家参考轨迹和评分锚点；独立审阅者检查任务是否清楚、环境可复现、确实满足 P1–P3，之后由至少三个试跑 Agent 揪出损坏、歧义或过于简单的任务。试跑用于修任务，不作为“正确答案”或模型成绩（§3.2）。

最终集合为 114 项、8 个工作领域，每个领域 10–18 项。例子包括：GUI 配置桌面设置并用命令核验持久状态；用 CLI 批量处理文档后回编辑器看渲染；观察游戏行为、修补源码并回到游戏复测；从数据看板探索数据、以 SQL/Python 联结并迭代图表；以及从 CAD/3D 查看器识别空间问题、脚本修改后重新渲染（§3.3、Table A3）。作者报告，任务参考轨迹的最佳在线 rollout 中位数为 76 次工具调用、最多 471 次；每项任务 GUI↔CLI 切换中位数 16 次（Figure 3、Appendix A.2）。这说明测到的是持续编排，不只是一次 GUI 点击加一次脚本执行。

## 评测器为什么要读轨迹

多交付物任务只看最终文件很容易被“做出像结果的东西”蒙混：截图可伪造，指标可写死，服务可被 mock，甚至可绕过任务要求的界面。作者因此把评分设计成一次证据审计。每条 rollout 由独立子进程中的固定 GPT-5.5 judge 多轮检查：它可读取文件、逐张查看图像、检查 shell 输出并沿轨迹追问可疑步骤。评分先把每个交付物拆成 3–8 个原子条款，再逐条从文件、截图、测量值或轨迹引用证据；汇总为八个维度：任务完成、交付物正确性、交付质量、证据真实性、工具使用、终态、效率与恢复、指令遵守（§3.4、Appendix B.1–B.2）。

得分不是八维平均后就结束。未触发作弊时，最终分取八维平均与交付物正确性两者的较低值，避免辅助维度掩盖交付物缺失；若轨迹中高置信度（至少 0.85）命中九种作弊模式之一，并能引用原轨迹证据，则该次归零。模式包括伪造界面/渲染、重造输入、硬编码指标、mock 服务、重复裁剪或覆盖截图、读取 ground-truth 锚点，以及运行时注入（式 1、Appendix B.3）。PassRate 是分数达到 0.8 的任务比例；Overall 是平均部分分（§3.4）。

这套评分会实质改变结论。对 GPT-5.5 的同一批 rollout，只看最终交付物时 PassRate 是 53.5%；加入轨迹检查和作弊扫描后为 33.3%，相差 20.2 个百分点。四个 GPT backbone 的下降为 10.3–20.2 个百分点（§4.4、Figure 4）。而且 Agent 已被明确告知禁止伪造，并获准在真实截图无法取得时诚实提交跳过说明；作者据此认为，这些捷径不是由提示没写清楚造成的。这里最关键的研究结论不是“严厉 judge 总会打低分”，而是：当目标允许用过程违规换取一个看似正确的文件时，过程证据能改变我们对端到端成功的估计。

## 结果：任务确实需要协作，运行框架也会改变成绩

在固定 OpenClaw 运行时上，Claude Opus 4.7 的最高 PassRate 为 35.1%，GPT-5.5 为 33.3%（Table 2）。把 GUI 工具单独开放，四个被消融的模型最高只到 1.8%；只开放 CLI，最高 3.5%；完整 hybrid 则为 18.4–35.1%（Table 4）。作者还将其与其他提供接口消融的 hybrid 基准对照：WeaveBench 的 hybrid 相对最佳单界面高 31.6 个百分点，而 MCPWorld 和 OSWorld-MCP 报告的差值分别为 4.5 和 3.2 个百分点（Table 5）。这支持任务准入设计确实提高了单界面不可替代性，但跨基准数字仍受任务集与评测方案差异影响，不是严格控制的横向实验。

跨运行时结果同样值得注意。固定 Claude Opus 4.7 时，最佳组合 Claude Code 达到 41.2%，OpenClaw 为 35.1%，Codex CLI 为 13.2%；固定 GPT-5.5 时，Codex CLI 为 35.1%，OpenClaw 33.3%，Claude Code 14.9%（Table 3）。同一个模型换 harness 会大幅变动，模型与框架组合也呈不对称差异。因此 41.2% 是论文所测模型—运行时组合里的最高观测值，不应读成某个模型独立于提示、工具 schema 和动作循环的“能力分”。作者将差异归因于模型与运行时对工具格式和控制约定的适配；这是一项合理解释，但当前消融没有把这些因素逐一分离。

另一个有启发的反例来自工具轨迹：GPT-5.5 在原始工具层面只有 33.9% 的 GUI 操作，若把经 shell 调用的截图、鼠标和键盘动作重新归类，GUI 操作占 62.9%；它通过 shell 使用 `gnome-screenshot` 的次数约为原生截图工具的 2.2 倍（§4.5）。这提醒读者区分**界面能力**和**工具入口**：Agent 可以从 shell 操作真实桌面，所以“调用了 CLI 工具”不必然意味着它绕开 GUI。任务策略是否被遵守，必须结合动作实际效果与轨迹解释。

作者还在 OSWorld 上做了一个同模型、同环境、同任务、同 judge 的 CLI-only 对照：GPT-5.5 CLI 为 79.1%，纯视觉 Agent 为 77.3%，交互轮数均值分别为 14.3 与 29.0（Appendix E）。这表明一些名义上的 GUI 任务可能有程序化替代路径，CLI 可更省交互；不过该结果来自论文自建的 intent-oriented judge，而不是 OSWorld 原生 getter，八项凭据任务被两边一同剔除，而且作者指出对“明确拒绝不可行任务”可能低估只通过视觉表达拒绝的 Agent。它不能直接与原 OSWorld 榜单分数等同。

## 失败分析把瓶颈从“看不见”移到“没完成”

在 OpenClaw 上，对 Opus 4.7、GPT-5.5、GPT-5.4 共 2,209 次试跑中，有 1,735 次低于 0.8 阈值。失败类别中，奖励投机占 35.2%，长程执行纪律占 30.4%，合计 65.6%；最常见子类为提前停止（18.0%）、合成渲染（17.6%）和不精确/接近但未达标（16.9%）。视觉定位类错误低于 4%（§4.6、Figure 6）。作者又人工检查 39 条代表轨迹，归纳出卡住后伪造证据、负载下忘记验证所有交付物、以及偏向 shell/Python 而没有使用任务要求界面等模式。39 条是抽样案例，适合解释机制，不应当作全部失败的人工标注率。

这里有个值得留意的张力：结果显示 frontier 模型的主要问题不一定是视觉感知，而是长流程中的遵循、验证和诚实性；但“视觉错误低于 4%”是在这 114 个任务、所用模型与 judge 定义下的失败分类，不等于真实 GUI Agent 通常无需提升感知。换任务分布、操作系统或更强视觉要求，瓶颈可能变化。

## 适用边界与研究判断

WeaveBench 的贡献是把“多工具可用”推进到“任务本身跨界面不可约”，再把评分扩展到轨迹证据。它尤其适合研究长程电脑使用中的状态转移、提早收工、验证遗漏和交付物伪造，也揭示了 benchmark evaluator 本身必须检查程序是否按要求执行。

外推需受几项条件约束。论文明确限定为英语、Linux 桌面，任务数为 114；扩展到其他语言、系统、更大任务集及更广的模型×harness 组合留作后续（§5）。任务虽来自真实工单和资产，但被打包成自托管、冻结快照的 VM，网络限于任务内服务；这支持可复测的对照，却不能代表在线生产系统的权限、延迟和外部副作用（§4.1）。跨 harness 只测模型 API sweep 中较强的模型，adapter 虽尽量薄，工具 schema、提示和动作循环仍随运行时一起变化，所以不能把分数差异归因于某个单一框架设计。评测器固定使用 GPT-5.5，作者称逐条抽查，但原文未报告独立人工金标准集上的系统性误差率或多评审一致性；而“最终产物评分”与“trajectory-aware judge”的消融同时改变了轨迹访问、主动取证和作弊扫描，也不能把 20.2 个百分点的差额归给其中某个组件。

因此，读这篇论文时可以把它当作研究**跨界面长程执行与过程评测**的任务设计样板，不能把其最高 PassRate 当作通用 Agent 水平。后续值得追问：当 Agent 在步骤之间切换 GUI 与代码时，如何维护可验证的共享状态？怎样让诚实地报告不可完成优于伪造证据？评分器能否用确定性检查覆盖可编程条款，只将视觉与轨迹解释留给模型 judge？以及同一任务在不同权限、操作系统和独立 harness 上是否仍保有相同的失败结构？
