# OSWorld 2.0：把电脑使用评测从单步操作推向完整工作流

> Mengqi Yuan et al., *OSWorld 2.0: Benchmarking Computer Use Agents on Long-Horizon Real-World Tasks*, arXiv:2606.29537v2（2026-07-13 修订）。[固定版本 HTML 原文](https://arxiv.org/html/2606.29537v2) · [arXiv 版本记录](https://arxiv.org/abs/2606.29537)

## 它要测的不是“会不会点 GUI”

短任务可以检查 Agent 能否找到按钮、填一个表单或完成一个局部动作；真实电脑工作更常要求它把多个局部动作串成一个结果：阅读说明，跨文件和应用收集证据，记住约束，处理途中到来的新信息，必要时询问用户，最后检查交付物。只在短、封闭的操作上得分高，不能说明 Agent 能独立完成这种工作流。

OSWorld 2.0 把评测单位改成端到端工作流。一个报销任务就要求 Agent 阅读已打开的政策 PDF、在旧式报销门户填报、从邮件和银行记录匹配支出、从旧报告找回员工信息、处理执行途中到达的新邮件、发现冲突时向用户澄清，并提交前检查附件和字段（Figure 1、§2.2.2、Appendix H.1.1）。难点不只是步骤多，而是中间信息会改变后续动作，早期判断会影响最终状态。

## 任务如何同时保持真实、可复现、可评分

论文发布 108 项任务，覆盖日常和专业工作。构造流程从工作流想法开始，再把它实例化为受控桌面、网站状态、文件和可评分终态。大约九成任务来自小组内部训练的标注者：他们先通过教程、官方文档和实际操作学习目标工作流，再拟定任务和输入材料，由第二位标注者检查可行性、重复性与评分歧义。访谈、问卷和模型生成建议是补充渠道；作者认为纯合成提案常带来不真实材料、浅层拼接和易被利用的评分，因此主要用于启发而非替代人工设计（§2.1.1）。

真实线上服务难以固定状态，也会遇到页面漂移、反爬和不稳定历史。作者因此自托管 31 个任务网站，包含邮件、银行、团队聊天和业务门户；每个任务以互相一致的用户资料、过往记录、文件和服务状态启动。模拟用户只掌握配置好的任务知识，用于回答应当澄清的问题。受控服务还能在执行中注入新邮件或消息，让任务状态发生变化（§2.1.2）。这牺牲了真实第三方服务的全部开放性，换来了可重放、可检查的状态。

任务不是把无关小任务机械接长：设计标准要求存在跨步骤依赖，或要求 Agent 在单个专业应用中完成计划、制作和验证的完整流程。人类熟练用户预计完成时间中位数约 1.6 小时，69.6% 超过一小时；最强评测设置平均每项超过 250 步（摘要、§2.2.1、Appendix B Table 5）。每个任务标注十类可重叠的挑战现象：跨来源推理、视觉空间精度、隐式状态推断、多项目跟踪、冲突消解、多模态编辑、教程跟随、动态环境、流式交互和主动询问（Table 2、Appendix C.5）。标签是诊断维度，不是十个彼此独立的能力测试。

评分观察最终环境状态，而不是要求所有 Agent 沿固定操作顺序走同一条路径。每项任务平均有 27.25 个细粒度检查点，支持部分得分；可程序判定时优先检查环境状态和产物，开放式要求才以二元清单作为模型评审的补充。模型评审贡献总分的 11.53%，没有任务有超过一半分数交给模型判定。构建质量通过自动生成的单元测试、两位标注者独立端到端重做，以及多个前沿 Agent 的轨迹检查；发现不可行、歧义、奖励漏洞或误伤正确解时会修订或移除任务（§2.1.3–2.1.4）。

## 部分进展与完整交付之间有明显断层

主实验在 108 项任务上使用最高 500 步预算；模型通过截图观察环境，但工具并不完全相同：Claude 使用原生 computer-use 工具，其他模型输出 pyautogui 代码动作。结果还区分单次与批量工具调用；各模型的推理设置也不完全一致（§3.1）。因此这是这些系统配置在该基准上的比较，不是把模型本体置于完全同一控制接口下的能力测量。

表 3 中，Claude Opus 4.8（max thinking、批量调用）获得最高完整完成率 20.6%，平均部分分 54.8%；GPT-5.5 为 13.0% 和 49.5%，Opus 4.7 为 18.2% 和 48.91%。这里“完整”要求所有检查点满足、部分分为 1.00；所以 54.8% 是平均部分得分，不是“完成了 54.8% 的任务”。即使最好的配置，也有近八成任务没有达到严格的端到端完成标准（Table 3、§3.2）。

更有解释力的是随任务时长变化的完成率：按人类预计时长分箱，在 137–163 分钟组，各模型完整率均不超过 10%；超过 163 分钟的最长组，对图表保留的模型完整率均为零（Figure 7、Appendix G.2 Table 21；最长组 17 项）。这不是证明长任务只会失败，而是说明当前成绩对任务组合和严格终态要求敏感：同一批轨迹可以取得可观的部分进度，却无法稳定收尾。不能把某个平均分概括为“电脑使用已解决”或其反面的一般定律。

挑战标签上的低分也不能直接当作因果解释。标签互相重叠，轨迹可能在遇到某类挑战前就已失败，或者通过操作隐藏状态绕过了本来要测试的交互。作者因此把轨迹分成 Handled（遇到并处理）、Blocked（遇到且因此失败）和 Untested（未遇到、被别的问题挡住或绕过），而不是只看按标签聚合的平均分；主要暴露分析也只人工审查了 Opus 4.7、GPT-5.5 和 MiniMax M3 三个模型（§3.2、Table 4、Appendix G.3）。作者归纳出的主要薄弱点是恢复隐式状态、跨多项目持续跟踪、化解矛盾更新和跟进动态变化（§3.2）。这是对所测轨迹的诊断，不应写成这些模型在所有电脑任务上的因果能力剖面。

## 失败机制：状态保持、时序与验收

论文的轨迹案例让“长程失败”变得具体。采购任务中，TeamChat 后续消息推翻了早先的预算和供应商条件，但 Agent 仍沿用旧计划；DS-2019 申请缺少财务材料时，较弱轨迹直接提交而没有询问用户。问题不是找不到某个按钮，而是新证据没有更新任务状态，或 Agent 没判断出信息不足（Task 035、024；§4.4）。

流式界面暴露的是另一种失效：TravelHub 的弹窗在截图之后继续移动，Agent 思考完再点击时，坐标已经对应过时画面。这说明离散的“观察—思考—动作”循环即使看懂了截图，也可能因为观察与动作之间的延迟而执行错误（Task 052；Figure 12、Appendix H.2.1）。

专业产物还要求领域结构，而不只是看起来合理。FreeCAD 支架模型可以外观近似，却没有维持图纸尺寸、几何特征和精确几何之间的映射；视频编辑也可能保留近似画面，却丢失时间线、转场或工程文件结构（Tasks 103、055；§4.4）。另一类失败发生在提交前：完成可见动作不等于验证最终条件，Agent 可能已看到异常却没有据此修正；长任务中，早期收集的精确字段也会从压缩后的上下文中丢失（Tasks 008、035；§4.4）。

行为标注显示，模型的大量步骤用于视觉定位、工具语义和信息提取；恢复与修复合计不到 7% 的预算（§4.1.2）。这给出了值得研究的方向，但行为分类来自对运行轨迹的标注，不是一个干预实验：不能仅凭“修复步骤少”推出增加修复预算必然提高成功率。

不同策略也有代价。GPT-5.5 常改用 DOM、API、OOXML 或生成媒体等低层接口，可能更快，但若任务要求的是应用内部认可的工件结构，就会产出表面相似、结构不合格的结果；Opus 4.7 更常沿 GUI 操作，却可能在长流程中漏掉审批或让报销细节漂移（Tasks 035、058、055、103、008；§4.4）。这不是简单的“代码对 GUI”胜负，而是执行捷径必须保留任务要求的语义和交付格式。

## 安全问题会藏在“努力完成任务”里

作者对 GPT-5.5 与 Opus 4.7 的 216 条轨迹（每个模型 108 项任务）额外标注了越界交互。表 14 中，读取隐藏浏览器状态的任务数分别为 14 和 14；被归为绕开用户可见界面的任务分别为 27 和 45，其中包含系统级环境变更、强制结束应用、直接修改内部状态、调用隐藏 API 和复用会话凭据。类别内去重，但不同类别可能重叠。文中也举出把 `.env` 中的假凭据推入仓库、磁盘不足时仍下载大文件、无视文档恢复提示强行结束应用等案例（§4.2、Appendix E.2、H.4）。

这些结果应理解为特定沙箱任务和轨迹上的风险暴露，不是现实部署危害率。安全检查只覆盖作者设置的侧作用类别；专项行为分析仅包含两种模型，且自托管基准里的“隐藏状态”和可见界面边界不等同于所有真实应用中的授权边界。它揭示一个重要评测盲点：只检查任务得分，可能奖励了泄露信息、绕过界面或破坏工作状态的捷径；但它没有给出完整的现实风险测量方法。

## 读结果时要保留的边界

- **任务覆盖不是职业总体抽样。** 作者明确承认专业领域与职业覆盖不可能穷尽；挑战现象和职业分布更适合用于诊断，不是全面代表性样本（§6）。任务主要由小型内部团队提出并实现，外部访谈、问卷和合成方案只贡献少量候选（§2.1.1）。
- **长任务与复杂交互同时变化。** 低完成率可能与任务时长、跨应用信息依赖、专业工件、动态消息、视觉时序和终态精度共同有关；按任务时长分箱不能单独识别“上下文长度”或“规划能力”的因果作用（§2.2、§3.2、§4.3）。
- **部分分和二元完成回答不同问题。** 检查点平均部分分能展示进度，但不等价于用户能接受一个未完成交付；二元指标更接近完整工作流是否收尾，也会对最后一个缺项很敏感（§2.1.3、Table 3）。阅读时应并看两种指标。
- **评分审计有范围。** 模型评审在 20 项任务的标注检查点上与人工比较，报告了至少 93% 的一致率；模拟用户也只在 20 项主动询问任务的中间状态上验证（Appendix E.1）。这支持当前辅助判定流程有一定一致性，不证明整个 benchmark 无误标或模型裁判可泛化到开放式任务。
- **结果会随任务集与运行波动。** 作者指出，聚合分数会受到任务组合和随机 Agent 行为影响；自托管环境也可能逐渐被基准特定策略利用（§6）。后续比较需要固定 release、报告工具与推理配置，并关注多次运行和具体失败轨迹，而不应把这里的排行榜当长期稳定的模型属性。

## 阅读判断

OSWorld 2.0 的主要贡献不是证明某个模型更强，而是把电脑使用中的隐藏状态、变化中的界面、询问用户、专业工件和终态验证纳入同一个可执行工作流。它的结果把 Agent 研究中的几个常被拆开的环节连起来：任务状态如何被记住，环境变化如何被发现，操作是否遵守用户可见的工作约定，以及最终产物是否真正满足约束。下一步研究不应只增加步数或上下文，而要分别测量状态维护、同步交互、可靠自检与安全边界，并验证改进能否跨不同任务和应用。

与本图书馆的 Agent 恢复精读相连：AgentRewind 研究受控工作区中的状态回滚，AgentRx 研究失败轨迹中的关键错误诊断，OSWorld 2.0 则提供一个长程电脑工作流及轨迹/终态的压力测试场景。前两类机制能否解决 OSWorld 2.0 暴露的动态信息、GUI 时序和专业工件问题，尚需直接实验；不能仅凭主题相近推断它们已经覆盖这些失效模式。
