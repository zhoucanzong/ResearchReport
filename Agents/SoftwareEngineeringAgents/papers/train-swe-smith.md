# SWE-smith：先造可执行的仓库任务，再扩展训练轨迹

来源：Yang et al., [*SWE-smith: Scaling Data for Software Engineering Agents*](https://arxiv.org/html/2504.21798v1)，固定版本 v1（2025-04-30）。重点阅读 §2、§3、§4.1、Appendix B–F，尤其 bug generation 与 issue statement 对照。

## 问题：真实仓库问题有价值，但难以大量配套成可运行环境

真实 issue + PR 让软件任务贴近开发者工作，却常缺少可靠复现步骤、单元测试或可复用容器；人工维护依赖和安装环境又昂贵。SWE-smith 倒过收集顺序：先挑选能够安装、主要测试能运行的 GitHub 代码库，再在这些代码库中合成“会让已有测试失败”的 bug 任务，最后自动生成 issue 描述。它因此可以把一个仓库扩展成多个训练环境实例。[§2](https://arxiv.org/html/2504.21798v1)

## 任务合成有几种来源，不同来源的真实性和偏差不同

论文包含四种 bug 候选构造：

1. **LM Modify**：把函数交给模型，让它产生有错误的改写。
2. **LM Rewrite**：只给函数头和 docstring，让模型重写实现；是否真的制造了可观察 bug 需由测试验证。
3. **Procedural Modification**：变换 AST，例如删分支、改操作符等；自动、可控，但模式受预设变换限制。
4. **Patch Combination / PR Mirror**：合并多个候选 bug，或反转已有 PR；更接近多处修改与真实软件演进，但构造与环境验证更复杂。

共同过滤器是执行原测试：候选变更若没有导致测试失败，就不算有效 bug instance；修复轨迹则要让 fail-to-pass 测试恢复通过。这样系统能大规模扩出任务，但“bug 是否有效”被操作化成测试是否触发，未触发的语义错误、隐式行为契约或性能回归可能不会进入数据。[§2.1–§2.2、Appendix B](https://arxiv.org/html/2504.21798v1)

## 从合成任务到训练样本，中间还有教师策略

SWE-smith 用 Agent scaffold 在 bug task 上采集修复轨迹，再筛出测试通过的成功轨迹，供学生模型做监督微调。也就是说，“50K task instances”不是“50K 高质量训练轨迹”：任务要能安装、触发测试失败，教师还要能修复并通过验收。数据管线能提高样本供给，任务难度、教师能力和 pass filter 又共同决定最终留下什么样的经验。[§3、§4](https://arxiv.org/html/2504.21798v1)

论文结果支持两个具体观察：在其代码仓库、专家 Agent 和 Qwen Coder 学生模型的训练设置下，数据规模/仓库覆盖扩展与学生效果相关；同等样本数下，PR Mirror、Procedural 和 LM Rewrite 生成策略所得到的成功轨迹效果不同。它不能证明合成数据普遍优于真实 issue；PR Mirror 与 SWE-Bench 的任务结构更接近，也可能解释其轨迹对同类评测更有效。[§4.1、Tables 4–5](https://arxiv.org/html/2504.21798v1)

## 提示和测试如何塑造学到的 Agent 行为

生成的 issue 描述不是中性的包装。论文发现，若直接把 fail-to-pass 测试条件写进 prompt，模型会学会跳过 bug reproduction script；自然语言 issue 虽信息少一些，却会诱导 Agent 主动复现问题。固定 issue 模板还会使轨迹中的 action 多样性降低。因此，测试反馈既决定候选是否保留，暴露给模型的任务描述也会决定它学会哪些开发行为。[§4.1、Table 5](https://arxiv.org/html/2504.21798v1)

论文还观察到训练特定仓库可显著提高同仓库任务表现，但对未见仓库存在泛化取舍；这体现的是仓库覆盖和专业化关系，并不代表用更多合成仓库就自动覆盖真实长尾依赖、隐藏集成测试或跨项目架构知识。[§4.2–§4.3](https://arxiv.org/html/2504.21798v1)

## 阅读边界

- **合成 bug 不等同真实 issue。** 它可系统控制“哪项测试坏了”，但其错误分布受 AST 变换器与生成模型制约。
- **测试可执行不代表测试完备。** fail-to-pass 机制也会漏掉不被现有测试覆盖的用户需求。
- **合成比例不等于学习量。** 任务候选数量、教师成功轨迹、训练 token 和经过筛选的多样经验必须区分。
- **真实代码库来源不等于真实工作流。** 任务仍可能缺少代码评审、依赖变更、产品需求澄清和多人协作。

SWE-smith 的核心贡献是把“任务生成”和“环境准备”组织为可复用的数据管线；它扩的是可执行 bug 样本的供给，不是让评测成为真实软件正确性的完备判据。
