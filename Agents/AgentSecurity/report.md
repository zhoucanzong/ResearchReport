# 工具 Agent 安全：提示注入、权限与动作证据

**范围**：研究外部内容如何改变 Agent 的工具动作，以及把防御放在提示、数据通道还是执行边界会带来什么取舍。这里的“安全”主要指工具使用过程中的任务完整性、隐私和未授权副作用；它不等于模型拒答能力，也不等于一套已经覆盖真实部署的通用安全率。

## 攻击发生在“读到数据”之后

工具 Agent 会把邮件、网页、文档和数据库记录交给模型处理。这些内容可能同时包含对用户有用的事实和针对 Agent 的指令。若模型将数据里的命令当成高优先级要求，攻击者就能借用用户本来授权的工具，诱导 Agent 外发信息、修改记录或改变原任务。

一次测试至少应区分三个结果：用户任务是否完成、攻击者指定的副作用是否发生、攻击是否使原任务偏离或失败。攻击成功率（ASR）、无攻击效用、受攻击效用分别对应不同问题；低 ASR 也可能只是 Agent 整体不会操作，不能单独证明防御有效。[AgentDojo 精读](papers/2406.13352-agentdojo.md)

## 从动态攻击评测到执行时隔离

| 工作 | 防御放在哪里 | 能处理的关键问题 | 主要代价与边界 |
|---|---|---|---|
| **AgentDojo：构造可变状态的测量环境** | 不主张一种单独防御；提供邮件、Slack、旅行和银行工具环境，让用户任务、攻击目标、工具执行与状态检查共同组成测试。[精读](papers/2406.13352-agentdojo.md) | 同一环境中分别观察 benign utility、utility under attack 和 targeted ASR；攻击提示改变即可让结果显著变化，因此它暴露静态单提示测试的局限。 | 工具、任务和状态检查是人工设计的模拟环境；测试攻击能力只覆盖已构造的攻击与目标。评测框架不能自动充当防御。 |
| **CaMeL：把信任边界落实为运行时控制** | Privileged LLM 先生成受限计划，Quarantined LLM 仅解析不可信内容；解释器追踪 provenance/capability，并在工具副作用前校验策略。[精读](papers/2503.18813-camel.md) | 让恶意数据不能自行新增计划外工具调用，并限制不可信派生值流向敏感操作。 | 需要工具 schema、来源标签和逐应用策略；“Data requires action”会受限。安全性质依赖解释器、标签及策略正确，论文未机器验证完整解释器。 |
| **ARGUS：检查上下文是否足以支持动作** | 在 IPG（影响来源图）上追踪上下文如何进入工具动作；执行前检查参数来源、异常片段的良性证据支持和用户任务不变量。[精读](papers/2605.03378-argus.md) | 允许 Agent 从请求未明确指定的上下文补全对象和参数，同时要求具体状态改变仍能由可信证据解释。 | 以额外模型判断构造信任标签、参数蕴含和不变量；来源链完整不代表来源真实。白盒攻击和多环境结果仍有限。 |

AgentDojo 主要告诉我们“要在什么动态工具环境里测”；CaMeL 把信任边界放进执行架构；ARGUS 则针对上下文决定参数的任务，检查每个写操作的证据链。三者的结果不能排成一个排行榜：测试集、工具、模型、攻击者能力和安全判据都不同。

## 几个具体数字应该怎样读

在 AgentDojo 的一项 GPT-4o 设置中，无攻击效用为 69.0%，受攻击效用约 50.1%，定向 ASR 为 47.69%；工具过滤把 ASR 降到 6.84%，无攻击效用升至 73.13%，但该方法利用了用户任务以读为主、攻击任务需要写的权限结构。检测器也把 ASR 降低，却使无攻击效用跌到 41.49%，主要受误报影响。这说明所谓防御收益必须与无攻击任务能力一起报告，而且某个用例上的权限分离不能泛化成任意工具授权方案。[AgentDojo, §4.3, Tables 3–5](papers/2406.13352-agentdojo.md)

CaMeL 在 AgentDojo 的特定攻击集上展示了运行时隔离带来的安全收益，也付出任务完成率下降，Travel 子集下降尤其明显。论文的安全保证不是“底层模型不会被注入”，而是模型计划、数据来源、能力传播和受控执行共同构成的系统性质；若操作需要读到外部内容后才知道下一步做什么，静态可信计划会压低效用。[CaMeL, §§3–5, Table 2, Figures 7/9](papers/2503.18813-camel.md)

ARGUS 在 AgentLure 上将其报告的 ASR 降到 3.8%，clean utility 为 87.5%；在 AgentDojo 上也报告 ASR 从 38.1% 降到 5.0%，同时 clean utility 从 65.0% 升到 69.0%。这些是论文特定模型、工具、攻击构造和 judge 配置的结果。消融显示片段分类、良性证据蕴含、参数 grounding 与任务不变量各自会影响防御表现；白盒改写后 ASR 从 3.8% 升至 5.9%，表明基于来源图的审计降低风险，但不封闭风险。[ARGUS, §§5.1–5.4, Tables 2–5](papers/2605.03378-argus.md)

## 三种研究设计给出的保证并不相同

可以把一次间接提示注入拆成一条链：外部内容进入上下文，模型用它选择或填写动作，工具再改变外部状态。三项工作分别研究这条链上的不同环节，而不是三种可直接横比的防御产品。

| 工作 | 主要控制点 | 它试图阻止什么 | 核心假设与残余风险 |
| :-- | :-- | :-- | :-- |
| AgentDojo | 测量环境 | 识别恶意工具内容如何影响用户任务与环境状态 | 任务、攻击载荷和状态检查覆盖有限；它本身不是防御器。ASR 必须连同 benign/attacked utility 读。 |
| CaMeL | 计划生成与执行解释器 | 不让不可信观察直接改写可信控制流；用 provenance/capability 检查数据是否能流向副作用 | 工具 schema、来源标签与应用策略必须正确；预先静态化计划会难以处理“读完内容才知道要做什么”的任务。 |
| ARGUS | 每个写动作的证据链 | 不把来源可疑的片段当作参数的充分依据，并检查动作是否仍满足用户任务不变量 | 片段分类、蕴含判断和不变量提取由模型辅助；来源链完整不证明内容真实，语义审计也可能误放行或误拦截。 |

CaMeL 的约束较靠近可执行边界：在假设标签和策略正确时，未授权数据依赖无法通过解释器触发受控副作用；代价是数据驱动的新动作可能被阻断。ARGUS 允许从上下文补全用户没有写出的参数，再检查良性证据能否支持具体写操作；它保留更多适应性，但把一部分安全关键判断交给审计模型。两者的研究路线反映一个实质取舍：**静态控制流更容易限定动作集合，动态证据审计更能适应上下文，却更依赖语义判断的可靠性。**它们都不能单靠 provenance 证明发件人、文件或网页真实可信。[CaMeL §§3–5、8–9](papers/2503.18813-camel.md) [ARGUS §§4–6](papers/2605.03378-argus.md)

AgentDojo 为这种机制比较提供有状态的工具环境，却不替防御器证明机制。它的攻击输入、任务状态和工具效用可控，便于重复比较；覆盖不到的应用动作、真实身份认证、跨租户权限和不可逆外部副作用仍然在测试边界之外。因此，一个可解释的安全结果至少要分别报告：无攻击的任务完成、受攻击时的原任务效用、未经授权的环境改变、正确动作被误拦截、以及剩余的状态恢复能力。单一 ASR 不能区分“安全地完成”与“什么也做不了”。[AgentDojo §§2–5](papers/2406.13352-agentdojo.md)

## 多 Agent 与电脑使用会改变信任边界

单个 Agent 的工具执行策略，在父 Agent 将工具结果交给子 Agent 时仍可能失效：原本是不可信观察的字符串，可能被包装成下游的可信请求。Multi-CaMeL 将这两类内容分成 `message` 与带来源/能力元数据的 `variables` 两条通道，在多 Agent 解释器层维护控制流完整性。它补的是 CaMeL 的跨 Agent 组合边界；实验用空安全策略，因此不证明真实用户授权和审批已解决。[Multi-CaMeL 精读](../AgentSystems/papers/2610.05640-multicamel.md)

电脑使用 Agent 还可能通过 shell、隐藏 API、应用内部文件或会话凭据绕过可见界面。基准若只看最终工件，可能奖励完成目标但未遵守操作约定的捷径；若只禁止特定工具名称，也可能漏掉功能等价的调用。长程桌面任务中的界面捷径与轨迹判分见[电脑使用专题](../ComputerUse/report.md)。因此工具安全报告应把**动作效果、可信来源、用户授权与终态**连起来检查，不能把可见 GUI 操作本身当作安全证据。

## 防御选择取决于任务怎样定义

- 若工具集合和副作用可枚举，策略可在执行前验证，运行时权限与数据来源隔离比单纯要求模型“不要听网页指令”更可检验。
- 若任务依赖外部内容补全参数，应保留数据读取能力，但把“可用来填参数”与“可授权新增动作”分开，明确哪些字段必须来自用户或可信系统。
- 若任务是动态的、需根据新观察改变动作，应把 replanning 纳入受约束系统，而非默认所有控制流必须在初始提示时静态写死；每次新计划仍需检查权限、来源和用户目标。
- 若结论来自攻击基准，报告 benign utility、attacked utility、targeted ASR、拒绝/误拦截率和真实副作用检查；明确攻击文本、模型、工具、提示、重试以及裁判构造。

以上是从三篇论文中抽出的设计判据，不是一个现成的统一部署方案。防御越严格通常越容易造成误拦截或降低任务能力；如果策略过宽，攻击可以把已授权工具用于未授权目的。安全研究要同时展示攻击者能做什么、防御在什么运行时层执行、正常任务损失多少，以及哪些侧信道和外部动作仍在边界之外。

## 尚未解决的问题

- provenance 能否证明内容来源可信，还是只记录“哪个工具返回了这段文本”？被攻陷的网页、伪造文件或被污染的外部服务如何验证？
- 当用户请求含糊或依赖外部内容决定下一动作时，如何在安全策略内继续规划并请求恰当澄清？
- 如何验证解释器、工具 schema 和应用策略本身，特别是遗漏工具、隐式控制流、并发状态和未登记副作用？
- 多 Agent、GUI/CLI 混合接口和长期运行环境如何保持权限、来源与用户意图的一致传播？
- 攻击者能观察拒绝、重试和输出差异时，怎样测量自适应攻击与信息侧信道？

本专题覆盖提示注入下的工具安全机制与评测，不覆盖完整应用安全、通用模型拒答、沙箱实现或真实生产事故率。阅读入口依次为 [AgentDojo](papers/2406.13352-agentdojo.md)、[CaMeL](papers/2503.18813-camel.md)、[ARGUS](papers/2605.03378-argus.md)，之后回读[多 Agent 信任边界](../AgentSystems/report.md)与[长程电脑使用](../ComputerUse/report.md)。原文结果未独立复跑，安全率不得外推为部署保证。
