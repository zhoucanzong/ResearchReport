# CaMeL：把提示注入防御做成执行边界

> Edoardo Debenedetti et al., *Defeating Prompt Injections by Design*, arXiv:2503.18813v1（2025-03-24）。本文阅读的是[固定版本 v1 的完整 arXiv HTML 原文](https://arxiv.org/html/2503.18813v1)，重点参照 §2–6、§8、Table 2、Figure 7–11 与 Appendix F。

## 为什么“计划模型不看网页”仍不够

假设用户让 Agent 把会议记录中提到的文件发给 Bob。一个 Privileged LLM（特权模型，P-LLM）只看用户请求，先规划“找会议记录、提取收件人和文件名、读取文件、发送邮件”；另一个 Quarantined LLM（隔离模型，Q-LLM）只负责从记录文本中提取结构化字段，不能调用工具。这个双模型结构阻止网页或邮件里的恶意文字直接改写原计划。

但它尚未阻止攻击者把字段改成自己的邮箱和另一个文件。工具调用顺序仍遵守计划，参数却被不可信数据操纵。论文把这看成经典软件安全里的数据流问题：只保护控制流（程序接下来调用什么），不保护数据流（参数来自哪里、依赖什么），就仍可能把秘密送错地方。CaMeL 的核心是在模型与工具之间加一层受限解释器：模型负责提出计划和解析，程序执行环境负责跟踪来源、依赖及权限，并在副作用发生前执行策略。[§2、Figure 1–3](https://arxiv.org/html/2503.18813v1)

## 可信计划和不可信数据如何分工

P-LLM 根据用户请求生成受限 Python 子集中的代码，并为每次 Q-LLM 调用声明一个结构化输出 schema。它只看到原始请求、工具接口和自己生成的代码；工具返回值被存进解释器变量，P-LLM 看不到这些值。Q-LLM 可以读取不可信邮件、网页或文档，把其中与任务有关的内容提取成 schema 字段，但没有工具权限，也不能把“还需要什么信息”的自由文本回传给 P-LLM。若信息不足，它只能设置 `have_enough_information=false`，让解释器抛出受控错误。

这条单向边界有意牺牲灵活性：不可信材料可以填充计划已经预留的参数，却不能临时发明新的工具步骤。它把容易混在同一上下文里的“指令”和“数据”变成不同的执行角色与接口。P-LLM 先定控制流，Q-LLM 在隔离区内解析数据，解释器再按显式依赖执行工具；因此，恶意内容即使影响提取结果，也不等于取得了任意调用工具的能力。[§4.1、Figure 3](https://arxiv.org/html/2503.18813v1)

代价也来自同一个设计选择。若用户说“按这封邮件里的要求操作”，实际动作本身要等读完邮件才知道，P-LLM 就无法事先写出完整计划；论文将这种 “Data requires action” 列为系统性失败模式。让 Q-LLM 把邮件里的动作交回 P-LLM 再规划，会重新打开恶意数据影响控制流的通道，只有在额外工具和严格策略的约束下才可能安全地扩展。[§5.1.2、Table 1](https://arxiv.org/html/2503.18813v1)

## provenance 与 capability：把来源追踪变成调用许可

CaMeL 给每个值附上 capability 元数据。原型实现的标签主要回答两类问题：**谁能读取这个值**，以及**这个值从哪里来**。来源可标记为用户、CaMeL 自身的变换或某个工具；工具还可以给出内部来源，例如邮件的发件人。变量运算会传播依赖：`c = a + b` 后，`c` 同时依赖 `a` 和 `b`。检查工具调用时，解释器沿依赖图检查参数及其祖先，而不只看眼前的字符串。

例如，邮件内容提取出的收件人地址虽然是合法邮箱字符串，但它的来源仍是外部邮件；待发送的附件也保留文件的来源和允许读取者。`send_email` 策略可以要求附件对所有收件人可读，或要求敏感收件人直接来自用户。若不满足，系统阻止执行或请求用户确认。这样，Q-LLM 被注入后即使返回攻击者地址，攻击者也不能仅凭改变字段就获得文件权限。

只靠粗粒度控制流规则会很僵硬：某个工具可合法处理名字和电话，却不应处理护照号。Capability 让策略能针对具体值及其派生结果表达限制。论文将策略写成 Python 函数，由服务方针对应用定义；这既提供了表达力，也把政策的正确性、覆盖面和维护责任留给系统运营者。若来源注释缺失或不准确，运行时就无法凭空推断真实授权。[§4.2–4.3、Figure 4、Appendix E](https://arxiv.org/html/2503.18813v1)

解释器还要追踪隐式控制依赖。若私密值决定 `if` 是否运行，即使分支中的工具参数没有直接引用该值，外部也可能从调用次数推断信息。CaMeL 提供 NORMAL 与 STRICT 两种模式；STRICT 把条件或循环迭代对象传播为分支内赋值的依赖，并将 Q-LLM 调用的输入依赖延伸到后续语句。这能挡住论文展示的部分侧信道，但会让更多调用触发策略确认，且不等于覆盖所有时序、异常或共享资源侧信道。[§4.4、§6、Appendix D](https://arxiv.org/html/2503.18813v1)

## “可证明安全”具体证明到哪里

标题里的 “by design” 指安全检查被放到确定性解释器与策略执行层，而不依赖模型是否服从“忽略恶意指令”的提示。它确实比只报告某个攻击集上的低成功率更强：在假设与标签可信、解释器正确执行、所有副作用都经过策略检查的范围内，模型即使被诱导，也不能让不受策略允许的数据流通过受控工具边界。

但这不是一份已经机器验证的完整安全证明。作者把形式化验证 CaMeL 解释器及其安全属性列为未来工作；论文原型的策略由服务方编写，目前也没有策略冲突解决机制。其保证针对特定威胁模型与受控工具接口成立，并依赖可信用户请求、未被攻陷的记忆、正确的来源标注和足够完整的策略。[§3、§4.2、§9](https://arxiv.org/html/2503.18813v1)

论文明确不试图阻止所有由提示注入引发的错误内容。例如，恶意邮件诱导 Agent 向用户错误概述邮件，若没有敏感数据外流或越权副作用，CaMeL 不一定能判断语义真伪；诱导用户点击钓鱼链接也属于非目标。若用户请求本身含糊，系统仍可能要求人澄清。另一个关键边界是“数据变控制流”：如果用户一开始就授权 Agent 按任意邮件内容逐条执行动作，可信计划本身可能预先包含遍历工具并按邮件指令选择调用的结构；隔离单个 Q-LLM 并不能自动使这样的宽泛授权安全，仍需细粒度策略约束。[§3.1、§5.4](https://arxiv.org/html/2503.18813v1)

实验提供的是对设计价值与效用代价的基准证据，而非普遍免疫证明。在 AgentDojo 的 949 个攻击实例中，不加额外安全策略、只启用模型隔离的设置下，GPT-4o 的成功攻击数从 233 降到 0；作者同时报告有些剩余“成功”属于其非目标，例如把未可信酒店评论原文展示给用户。对 Claude 3.5 Sonnet 的防御比较中，CaMeL 在该攻击集上的成功攻击为 0，次优 tool filter 为 8；但作者指出，基线模型对 AgentDojo 默认攻击本来就较稳，改变攻击提示可能改变结果。[§5.2.1、§5.3、Figure 7、Figure 9](https://arxiv.org/html/2503.18813v1)

## 效用成本不是一个平均分能概括

在无攻击的 AgentDojo 任务上，Claude 3.5 Sonnet 的整体任务成功率由原生工具调用的 81.7% 降到 CaMeL 的 62.0%；Travel 子集下降更明显，为 70.7% 到 26.4%。作者将主要原因归于受限计划对工具输出结构的依赖：Travel API 文档不足时，P-LLM 不知道怎样解析返回值；Q-LLM 虽能提取字段，却不能将新动作建议回可信规划端。某些后端模型使用 CaMeL 后效用反而更高，所以成本依赖模型与任务，不能压成统一折损率。[§5.1.1–5.1.2、Table 2](https://arxiv.org/html/2503.18813v1)

在 token 用量上，作者报告对 Claude 3.5 Sonnet，CaMeL 相比原生工具调用的**中位任务**输入、输出 token 开销各约为 2.7–2.8 倍。主文 Figure 11 的说明与 Appendix F Table 10 对输入、输出的具体倍率标注互换，因此这里不把每个方向的倍率当作精确值；两处共同支持的是 token 成本大致在该范围。计量排除了两边工具文档 token，但计入受限 Python 子集说明。额外成本来自计划代码、结构化提取和代码错误后的重试。解释器维护依赖图的 CPU/存储开销相较模型推理较小；更大的工程成本是把工具和数据源接入统一的标注与策略体系，以及让规则既能拦住越权，又不会引发过多确认和用户疲劳。[§5.5、Figure 11、Appendix F Table 10](https://arxiv.org/html/2503.18813v1)

## 读完后应保留的判断

CaMeL 的关键贡献是把 Agent 安全从“模型能否识别恶意文本”转成“运行时允许什么数据依赖触发什么副作用”。可信计划/隔离解析保护控制流；provenance 与 capability 策略约束数据流。它特别适合工具集合受控、工具 schema 明确、组织能维护数据标签与授权规则的工作流。开放网页、第三方工具和需要根据不可信内容动态决定行动的任务，会暴露覆盖、标注和效用上的难点。

后续问题不是简单地把策略写得更严格，而是怎样证明解释器与策略组合确实保留安全属性、怎样为陌生工具可靠补齐来源与读者元数据、怎样表达用户授权而不过度弹窗，以及怎样在不恢复“数据决定新计划”的前提下处理必须根据外部内容采取新行动的任务。作者明确承认提示注入尚未解决，并把策略维护、能力生态接入、去敏/授权负担与侧信道列作未解问题。[§8–9](https://arxiv.org/html/2503.18813v1)

和本库的 [Multi-CaMeL 精读](../../AgentSystems/papers/2610.05640-multicamel.md)相比，原始 CaMeL 建立单个 Agent 内部的可信计划、污点传播和工具执行策略；Multi-CaMeL 进一步把指令通道与带 provenance/capability 的数据通道跨父子 Agent 边界传递。后者处理的是原理在多 Agent 编排中的组合问题，并不取代本文的单 Agent 执行机制。
