# AgentRx：把“Agent 失败了”拆成可定位的关键步骤

> Barke et al., *AgentRx: Diagnosing AI Agent Failures from Execution Trajectories*, arXiv:2602.02475v2 (2026-08-31; accepted to EMNLP Findings 2026). [固定版本 HTML](https://arxiv.org/html/2602.02475v2)

## 问题：最终失败不等于最后一个错误

长轨迹可能先出现一次无效调用或错误假设，Agent 随后还能恢复；也可能早期偏差一直传播，到最后才表现为失败。AgentRx 将目标定义为定位**第一个不可恢复的关键失败**，而不是第一个错误或最后的失败症状（§1–2）。

## 机制：用逐步约束给 judge 提供可查证据

系统先把不同框架日志规整为统一轨迹，再根据工具 schema、领域策略和截至当前步骤的历史生成约束。它逐步检查约束，把违规与相应消息、调用或环境状态组成 validation log，最后由 LLM judge 判断关键步骤和根因类别（§3）。

论文基准包含 170 条失败轨迹、11 种任务设置，覆盖 τ-bench、Flash、Magentic-One 和 RelWork 等来源；分类法含 9 类根因。三位标注者在 30 条抽样轨迹上的成对平均 Cohen’s κ 为 0.89；这不是对全量 170 条的三重标注一致率（§2.1）。

在默认 GPT-5 judge 设置下，τ-bench 的关键步骤精确定位准确率从 baseline 的 29.9±1.2% 升至 42.7±1.2%，平均步骤距离从 5.4±0.14 降至 3.8±0.6；每个配置运行三次（§4.1、Table 7）。这是诊断器在该失败轨迹集上的指标，不是 Agent 任务成功率或恢复率。

## 诊断输出仍可能误导

作者的错误分析指出，自动检查可能出现两种问题：约束假阳性会把 judge 引向错误类别；真实但较晚的违规也可能只是更早根因的下游症状（§4.7）。论文因此把 AgentRx 定位为证据化的调试助手，而不是正确性 oracle。失败分类表能帮助查错，却不能证明 Agent 已经恢复或运行环境安全。
