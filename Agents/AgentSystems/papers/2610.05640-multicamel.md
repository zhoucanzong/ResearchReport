# Multi-CaMeL：多 Agent 之间，数据不能因转发而变成指令

> Peters-Gill et al., *Can CaMeLs Talk? Securing Multi-Agent Systems Against Indirect Prompt Injection Attacks*, arXiv:2610.05640v1, 2026-10-05. [arXiv 页面](https://arxiv.org/abs/2610.05640) · [实际阅读的完整 HTML 原文 v1](https://arxiv.org/html/2610.05640v1)

## 一个 Agent 守住了边界，整个系统仍可能失守

设想用户让系统把数据库里申请人的摘要发给同事 Julie。SQL 子 Agent 从数据库读出资料；其中混入一条恶意指令，要求再把资料发到攻击者邮箱。每个 Agent 都单独运行 CaMeL：模型先根据可信请求生成受约束的 Python 控制流程，工具返回值在运行时保留来源信息，随后由解释器检查工具调用。问题发生在编排 Agent 把摘要拼进下游通知 Agent 的自然语言请求时：对前一个 Agent 来说，这段内容是数据库返回的不可信数据；到下一个 Agent 那里，它却成了看起来可信的“用户请求”。下游于是新增邮件发送动作。

论文把这种跨边界的信任升级称为 **boundary laundering**。关键漏洞不是某个模型没学会拒绝“忽略之前指令”，而是系统接口把“父 Agent 写的指令”和“父 Agent 转交的数据”混成一段文本。安全性质若只在单个 Agent 内成立，就不必然能组合成系统安全。[§II–III、Figure 2–3](https://arxiv.org/html/2610.05640v1)

## 两条通道把信任边界带过 Agent 接口

Multi-CaMeL 将父子 Agent 调用拆成两个参数：`message` 是可信自然语言指令，交给子 Agent 的 privileged LLM；`variables` 是运行时数据字典，工具返回值及其 capability/provenance（权限与来源元数据）放在其中，privileged LLM 不直接读取这些值。子 Agent 需要处理数据时，通过专门的运行时接口访问变量，再将处理结果交给受策略检查的执行层。

这不只是约定调用者“请把两类文本分开”。扩展后的解释器在调用点强制两条不变量：`message` 不能依赖任何工具输出；经 `variables` 传递的数据则必须保留原有来源和 capability。于是，一个网页可以影响本来就计划好的消息正文，却不能通过正文注入让下游 Agent 临时加出“再给陌生人发一封邮件”这条控制路径。读者可以把它理解为给 Agent 间 RPC 加了类型和污点传播：调用者显式提供指令通道、数据通道，运行时拒绝把不可信依赖塞入前者。[§IV-A–C、Figure 4](https://arxiv.org/html/2610.05640v1)

论文把这种保证称为**控制流完整性**（CFI）：工具返回值可以决定执行预先写入计划的哪个分支，但不能凭空引入计划之外的工具调用。这里的“可信计划”仍由模型生成；执行层保障的是计划之后的控制流边界，不是证明用户的原始授权描述完整、正确或无歧义。论文还指出，在其树形 agent-as-tool 模型和温和的表达能力假设下，凡是多 Agent 系统含有不可信工具返回值，单 Agent 的 CFI 一般都不能推出系统级 CFI；这解释了为何只加固每个模型提示并不足够。[§II-B、III-C](https://arxiv.org/html/2610.05640v1)

## 安全收益有实验支持，但“有权限”尚未被真正验证

作者将 AgentDojo 改造成 MultiAgentDojo：把 Workspace、Banking、Slack、Travel 中的工具分给二至四个专职子 Agent，再由 orchestrator 委派，以便攻击必须穿越 Agent 边界。对每个模型配置运行 949 个注入任务实例；五种后端模型的平均攻击成功率从无 CaMeL 的 12.9%，降至单独 CaMeL 的 0.2%，再降至 Multi-CaMeL 的 0%。零次成功是这个基准和攻击集上的观测，不是对自适应攻击的普遍免疫证明。作者也特别提醒，GPT-5.5 在基准里无防御时已经是 0%，不能据此断言它普遍安全。[§V-B、Table III](https://arxiv.org/html/2610.05640v1)

效用成本需要和安全收益一起读：在 AssetOpsBench 排除作者识别出的 29 个不可按要求完成的任务后，Multi-CaMeL 相比单 Agent CaMeL 平均再降低 3.2 个百分点；两个最强模型上平均降低 0.85 个百分点。每个模型这两种配置的 95% 区间有重叠。对单 Agent CaMeL 而言，相较无防护的平均效用损失则是 21.6 点，显示主要约束来自先生成计划、后观察工具结果的执行模式，而非只来自跨 Agent 通信协议。方法还要求预先给工具补充完整返回 schema，否则 privileged LLM 在不知道返回结构时难以预先写出解析代码。基准上相对温和的增量效用损失，不能直接等同于真实工作流成本。[§V-A、Figure 5](https://arxiv.org/html/2610.05640v1)

尤其要留意授权边界：论文的 MultiAgentDojo 实验明确使用**空安全策略**。协议和形式化分析说明它可以保留跨 Agent 的来源与 capability，以便配合非平凡策略；但本文没有实证检验“某用户是否真的授权把某类数据发给这个收件人”，也没有比较确认提示、审批门、最小权限、撤销或补偿操作。因此，这篇论文证明的重点是**外部副作用的控制路径不能被跨 Agent 注入悄悄改写**；它没有证明某一封原计划邮件、转账或删除操作本身符合用户真实意图。发送前的目的地/对象授权和高影响操作审批，仍须由具体策略与宿主执行层落实。[§II-B、IV-B、V](https://arxiv.org/html/2610.05640v1)

## 边界、未解问题与现有精读的关系

Multi-CaMeL 只研究有根树形的父子 Agent-as-tool 调用。DAG、共享状态、异步队列、Agent 间保留会话历史的重入以及循环通信都需要额外处理，因为它们可能让污点通过未受控通道重新进入指令上下文。实现继承 CaMeL 解释器对隐式控制依赖追踪不完备的问题；例如依赖不可信条件的分支赋值可能漏标。作者还指出 CaMeL 的外部重试循环可能形成信息侧信道，而当前 Multi-CaMeL 实现不重试，因此没有继承这一特定问题。这些边界提醒我们：显式双通道是一个可检验的组合原则，不是完整的信息流机密性证明。[§VI](https://arxiv.org/html/2610.05640v1)

它和本专题已有工作互补：**AgentRx** 从失败轨迹定位最早的不可恢复错误；**AgentRewind** 把受控工作区与上下文回滚到检查点；**Fission-GRPO** 学习在工具报错后修正策略。三者都不规定多 Agent 之间如何保留权限与数据来源。Multi-CaMeL 直接补的是这条安全边界，但也不做环境回滚或训练恢复。[AgentRx](2602.02475-agentrx.md) · [AgentRewind](2608.14380-agentrewind.md) · [Fission-GRPO](2026-acl-long-1880-fission-grpo.md) · [Agent 系统入口](../report.md)

现有[评测科学报告](../../../Evaluation/EvaluationScience/report.md)解释 benchmark、harness、metric、judge 和闭环外部效度如何约束分数含义；它能帮助读者审视这里的 949 个注入实例、任务筛除和基准泛化，却没有覆盖 Agent 安全策略本身。后续评测若要支持“授权安全”，需将攻击成功与合法任务效用分开，明示用户/工具授权策略及副作用判定规则，并在重复运行中记录最终环境状态；终态正确也不能单独证明中间未发生未授权但可逆的动作。
