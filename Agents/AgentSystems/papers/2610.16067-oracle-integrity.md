# Agent 评测的 oracle 也需要被测试

> Junjie Chen, *When Agent Evaluation Becomes Unreliable: An Empirical Study of Oracle Failures and Configuration-Dependent Measurement in an LLM Agent Benchmark*, arXiv:2610.16067v2（2026-10-21）。[固定版本原文](https://arxiv.org/html/2610.16067v2) · [arXiv 版本记录](https://arxiv.org/abs/2610.16067)

## 分数可能错在 Agent 之外

长程 Agent 的失败分析通常盯着轨迹：它何时走偏，能否恢复，重复运行是否稳定。但一条轨迹被判成成功，还取决于评分器如何读取和改变环境。本文把评测 harness 本身当作待测软件，核心问题不是“哪个模型更可靠”，而是“产生成功标签的 oracle 是否完整、标签是否真对应 Agent 留下的终态”。

这个区分很实际：如果评分器为了构造参考答案而修改了它随后要检查的数据库，那么即使它返回的参考值本身正确，稍后的评分也可能读取到参考解留下的状态，而不是 Agent 的结果。于是同一个系统既能有随机轨迹，又能被一个确定但状态有副作用的 evaluator 错判；两种误差不能靠多跑几次相互抵消。

## 如何审计评分器

作者将 oracle 通过四个操作暴露出来：创建新环境、取得可比较的环境状态签名、调用评分器、选择可注入缺陷的评分器实现。检查分两类：五项状态不变量检查评分前后是否污染状态、重复评分是否改变 verdict、评分顺序是否影响结果、异常时能否恢复，以及终止后状态是否仍属于 Agent；三项已知答案控制则检查空操作不能通过、参考解应通过、允许的替代表述应被接受。随后向评分器注入七类缺陷，形成 21 个变体，并在三个目标上检验这些检查能否发现问题（§3.2，§4.1）。

在 57 个差分探针确认可区分的“变体×目标”组合中，检查套件发现 54 个；另有 6 个组合无法由探针判定，作者单独列出而没有算作成功。一个“评分器吞掉内部异常”的变体在三个目标上都漏检：缺陷破坏了检查的前提，使检查把路径记为“不适用”。因此，54/57 是对作者构造的缺陷集和所测实现的检测结果，不是对未知评分器错误的普遍召回率。两个目标共享同一评分实现，第三个是合成环境，也不是三个独立的生产 benchmark（§4.1）。

## 一个评分副作用如何改写实验结论

在所审计的工具交互 benchmark 中，reward 函数会重置数据库、执行参考工具序列以构造 ground-truth hash，却没有在返回前恢复数据库。函数计算出的 hash 没错；问题出在外部 harness 在会话后再次读数据库判分，此时数据库已留在参考解状态。benchmark 自身的 runner 直接使用 reward 返回值，不会遭遇这个二次读取问题；错误标签来自 reward 与外部评分流程的集成（§4.1）。

论文重放了 4,320 条已归档轨迹：30 个 retail 任务、4 个 Agent、6 个用户模拟器、两种用户语言、每格 3 次。由于服务端既不提供有效确定性 seed，也没有不可变模型版本，作者不能重新生成同样轨迹；他们将已记录的工具调用在干净数据库上重放，再比较终态。137 条以步数上限结束、原本不会经过缺陷路径的轨迹标签保持一致；33,402 条工具观察也逐字重现。数据库通过数从原标签的 4,194 降至重放校正后的 2,883，总成功率从 94.3% 降到 65.5%，下降 28.8 个百分点（按任务聚类的 95% 区间为 −38.79 至 −18.81 个百分点；§4.1，Table 4）。

影响并非统一扣分：四个 Agent 各自下降约 24–34 个百分点，点估计的领先组发生变化。但原标签下领先者相对第二名的差距本来就没有统计分辨力；校正后新的前两名也无法相互区分。因此可支持的结论是“评分缺陷足以改变这个矩阵的标签和比较对象”，不能据此宣布某个模型真实胜出。范围仅限该论文的 30 个任务、单一服务提供方和这批已归档轨迹，不代表所有 τ-bench 版本、任务或部署结果。

重放是这里的关键机制：它不要求再次调用模型，所以能在轨迹不可复现时检查原动作在干净状态下产生了什么结果。它的前提也很明确：benchmark 必须记录足够完整、可重新执行的工具调用，而且环境可重置。作者在另一个独立实现的 benchmark 上无法从 API 调用日志重建正控制所需的参考终态，因而没有报告迁移检测率（§6.3）。对不可重放、真实外部副作用不可撤销的环境，这个修正路径并不自动成立。

## 可靠性测量还依赖配置

论文的次要实验显示，轨迹退化率也会随 harness 配置变化，但它测量的是 Agent、模拟器与提示环境组成的配置，不是模型的内在属性。一个按“至少五个连续回复步、每步最多两个 completion token、且无工具调用”定义的停滞事件，在 retail 与 airline 两个域里对模拟器语言的变化呈相反方向；作者据此收窄外推，而不是把某一配置的结果讲成通用规律（§4.2–4.3，§6.1）。这个操作化定义和两域反转提醒读者：重复成功率应连同任务、模拟器、终态 checker 与交互配置一起报告，单独一个百分比不足以描述 Agent 的可靠性。

## 与 Agent 故障恢复研究的关系

这篇论文与本专题已有的三条工作线互补，测量对象不同：

- [AgentRx](2602.02475-agentrx.md) 在失败轨迹中定位第一个不可恢复的关键步骤，研究“Agent 为什么失败”；它的诊断器可能误报，但不审计最终给分的 oracle 是否污染环境。
- [AgentRewind](2608.14380-agentrewind.md) 回滚受控工作区和上下文，研究“Agent 出错后能否从可恢复状态继续”；其重复运行差异被作者归于轨迹等运行变化，并非 evaluator 噪声估计。本文提供了一个相反方向的必要检查：先确认评分器没有改写它要评估的终态。
- [Fission-GRPO](2026-acl-long-1880-fission-grpo.md) 将在线工具错误变为策略更新信号，研究“训练能否教会 Agent 从反馈中恢复”；更好的恢复策略无法修复错误标签，oracle 审计也不会教模型如何重试。

合起来看，长程可靠性至少有三处需要分开测：Agent 轨迹是否重复成功、运行时恢复是否保留正确环境状态、评估器是否诚实地读取轨迹留下的状态。本文新增的是第三项的可操作审计与反例，而不是另一种 Agent 恢复算法，也不是 τ-bench 的重复成功率研究（该基准的 `pass^k` 已在[评测科学精读](../../../Evaluation/EvaluationScience/papers/2406.12045-tau-bench.md)讨论）。

**阅读判断：**值得读它，是因为一个评分函数的普通状态管理 bug 就能静默污染结果，并且差异重放能在无法复现模型轨迹时纠正标签。最应带走的不是 94.3% 这个特定数字，而是可迁移的审计问题：重复评分是否稳定、调用前后状态是否守恒、已知正反例是否得到正确标签、记录的动作能否独立重放。检查集仍受构造的缺陷类型、接口契约和可重放条件限制；部署到新 benchmark 前，必须先确认它能提供可比较终态和干净重置。
