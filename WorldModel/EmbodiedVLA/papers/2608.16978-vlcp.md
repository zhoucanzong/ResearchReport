# VLCP：在单个 episode 内重写失败的控制代码

> **来源版本**：[arXiv:2608.16978v1](https://arxiv.org/html/2608.16978v1)，2026-08-17（版本记录见[来源清单](../sources/MANIFEST.md)）。
> **主等级**：`[精读原文]`（全文 PDF，由 PaperFetcher 下载并提取；关键结果回查 arXiv HTML）。
> **适用问题**：冻结 VLM 不微调、不用机器人示范时，能否通过重观察并改写控制程序在单个 episode 内恢复失败？

## 亮点与差异

- **一句话亮点**：VLCP 在每个控制 block 结束后让 VLM 基于新 RGB、proprioception 与状态变化重写 Python 控制函数，把反馈闭环落在“导致失败的程序”本身。
- **新在哪**：和只把相同策略重试一次、或让高层 planner 选另一个子任务不同，它允许中途修改低层控制逻辑；同时生成的 helper skill 可跨 episode 复用，但主结果测试把技能库清空以隔离每项任务。
- **证据强度**：57-task MuJoCo/RoboVerse 主 sweep，配对同模型 open-loop（K=T）对照，仅改变是否 episode 内重规划；另有 75 个抓放 episode 的失败恢复分析。所有硬件证据均为仿真：Franka Panda 7-DoF + 平行夹爪，物体 pose 来自 simulator。
- **值不值得引用**：值得作为“代码级、单 episode 失败恢复”的机制论文；不能引用为真机闭环 VLA 结果。18.8 秒中位 VLM 单次延迟也限定其用途在较慢操作。

## 七问

### 1. 解决什么问题？

通过 VLM 一次生成程序做机器人操作，虽然复用了模型原有代码能力，但通常是开环：前面的抓取错误会一直带到 episode 结束。只给动作输入新观测的反馈不一定能改正控制逻辑；VLCP 因而在 block 边界重新观测并重写函数（VLCP v1 §1、§3.1–3.3）。

### 2. 核心方法是什么？

VLM 保持冻结，不做微调，也不使用示范。它为低层机器人 API 生成一个运行 `K` 步的 Python 函数；每步接收当前 observation 和雅可比/控制状态 `J` 并输出动作。默认每 50 步重新查询，生成下一个控制函数。重规划请求含两路同步 RGB、EE pose/关节/物体 pose 等数值摘要，以及前一 block 的图像、代码和 action trace（§3.1–3.3）。

这里有两层反馈：block 内函数每步拿到新 observation，但不会调用 VLM 改代码；block 边界处模型可根据失败重写函数。它不是高频 token-by-token 策略，也不是训练更新（VLCP v1 §3.1–3.3）。

模型在重规划时可以创建 helper skill，原子写入共享磁盘目录并供后续任务 prompt 引用，最多注入近期 12 个模块（§3.4）。该跨 episode skill 记忆与当回合在线纠错相邻，但属于代码库积累，不等同于对策略权重的 RL 更新。

### 3. 数据与规模是什么？

- MuJoCo 经 RoboVerse 仿真，Franka Panda 单臂 7-DoF、平行夹爪，GPT-5.5，每 `K=50` steps 重规划（§4.1）。
- 主对照含 Object Picks 10 项、Kitchen Scenes 30 项、Living-Room Scenes 17 项；每项单 episode，共 57 个 closed-loop episodes，并与 57 个匹配 open-loop `K=T` episodes 对照。任务间 skills library 清空，避免积累迁移影响（§4.1）。
- 抓放恢复统计使用更大的 75 个闭环 episode 语料，其中 55 个至少出现一次失败抓取（§4.5，Table 2）。这不是 57-task 主 sweep 的分母。
- 方法依赖 simulator 提供的 object poses；视觉输入用于诊断抓偏、空抓、滑落等过程，而 localization 被刻意隔离（§3.3、§5）。

### 4. 主要结果是什么（带条件）？

- 57 项仿真主 sweep 中，pooled success 为 **35.1%**；将查询间隔设为 `K=T` 的同模型 open-loop 退化版为 **3.5%**，每个 scene family 的 95% Wilson 置信区间不重叠（Fig. 2，§4.3）。这是配对仿真结果，不是现实世界成功率。
- 在 75 个抓放 episode 的失败抓取中，55 个有失败，15 个后续重规划成功重新靠近并举起物体：**15/55=27.3%**；恢复中位需要 3 次 replanning（Table 2，§4.5）。40 个仍未在 horizon 内抓起物体，说明恢复可见但有限。
- 主 sweep 之外的运行成本集计为 81 episodes、约 721 次 replan calls；每 episode 中位 10 次（均值 8.9），单次 VLM 延迟中位 18.8s（均值 25.9s），cached-prefix fraction 中位 83.8%（Table 3，§4.6）。论文摘要概述为约 84% tokens 命中缓存。
- 778 个生成 block 全部成功 parse/compile；这只说明代码语法/编译有效，不代表所有运行期执行成功（Table 3，§4.6）。

### 5. 消融说明什么？

`K=T` 的同模型 open-loop 对照保持 simulator、API、privileged poses、任务、模型和 episode budget 一致，只移除 episode 内重规划（§4.3，Fig. 2），因此支持“本设置里的即时重规划是主要增益来源”。恢复率分析进一步把一部分成功增益连接到可观察的失败后重新靠近与举起物体（Table 2）。

此消融并未隔离 VLM 强度、实际感知模型，亦未与训练后的 VLA 做硬件匹配比较。

### 6. 什么条件下失效或结论受限？

- **没有真机试验**，作者明确依赖仿真 object pose，感知噪声与真机动力学鲁棒性尚未验证（§5）。
- 18.8s 中位请求延迟难以用于高速接触控制；它适合较慢 manipulation，不能由 50 simulation steps 误读成 50 Hz VLM 决策（§4.6、§5）。
- 57-task sweep 每任务只测一个 episode；成本分析补充语料增多，但不等于全体 57 任务均多随机种子重复（§4.1、§5）。
- 失败抓取后，只有 27.3% 的失败样本成功恢复；有限 episode horizon 仍会被重复近失误耗尽（§4.5）。
- 系统依赖强闭源 GPT-5.5；作者报告尝试的 Qwen3-4B 未能稳定生成有效控制代码和有效重规划（§5）。

### 7. 与同类系统如何判定差异？

VLCP 的核心是**同一 episode 内重写代码控制器**；RECAP 则训练更新跨 episode 的参数化 VLA，使用现实轨迹和奖励；LingBot-VA 以因果视频/动作生成滚动多个动作步并用真实 observation 更新状态；VersualRL 在 episode 结束后编辑任务层 Behavior Tree。VLCP 可在“training-free VLM code policy”中形成独立机制代表，但因只在仿真验证，不能用于说明真实机器人收益。
