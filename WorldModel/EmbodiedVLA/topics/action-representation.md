# 横切专题：动作表征三路线（token / flow matching / diffusion head）

> **定位**：`report.md` 第 2 章的机制级展开。回答一个可判定的问题：**"动作"在 VLA 里到底被表示成什么**，为什么同一主干会同时提供多条路线，以及每条路线的边界在哪。
> **本册的判据**：一条路线归属由**训练目标 + 推理形态**决定（不是由论文标题或机构决定），并尽量落到**代码事实**（固定 commit 的 `文件:行`）。
> **证据口径**：8 篇精读分册内的内容标 `[精读原文]`；代码读数标 `[代码事实]`（commit 见 §7）；未精读对象标 `[摘要级]`。

---

## 0. 本册结论

1. **三路线的分界不是"离散 vs 连续"这么简单**，而是**训练目标**不同：token = next-token 交叉熵（离散符号序列）｜flow matching = 线性插值目标的**速度场回归**｜diffusion head = 逐步去噪（DDPM 式噪声预测）。`[精读原文]` + `[代码事实]`
2. **同一主干可以两条路线并存**：π0 官方仓库同时给出 flow matching 头（`pi0`）与 FAST tokenizer 自回归头（`pi0_fast`）。说明"路线之争"在工程上首先是**延迟 / 精度 / 复用性**的取舍，而非互斥范式。`[代码事实]`
3. **token 路线的瓶颈是"token 数 × 频率"**：高频灵巧任务的 token 序列会迅速变长，因此**压缩型动作 tokenizer 是 token 路线能否用于高频任务的先决条件**。`[精读原文]`（FAST）
4. **flow matching 的关键工程选择是"步数压到很小"**：π0 用固定 **10 步**积分得到整个 action chunk；这决定了它的推理代价与延迟量级。`[精读原文]` + `[代码事实]`
5. **diffusion head 与 flow matching 同属连续动作生成**，差别在训练目标（去噪 vs 速度回归）与采样器（DDPM/DDIM/DPM-Solver vs Euler 积分）；Diffusion Policy 一脉的数据效率优势与"多步采样"代价是同一枚硬币两面。`[精读原文]`
6. **"哪条路线更好"在本轮没有共基准证据**：三方均由各自系统自报，且评测协议不同（见 [评测与数据集册](evaluation-and-datasets.md) §4）。因此本册只做**可判定差异对照**，不做优劣排序。

## 1. 三路线总览（可判定定义）

| 路线 | 动作空间 | 训练目标 | 推理形态 | 代表系统 | 等级 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| **token（离散 / 自回归）** | 离散 token 序列 | 与语言模型同源的 **next-token 交叉熵** | 自回归解码；token 数 ∝ 动作维 × 步数（压缩后减少） | RT-2、OpenVLA、π0-FAST | `[精读原文]` |
| **flow matching（连续）** | 连续 action chunk | **速度场回归**（噪声与目标线性插值） | 少数步数值积分（π0 默认 10 步） | π0、GR00T N1 的 System 1 | `[精读原文]` + `[代码事实]` |
| **diffusion head（连续）** | 连续 action chunk | **去噪目标**（DDPM 式噪声预测） | 多步迭代去噪（可用 DPM-Solver 等加速） | Diffusion Policy、RDT-1B | `[精读原文]` + `[代码事实]` |

### 1.1 判定规则（走通判据的三条问法）

- 动作是**离散符号**、由语言模型头**直接生成** → **token 路线**；
- 动作是**连续向量**、由回归"噪声→目标"的**向量场/速度场**得到 → **flow matching**；
- 动作是**连续向量**、由**逐步去噪**（DDPM/DDIM/DPM-Solver）得到 → **diffusion head**。

> **常见误判**：把"用了 transformer"当成路线依据；把"输出连续动作"当成 flow matching（Diffusion Policy 也输出连续动作）。**要看训练目标**。

## 2. token 路线

### 2.1 两个历史节点

- **RT-2（2023）**：把动作**写成文本 token**，与网络规模视觉-语言任务**联合微调**（co-fine-tuning），不新增 action 专用参数层——语言与动作任务**完全共享权重**。这是"动作即 token"的范式确立点。`[精读原文]`（[RT-2 分册](../papers/2307.15818-rt2.md)）
- **OpenVLA（2024）**：7B 开源主干 + **每动作维 256 bin** 的离散 token 化，把这条路线做成**可复现的基线**。`[精读原文]`（[OpenVLA 分册](../papers/2406.09246-openvla.md)）

### 2.2 关键超参（落数值）

| 系统 | 动作离散化 | 备注 |
| :-- | :-- | :-- |
| OpenVLA | 每维 **256 bin**（目标区间均匀分箱，取 bin 中心反离散化，再做 q01/q99 反归一化） | `[代码事实]`（§7 行号） |
| RT-2 | 动作表示为离散 bin 的**序号整数**，作为文本 token 与语言 token 同等对待 | `[精读原文]`；具体 bin 数见分册第 2 问 |

### 2.3 压缩型 tokenizer：把 token 路线从"高频不可用"救回来

- **问题**：逐维逐时刻分箱在**高频灵巧**数据上表现差（token 序列过长，自回归解码代价与误差累积都上升）。`[精读原文]`（FAST）
- **FAST 的做法**：频率域变换 + BPE（把动作 chunk 压成"学到的字"），使 token 数从"维 × 步"降到**每臂约 30 个 token**量级。`[精读原文]`
- **量化收益（带条件）**：压缩率依数据集而变（Bridge V2 / DROID / bussing / shirt-folding 各不相同），训练步数与 GPU 小时的下降也**逐任务不同**——**引用时必须带数据集条件**。数字见 [FAST 分册](../papers/2501.09747-fast.md) §4。
- **推论 `[推断]`**：token 路线的推理延迟随"token 数"增长，因此**压缩率就是延迟**；"要不要 FAST"在工程上等价于问"任务频率有多高、动作维有多少"。

## 3. flow matching 路线

### 3.1 训练目标（π0 形态）

- 采样噪声与真实动作的**线性插值**得到带噪动作，网络回归**速度场**；时间步从一个**偏向低时间步（高噪声）**的分布中采样——π0 用 `p(τ) = Beta((s−τ)/s; 1.5, 1)`，并取 `s = 0.999`（允许积分步长 δ > 1/1000，即至多 1000 步）。`[精读原文]`（[π0 分册](../papers/2410.24164-pi0.md) Appendix B）+ `[代码事实]`
- 推理是**固定步长积分**：官方代码默认 **10 步** Euler 积分，一次生成整个 action chunk（π0 用 `H = 50`）。`[精读原文]` + `[代码事实]`

### 3.2 关键超参速查

| 超参 | π0 取值 | 意义 |
| :-- | :-- | :-- |
| action chunk 长度 `H` | **50** | 一次推理执行多少步动作 |
| 积分步数 | **10** | 推理代价 ∝ 步数 |
| 时间采样分布 | `Beta((s−τ)/s; 1.5, 1)`，`s = 0.999` | 偏向高噪声时间步 |
| 推理间隔 | 20 Hz 本体：每 **0.8 s**（执行 16 步）；50 Hz 本体：每 **0.5 s**（执行 25 步） | 与**控制频率绑定** |
| 推理耗时 | on-board **73 ms**（RTX 4090） | 与本体/硬件绑定 |

> 上表全部可在 [π0 分册](../papers/2410.24164-pi0.md) 与原文 Appendix B/D 回溯。**引用任何一项都要带"哪个本体 / 什么频率 / 什么硬件"**。

### 3.3 GR00T N1 的 System 1 也是 flow matching

- GR00T N1 的动作专家是**扩散 transformer（DiT）**，走 flow matching 过程，且与视觉-语言模块（System 2）**联合端到端训练**。`[精读原文]`（分册在 `report.md` 第 8 章"未收录"说明中登记）
- **代码与论文的差异提醒**：官方仓库默认分支已演进出新代号（`gr00t_n1d7` 路径），**不要把新代码形态直接当作 N1 论文方法**；对齐论文应取发布 tag / 历史 commit。`[代码事实]`（`report.md` 代码核验表）

## 4. diffusion head 路线

### 4.1 训练目标与推理（Diffusion Policy 形态）

- 把 visuomotor policy 表述为**条件去噪扩散过程**（基于 DDPM）：推理从高斯噪声出发经 K 次去噪得到动作；训练目标是预测所加噪声（MSE）。`[精读原文]`（[Diffusion Policy 分册](../papers/2303.04137-diffusion-policy.md) §2）
- 作者给出**梯度场解释**：去噪迭代可重写为一步带噪梯度下降，噪声预测器近似**能量函数梯度场**——这是"为什么扩散适合多模态动作分布"的理论表述。`[精读原文]`

### 4.2 为什么连续动作生成对多模态重要

- 同一观测下可能存在**多个同样正确的动作模式**（例如抓一个方块有多种抓法），逐维平均会落在**两个模式之间**的不可行动作上。扩散/flow matching 通过"生成"而非"回归均值"规避这一点。`[精读原文]`（Diffusion Policy、RDT-1B 的动机章）
- **代价**：多步迭代去噪 → 推理延迟与步数正相关；加速手段（DDIM / DPM-Solver / 蒸馏）会引入各自的近似误差。`[精读原文]` + `[代码事实]`

### 4.3 代码事实：三个系统各自的扩散实现

| 系统 | 实现要点 | 证据 |
| :-- | :-- | :-- |
| LeRobot `DiffusionPolicy` | 1D UNet + DDPM/DDIM 调度器 | `[代码事实]`（§7） |
| RDT-1B | DDPM 训练 + **DPM-Solver** 多步采样 | `[代码事实]`（§7） |
| GR00T N1.7 动作头 | `AlternateVLDiT` / `DiT` + flow matching 扩散过程（torch 侧） | `[代码事实]`（§7） |

## 5. 三路线的可判定差异对照表

> **列之间不是排行榜**：每行只在"其自身条件下"成立。判断"哪条适合我"要回到最右列。

| 维度 | token | flow matching | diffusion head |
| :-- | :-- | :-- | :-- |
| 动作空间 | 离散符号 | 连续向量 | 连续向量 |
| 训练目标 | next-token 交叉熵 | 速度场回归（线性插值） | 噪声预测（去噪） |
| 推理 | 自回归，逐 token | 少量步积分（如 10 步） | 多步去噪（可加速） |
| 推理代价的驱动量 | **token 数**（∝ 动作维 × 频率 ÷ 压缩率） | **积分步数** | **去噪步数** |
| 与 LLM 生态复用 | **最好**（同词表、同解码器） | 需独立 action expert | 需独立动作头 |
| 高频灵巧任务 | 需要**压缩 tokenizer** 才可行 | 原生支持 chunk | 原生支持 chunk |
| 主要失效模式 | token 序列过长 → 慢与误差累积 | 步数太少 → 精度不足；步数太多 → 慢 | 同理，且多步采样稳定性依赖调度器 |
| 本专题代表 | RT-2、OpenVLA、π0-FAST | π0、GR00T N1 (S1) | Diffusion Policy、RDT-1B |
| 判断"适不适合我"的问题 | 动作维 × 频率 ÷ 压缩率是否可接受？ | 能不能接受固定 N 步积分的延迟？ | 能不能接受多步采样并用调度器加速？ |

### 5.1 一个被忽略的共同点

三条路线的**输入侧完全相同**：都是"视觉 + 语言指令条件化"。差异只在**动作头与训练目标**。`[精读原文]`（四篇分册的架构章）

> 这解释了为什么同一主干（预训练 VLM）能挂三种动作头——**判据 (a)(b) 相同，只在 (c) 的实现上分化**。

## 6. 什么条件下各路线失效（本册汇总）

| 路线 | 失效条件 | 证据 |
| :-- | :-- | :-- |
| token | 动作维高 + 控制频率高 + 未压缩 → token 序列超长，训练与推理都退化 | `[精读原文]`（FAST 的动机与对比） |
| token | 数据混合中含高频数据集时可能"学不会"（例如 OpenVLA 训练中 DROID 的 action token accuracy 持续偏低，末段被移除） | `[精读原文]`（OpenVLA §3.3 + Table 3 脚注） |
| flow matching | 积分步数被压得过低时精度下降；论文未给出"步数—成功率"完整曲线 → **不要假设 10 步是普适最优** | `[推断]`（基于代码默认值与消融缺失） |
| diffusion head | 采样步数多 → 延迟高；任务频率高时实时性受挑战 | `[精读原文]`（Diffusion Policy 的架构/消融章） |
| 三路线共同 | **无法跨系统比较"哪条更好"**：无共基准、协议不同 | 见 [评测与数据集册](evaluation-and-datasets.md) §4 |
