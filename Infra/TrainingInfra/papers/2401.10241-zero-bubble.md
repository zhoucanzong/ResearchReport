# Zero Bubble Pipeline Parallelism：把参数梯度移出关键路径

来源：[Zero Bubble Pipeline Parallelism](https://arxiv.org/html/2401.10241v1)，固定版本 v1。重点阅读 §1–3、§5–6，尤其 Figure 2–4、Table 2 与 §5.4。

## 问题不是“前后向不能并行”，而是反向被当作一个不可拆操作

标准反向要算两类梯度：对输入 `x` 的梯度决定误差能否继续传回前一层；对权重 `W` 的梯度用于优化器更新。通常框架把它们封在一个 backward 中，但流水线的依赖链主要等待输入梯度 `B`。权重梯度 `W` 在本 micro-batch 的 `B` 完成后已经可算，却不一定需要立即阻塞下一 stage 的 `B`。论文的核心设计是把二者拆开，优先保持 `F → B` 的跨 stage 顺序，再把 `W` 移到空闲槽位。

## 调度自由度从哪里来

```text
传统：F → (B + W) → 前一 stage 的 B
拆分：F → B → 前一 stage 的 B
             └─ W 在本 stage 之后的空闲槽位计算
```

这不是把权重梯度丢弃或延迟 optimizer step 到任意时刻。`W` 必须属于正确的 micro-batch，并在 optimizer update 前按约定累积；论文还处理 optimizer step 的同步边界，使其在同步训练语义下插入更新。Schedule 需要满足 micro-batch 的前后向依赖、stage 间发送/接收、梯度累计和参数更新同步。

作者给出 ZB-H1/H2 与 ZB-V 等手工构造，再提出输入具体 stage 数、micro-batch 数、activation memory limit、F/B/W 和通信时长的自动 scheduler。最优排程取决于 profile 到的 F、B、W 与通信延迟；若默认三者等时或忽略通信，自动化之前的固定公式可能会给出不适合目标模型的 schedule。[§2–3、Figure 3–4](https://arxiv.org/html/2401.10241v1#S2)

## 空泡与激活内存不能分开优化

`B` 使用并释放一部分激活，`W` 仍需要保留权重梯度所需的较小状态。论文显示，同样的 B/W 拆分可以构造出不同 schedule：一种以较低 activation memory 换少量 bubble，另一种追求近零泡但要保留更多微批激活。Figure 2–4 和 Table 2 对照了这些时间表及 activation footprint；其理想分析从 F/B/W 相等的简化出发，§3/§5 再引入真实时长、通信和 memory limit。

原文报告在其 Megatron-LM 衍生实现中，模型规模约 6.2B、14.6B、28.3B，采用 16、24、32 个 GPU 的设置，对比 1F1B、ZB-1P、ZB-2P 与 ZB-V；Table 6 为公平对齐全局 batch 和显存而调整 micro-batch 数。摘要中“最多提升 23%（相似内存）/31%（放宽内存）”是作者的最高结果总结，不适用于任意模型、设备、网络或不同 memory limit。[§5.1–5.4、Table 6](https://arxiv.org/html/2401.10241v1#S5)

## 与 1F1B 和 DualPipe 的关系

1F1B 用 warm-up 填充流水线，稳态前向/反向交替，cool-down 排空。Zero Bubble 改变 backward 的计算粒度，但仍遵守同步 micro-batch 训练；它不是 PipeDream 那种靠接受参数陈旧度消除同步等待的异步流水线。DeepSeek-V3 的 DualPipe 也拆 B/W，却把 dispatch/combine all-to-all 作为同一时间表中的通信任务，并双向送入 micro-batches。Zero Bubble 的贡献是更一般的 B/W 调度自由度；DualPipe 的设计目标还包括隐藏 MoE 跨节点通信。

## 开放边界

- F/B/W 时长不平衡、activation limit、micro-batch 数和通信时延都会改变可行且高效的排程。
- 调度将 `W` 延后会影响梯度/optimizer 的同步安排；要按论文和框架实现的更新顺序核对，不能仅根据时间线推断“完全无同步”。
- 论文实验是特定 GPU、模型规模和 parallelism 配置，不支持通用吞吐加速承诺；本专题未运行训练或性能测试。
