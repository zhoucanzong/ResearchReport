# PyTorch FSDP：参数分片如何变成可执行的训练流程

> **固定原文**：[arXiv HTML v2](https://arxiv.org/html/2304.11277v2)，*PyTorch FSDP: Experiences on Scaling Fully Sharded Data Parallel*，PVLDB 16(12), 2023。本文精读 §2.3、§3.2–§3.4、§4.2–§4.3、§5.4 与 §7.1–§7.2。它解释的是以 FlatParameter 为中心的 FSDP 系统设计（通常对应 FSDP1 的主要实现思路），不是 FSDP2 的实现说明；FSDP2 的实际生命周期见[主报告 §4.6](../report.md#46-fsdp2用-dtensor-表示分片用模块边界安排通信)。

## 1. 论文要解决的不是“如何把权重切开”

参数分片后，单个 rank 不再持有完整模型，所以不能照常执行每一层。论文把恢复正确计算的办法分成两类：让各 rank 用参数碎片计算并在层间交换激活，或在需要计算前临时收集完整参数。FSDP 选择第二条路：按执行单元收集当前层组的参数，完成计算后释放它们。这样计算仍像本地模型一样作用于完整参数，通信则有机会和前后计算重叠；限制是每个被执行的单元仍必须能在单卡上物化。[§2.3、§3](https://arxiv.org/html/2304.11277v2#S2.SS3)

这解释了 FSDP 与 TP 的分工：FSDP 把**保存状态**切开，计算时暂时聚合；TP 把**计算本身**切开，使层内矩阵运算直接使用参数切片。FSDP 能省下数据并行 rank 间的完整副本，却不会让过大的单层权重无需完整物化；遇到单层放不下时，通常需要 TP 等计算切分方法。

## 2. 一个 FSDP 单元的完整生命周期

假设 Transformer 按层切成若干 FSDP 单元，每个 rank 平时只保存每单元的参数分片、梯度分片和优化器状态分片：

1. **前向之前**：从参与 rank 收集当前单元的参数，恢复完整参数。
2. **前向计算**：模块像普通本地模块一样使用完整参数。
3. **前向之后**：释放其它 rank 的参数副本，保留本地分片，以控制显存。
4. **反向之前**：若前向后已重分片，再次收集参数；随后计算局部梯度。
5. **反向之后**：reduce-scatter 将梯度求和并切回各 rank；优化器在本地分片上更新参数和状态。

因此，参数组是内存和通信的共同单位。论文给出的参数峰值模型可直观写作“常驻分片总量 + 当前最大完整参数组”；组越小，临时物化的峰值越低，但每步 collective 越多。组越大，通信调用更少且缓冲更易填满，却需要更多完整参数同时驻留。论文建议组边界大致贴合层或执行单元顺序，而不是任意按字节数切块。[§3、§4.2](https://arxiv.org/html/2304.11277v2#S3)

## 3. 为什么 FSDP1 发明 FlatParameter

若为每个原始权重分别发 all-gather，消息会很小、调用次数多；而 NCCL 等集合通信更适合尺寸均匀的大缓冲区。FSDP1 因而把一个单元中的原始参数展平后拼接成一个 `FlatParameter`，必要时末尾补齐，再把平坦向量均匀分给 ranks。反向的梯度也遵循同一布局，所以可以对一大块缓冲做 reduce-scatter。其目的不只是抽象简化，更是把参数组织成集合通信能高效处理的形状。[§3.2.1、§4.2](https://arxiv.org/html/2304.11277v2#S3.SS2.SSS1)

但这个实现优化也带来表达代价：分片边界由拼接后的扁平布局决定，某个 rank 上原参数可能只剩一段、没有元素，或与其它参数共享同一平坦状态。论文指出，依赖原参数整体向量范数、张量形状或全局参数状态的优化器操作，可能无法与此布局保持和单机训练相同的数学语义。也就是说，FSDP 对常规逐元素优化器很自然，但不是所有“作用于参数”的算法都能在不加通信或改变切分方式时自动等价。[§7.2.1](https://arxiv.org/html/2304.11277v2#S7.SS2.SSS1)

FSDP2 的一个重要变化是逐参数用 `DTensor` 表示分片而不把参数存储全部塞入一个 FlatParameter；它保留了更清楚的参数级布局信息。但为了减少通信调用，FSDP2 仍需要把多个参数按模块边界分成通信组。因此，FSDP1 的“每组扁平张量”实现约束变弱了，组大小的内存—通信取舍仍然存在。还要注意论文 §4.2 中的 `fully_shard` 是当时围绕 FlatParameter 的 FSDP 接口；它与今天以逐参数 DTensor 为基础的 FSDP2 `fully_shard` 同名但不是同一实现。[主报告 §4.6](../report.md#46-fsdp2用-dtensor-表示分片用模块边界安排通信)

## 4. 通信重叠不是自动发生的

FSDP 的前向 all-gather 通常发生在当前单元之前。若直接把它排在正在执行的计算流之后，通信会等待这段计算结束，失去重叠机会。论文通过单独的 CUDA stream 启动参数 all-gather；反向阶段则依据模块实际前向顺序反向预取下一组参数，避免当前梯度 reduce-scatter 阻塞下一单元的参数聚合。若计算图跨迭代稳定，还可用前向预取提前发起下一组聚合。[§3.3.1–§3.3.3](https://arxiv.org/html/2304.11277v2#S3.SS3)

这条路径还受 PyTorch CUDA caching allocator 影响。CPU 若过快发出多个 all-gather，生产流上尚未被消费的缓冲区可能无法及时复用；allocator 可能为不同 stream 保留额外块，最终触发同步式的内存分配重试。论文的 rate limiter 限制同时在途的 all-gather 数量，减少这类碎片与暂存压力，但它本身会节流通信，因此只有在目标负载确实出现此类分配问题时才可能有益。论文的模型实验里它对不同网络呈现不同影响，并非可无条件开启的加速开关。[§3.4、§5.3](https://arxiv.org/html/2304.11277v2#S3.SS4)

## 5. 论文结果说明了什么，又没有说明什么

论文报告其大模型实验在特定集群和设置下可以扩展 FSDP 训练；更有教学价值的是其中的边界观察：在 T5-11B、序列长度 512、BF16/Adam 配置下，将规模从 8 扩展至 512 GPU 时，作者报告每 GPU TFLOPS 下降约 7%。作者将其解释为大规模训练时通信开始超过可重叠范围。该数字只描述论文的 T5/硬件/并行配置，不能直接外推到 FSDP2、其他网络拓扑或模型结构。[§5.4、Figure 7(c)](https://arxiv.org/html/2304.11277v2#S5.SS4)

还要留意两项论文自身说明的边界：

- **流水线并行**：一个 pipeline stage 在多个 micro-batch 间重复前向；完全分片时可能为每个 micro-batch 重复聚合该 stage 的参数。保留前向后的完整参数能减通信，却要让整个 stage 参数常驻显存。[§7.1.1](https://arxiv.org/html/2304.11277v2#S7.SS1.SSS1)
- **共享参数**：同一参数跨多个单元使用时，必须保证所有使用点执行时它仍处于完整状态；让参数归属更高层单元可避免提前重分片，却可能延长其完整驻留时间。[§7.2.2](https://arxiv.org/html/2304.11277v2#S7.SS2.SSS2)

这些是 FSDP 的执行单元和生命周期问题，不只是 API 配置问题。FSDP2 将参数身份和布局改成 DTensor、让模块本身保留在原结构中；但当前模块如何分组、何时 reshard、多少组在途以及故障时如何恢复状态，仍决定峰值内存与暴露在关键路径上的通信。固定 PyTorch v2.14.0 的源码证据见[主报告 §4.6](../report.md#46-fsdp2用-dtensor-表示分片用模块边界安排通信)。
