# Pipeline Parallelism with Controllable Memory：从 building block 看激活生命周期

来源：[Pipeline Parallelism with Controllable Memory](https://arxiv.org/html/2405.15362v4)，固定版本 v4。重点阅读 §2–4、Appendix E 与 I。本文并非提出单一调度，而是提供比较 pipeline schedules 的共同视角。

## 为什么只比较 bubble ratio 不够

流水线的 bubble 率通常描述一个时间表中有多少计算槽空着，却不直接回答：一个 micro-batch 的激活在设备上活多久、多少份同时保留、能否放进目标显存。作者把 schedule 写成可重复的 building block，再把该 block 中 forward/backward 操作的相对顺序与重复周期联系到峰值 activation memory。读者因此可以把 GPipe、1F1B、交错 1F1B 和 zero-bubble schedules 放到一套结构里比较，而不是只按名字做列表。

## Building block、寿命和 V-shape 调度

时间表从一组 micro-batch 的计算片段开始，再把 building block 重复并交错；随后可压缩不必要的空档，最后在 warm-up/cool-down 有空余时重排操作。核心变量是操作之间的偏移和 block 重复周期：activation 保留到对应 backward 才能释放，缩短生命周期可减少峰值；偏移不合依赖关系会造成碰撞，重复周期过长又会留下稳定态空泡。

V-shape schedule 将计算分段在不同设备上以 V 形走向，使高激活占用的阶段分布更平衡。论文的 V-Min、V-Half 和 V-ZB 在激活内存、bubble 和 stage 间通信之间各有取舍；不是单纯让每个 stage 工作量相等。其结论依赖作者采用的模型切分、profile 时间和设备分配。

## 交错 1F1B：虚拟 stage 降泡，但增加交接

交错 1F1B 让同一物理设备包含多个 virtual stages，逻辑 stage 数因此大于设备数；schedule 在这些虚拟段间交替，减少设备粒度流水线的 fill/drain 空档。代价包括更多 stage 间 activation/gradient 交接、更复杂的调度和额外的活跃激活。该论文把 Interleaved 1F1B 放在 memory-throughput Pareto 比较中，并指出不同 micro-batch / 显存设置会使部分方法 OOM 或需要更小 micro-batch；所以不能把不同配置下的最大吞吐直接当作同预算的 schedule 排名。[§4.1–4.3、Figure 7](https://arxiv.org/html/2405.15362v4#S4)

## 如何使用论文结果

摘要报告的激活内存与 1F1B 相比可降至其渐近一半或三分之一，分别对应不同 throughput 取舍；纯 pipeline 设置和 hybrid parallelism grid search 的吞吐改进也属于论文选定的模型、GPU、stage/micro-batch 与并行超参。更适合学习的结论是：**schedule 选择是受显存上限约束的排程问题**，而非只追求 bubble rate；论文数字需按对应设置阅读，不应外推成通用加速比。

论文也报告其 V-shape 方法相较 1F1B 几乎是以额外 stage 间通信换取更低激活内存/更少泡；这项通信在作者实验设定里较小，但跨机网络或通信敏感 workload 可能改变代价。[§4.4、Appendix D.4](https://arxiv.org/html/2405.15362v4#S4)

## 与 FSDP、TP 和 Zero Bubble 的关系

这项工作只改变 PP 的时序与 activation 生命周期。它不负责参数状态分片，也不改变 TP 的层内计算；与 FSDP/ZeRO/TP 组合后，每个阶段的 F/B/W/通信耗时和 memory budget 都会变化，最优 block 必须重新规划。Zero Bubble 将 backward 拆成 B/W 增加排程操作类型，本文的 building-block 视角则提供在不同显存预算下安排这些任务的框架；组合时仍需具体拓扑、profile 和 schedule 证明可执行。[Appendix D.4、E、I](https://arxiv.org/html/2405.15362v4)

本精读只覆盖作者提出的 building-block 视角、代表 schedules 与相应实验边界；没有对 Megatron、PyTorch 或其它框架做实现复核，也没有运行训练性能测试。
