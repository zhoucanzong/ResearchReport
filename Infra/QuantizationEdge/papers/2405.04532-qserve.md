# QServe：W4A8KV4 为什么需要协同设计

**原文**：[QServe: W4A8KV4 Quantization and System Co-design for Efficient LLM Serving](https://arxiv.org/abs/2405.04532v3)，arXiv v3（2025-05-01，MLSys 2025）。重点位置：§3、§4、§5.1–§5.3、§6。完整 HTML 原文：[arxiv.org/html/2405.04532v3](https://arxiv.org/html/2405.04532v3)。

## 论文挑战了“位数越低，速度越快”的直觉

权重变成 4-bit 会减少显存读取，但如果每个 GEMM 主循环都要把权重或 partial sum 转成更高精度，再交给矩阵乘单元，解量化可能落在吞吐较低的 CUDA core 上。KV cache 的 4-bit 也只有在 attention 能边读边解码、避免物化完整高精度 cache 时才可能减少访存。因此，QServe 的问题不是只找一个准确的 4-bit quantizer，而是问：精度、数据布局和 GPU 指令流能否构成匹配的 serving 系统？[§3.1–§3.2](https://arxiv.org/html/2405.04532v3#S3)

## QoQ 与 QServe 的分工

QoQ 是量化算法，采用 W4A8KV4：4-bit 权重、8-bit 激活和 4-bit KV cache。其 progressive quantization 与保护范围用于减少 W4A8 矩阵乘主循环中的反量化开销；SmoothAttention 对 Key cache 的离群通道做尺度变换，缓解 KV4 对注意力分数的影响。[§4.1–§4.2](https://arxiv.org/html/2405.04532v3#S4)

QServe 是执行系统：权重重排适配计算布局，寄存器级并行隐藏 scale / dequant 操作，fused attention 把 KV4 的访存节省变成实际执行效率。论文特别指出，W4A4 虽有更高理论 Tensor Core 峰值，但在其 Ampere/Hopper 数据流里，主循环中的 CUDA core 转换成本和精度损失会吞掉收益。结论是格式与 kernel 的组合决定速度，不是“W4A4 总比 W4A8 快”。[§5.1–§5.3](https://arxiv.org/html/2405.04532v3#S5)

## 如何读性能数字

论文报告 Llama-3-8B、Qwen1.5-72B 在 A100 / L40S 上相对 TensorRT-LLM 的 serving 吞吐结果，并给出精度选择、batch 和负载条件；这些数据属于论文的模型、GPU、引擎版本和调参协议。[§6.1–§6.4](https://arxiv.org/html/2405.04532v3#S6) 不能从某个最大吞吐点推出每个服务请求都更快，也不应把论文中特定 GPU 的成本比较当作普遍部署排序。

## 阅读所得

QServe 说明量化算法表中的“bit-width”不是性能结论。理解推理收益需要沿着完整路径追问：权重压缩减少了多少读取？scale、打包、部分和在什么单元中处理？是否进入主循环？KV cache 有没有在 attention 中融合解码？评测负载是否是相同的 prompt/output 长度和并发？这使它与 [ServingEvaluation](../../ServingEvaluation/report.md) 的 SLO/负载口径形成直接连接。
