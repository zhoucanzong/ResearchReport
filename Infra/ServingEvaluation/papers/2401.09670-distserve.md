# DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving

Zhong et al., OSDI 2024; arXiv:2401.09670v3. [官方原文 HTML](https://arxiv.org/html/2401.09670v3) · [OSDI 页面](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin)

**阅读范围**：精读 §2–§4、§6.1–§6.4 及 Appendix C；关注 TTFT/TPOT 约束如何进入资源配置、到达负载和 SLO attainment 的实验条件。未运行作者代码或复现论文实验。

## 从 SLO 目标推回资源分配

Prefill 一次处理整段输入，偏计算密集；decode 每步生成一个 token，更多受权重/KV 访存限制。把两者混在同一批次，可让长 prefill step 推迟已进入 decode 的请求，损害 TPOT；反过来， decode 作业也会占用 prefill 资源，增加 TTFT。传统系统往往以总吞吐调并行度，难以同时满足不同应用的首 token 与生成节奏要求。

DistServe 分开部署两阶段，针对 TTFT 和 TPOT 分别搜索 GPU 数与并行方案，再按集群带宽选择 P/D 放置，使 KV 传输成本也进入配置选择。在线阶段由 controller 根据队列负载分配请求。它体现一个关键研究关系：架构变更应按“在给定交互 SLO 下完成多少请求、耗用多少 GPU”评价，而非只看总 token/s 或单项 kernel 延迟。

## 论文如何定义并测量容量

论文在 ShareGPT 聊天、HumanEval 代码补全和 LongBench 摘要任务上构造工作负载，并按 Poisson 过程生成到达时刻。每类任务配置各自 TTFT 和 TPOT 门槛；capacity 曲线逐步提高请求率，查看能否保持 90% 请求同时满足 SLO，附录还给出 99% attainment 结果。per-GPU goodput 即达到目标请求率与门槛时的系统容量指标。

测试集群为 4 个节点、32 张 NVIDIA A100-80GB，节点内 NVLink，跨节点 25 Gbps；模型是 FP16 OPT 13B、66B、175B。作者报告 DistServe 相对基线最高可承载 7.4 倍请求率，或满足更严格 12.6 倍 SLO；这两个 headline 的比较条件对应不同工作负载/曲线，不应合并为一个同时成立的普遍速度因子。对 OPT-175B ShareGPT 的延迟分解中，KV 传输不到总请求延迟 0.1%，而超过 95% 请求的传输延迟低于 30 ms；这依赖其层级放置策略、NVLink 路径和测试集群，不能推到任意网络拓扑。

## 能从结果推出什么，仍缺什么

论文支持：在其特定 workload 和硬件条件下，prefill/decode 干扰与资源配置耦合会限制同时满足 TTFT/TPOT 的容量；分离和联合放置搜索能够改变满足门槛时的请求率。模拟器在给定 real-system 的 arrival rates 上和 attainment 相差不到 2%，是该任务/设备上的校准结果，不是所有未来配置的模拟误差界。

论文使用“超过阈值的请求占比”做 SLO attainment，但没有把 HTTP admission rejection、服务端失败、客户端取消、中途输出后放弃以及取消后资源回收时延作为主要分类问题。它因此适合精读 SLO 驱动资源配置，不足以独立回答失败请求该如何归入服务分母、socket 断开后 KV 何时可复用。此处应与引擎的固定版本生命周期证据及更完整的负载账本结合。
