# Revisiting Service Level Objectives and System Level Metrics in Large Language Model Serving

Wang et al., arXiv:2410.14257v2 (2025-10-29). [官方原文 HTML](https://arxiv.org/html/2410.14257v2) · [arXiv 版本记录](https://arxiv.org/abs/2410.14257)

**阅读范围**：精读 §2–§5、§6.1–§6.2；重点核对 SLO 定义、goodput 公式、实验配置、输出延迟反例与 smooth-goodput 参数。本文讨论度量问题，并非 LLM 引擎的实现源码审计。

## 这篇论文追问什么

在线推理系统常用首 token 延迟、相邻 token 时间（TBT）、平均每输出 token 时间（TPOT）、SLO attainment 和 goodput 来描述体验与容量。论文不只问这些量能否测量，而是问：系统能否通过“优化指标本身”反而让用户体验更差？作者给出两个答案：缓冲 token 可让 TBT 看起来更平滑，却没有减少用户真正等待；主动终止已经不满足 SLO 的请求，可能改善只奖励合格请求的系统指标，却把用户留在半截答案上。

## 把每个 token 放回用户等待时间线

论文把每个输出 token 的生成时刻记为 $t_i$，并给它一个截止时刻 $d_i$；满足 SLO 要求所有 token 都不晚于各自 deadline。常见指标可看成不同的 deadline 规则：

- TTFT/TBT：首 token 有独立的首包期限，之后每个 token 的期限相对前一个 token；这会让一个 token 的人为延迟放宽后续 token 的窗口。
- TTFT/TPOT：首 token 有期限，最后一个 token 受首 token 加输出长度乘平均 TPOT 的期限约束；中间 token 可以出现较大间隔而不改变这个均值约束。
- 端到端：只检查整条请求完成时间，忽略输出流中的停顿位置。

作者改以相对开始时刻的阅读进度安排 token deadline，并用请求中最大的“超过 deadline”时间近似用户无内容可读的 idle latency。smooth goodput 把输出 token 数与 idle-time 惩罚组合后按时间聚合。机制的价值在于保留部分不达标请求的贡献，避免二元 SLO 把已生成内容记作零；它的代价是引入用户信息处理速度和惩罚权重，需按场景校准。

## 反例为何重要

在 TBT 规则下，若服务端延迟释放已生成 token，下一 token 到达时相邻间隔变短，传统 TBT 会改善，但用户只是在更晚看到相同内容。相反，如果过载时将某请求判定为无法满足 SLO 后直接丢弃，该请求的 goodput 贡献仍为零，而将资源留给新请求可能抬高完成的合格速率。论文提醒：只有计量“好请求”而不显示被舍弃的请求，会把请求完成率、服务质量和资源代价压成一个不完整的数字。

## 实验能支持到哪里

作者在单张 NVIDIA A100-SXM4-80GB 上，以 vLLM 0.6.3 运行 LLaMA-3.1-8B-Instruct 和 Qwen2.5-14B；输入来自 ShareGPT 和较长对话 LooGLE，请求按 Poisson 到达或真实 trace 回放。论文把用户信息处理速度设为 5 tokens/s、惩罚参数 $\alpha=2.5$ 的一组实验，观察 smooth goodput 会随负载先升后降；启用 chunked prefill 的配置在其设置中能把峰值推到更高负载点。输出延迟反例显示传统 tail-TBT 改善时，idle latency 并没有同步下降。

这些结果说明评价口径能改变策略排序和容量峰值解释；不证明 5 tokens/s 或 $\alpha=2.5$ 适用于所有语言、阅读模式或产品，也不把单卡 vLLM 结果推广成当前多卡服务结论。论文未给出统一的 HTTP 错误、服务端超时、客户端取消和资源回收结果分类账；真实 deadline 和失败请求分母仍需由基准协议单独规定。

## 与本专题其他工作的关系

该文给出“优化目标可能奖励什么行为”的诊断；[DistServe](2401.09670-distserve.md) 展示固定 SLO 与目标 attainment 如何影响阶段资源配置。两者互补：前者质疑服务质量指标，后者以指标驱动系统容量优化。若指标定义本身遗漏用户等待或中途失败，优化器越精确地优化该指标也未必让真实服务更好。
