# Traversal Verification：先比较整条候选路径，再决定接受哪一段

> 原文：Weng et al., [*Traversal Verification for Speculative Tree Decoding*](https://arxiv.org/abs/2505.12398v2)，arXiv v2，2025-11-05，NeurIPS 2025。重点阅读 §§2–4、Algorithm 3、Theorems 3.3–3.4、Tables 2–4、Appendix G。以下结果均为论文作者报告，未独立复现。

## 它改变的是验证顺序和接受粒度

树草稿让 target 一次为多个候选节点计算 logits，但“这些 logits 已经算出来”不代表它们都能提交。常见树验证从根向叶逐 token 检查：若根节点不匹配，就丢掉这一分支的所有后代，即使某个后代在另一条已验证历史下仍可能成为有用候选。另一个问题是逐 token 接受只看局部条件概率，没有直接用整条候选路径的联合概率。

Traversal Verification 不换草稿模型，也不改变已有树的形状。它把问题改成：**在这棵已经评分的树里，哪条路径作为整体最有机会被 target 接受？** 验证按叶子路径展开，先检查较深的完整序列；若被拒，就删除最后节点、在对应父前缀处更新 residual 和剩余 draft 分布，再测试仍存活的路径。这样，一条路径的父节点被拒，并不会机械地同时抛弃所有兄弟分支。[§3.1、Algorithm 3、Fig. 2]

## 机制：把路径接受率作为一个整体

对一条候选链 α=(x_0,…,x_γ)，论文先逐位置递推该链的累计接受概率：

\[
p_\alpha(x_i)=\min\left(p_\alpha(x_{i-1})\frac{p_{\text{target}}(x_i\mid x_{<i})}{q_{\text{draft}}(x_i\mid x_{<i})},1\right),\qquad p_\alpha(x_0)=1.
\]

实现时选择树中一条从根到叶的候选链，按这条完整路径的接受率做一次随机判定。若接受，整条链可提交；若拒绝，则修正其末端父前缀下的 target residual distribution，并把已拒 token 从对应 draft support 中移除，再对其余链更新累计概率。所有候选都耗尽后，才从 root 的 residual 分布生成回退 token。[§3.1、Eqs. 1–3、Algorithm 3]

这不是“无条件选联合概率最大的叶子”。遍历过程仍包含采样和残差修正，其目标是既提高整段序列被接受的机会，又严格补回 target 概率质量。论文利用递归子树的自相似性归纳证明输出分布等于 target；另外，在树退化成单链时，Traversal 的期望接受长度等于 Block Verification，并达到论文定义下任意有效链验证器的上界。[§3.3、Theorems 3.3–3.4、Appendix A]

## 保证的前提，以及它不解决什么

无损性针对**由同一 draft 条件分布按自回归规则采样出的有效树**，并要求 verifier 使用每个节点对应的 draft / target conditional probabilities 做接受与 residual 更新。改变候选生成分布、去掉概率质量、或缓存提交路径不一致，都不能直接套用定理。这里的“序列级”表示验证单位和接受概率按路径联合条件构造；它不是另一个比“分布严格等价”更高的正确性等级。

一个关键边界是 **Traversal 的收益属于有随机性的采样验证**。论文在 Limitations 中明确指出，temperature=0 时没有随机采样，现有 greedy 验证器功能等价，因此该方法不带来接受长度收益。温度越低，论文观察到与 token-level 的差距越小；这与“序列概率考虑得更完整”并不矛盾：分布越尖，单链局部接受已经更容易接近最终路径。[§4.4、Table 4、§G Limitations]

另一个取舍是计算成本。它要反复处理树路径和概率分布，接受长度增益不会一比一变成 wall-clock 吞吐。作者在一张 RTX A6000、PyTorch 后端上做三次独立运行，并报告 throughput 增幅通常小于 acceptance-length 增幅；更大树理论上可能扩大收益，也会增加遍历开销。[§4.1–4.3、Tables 2–3]

## 论文报告的结果如何读

| 设置 | 作者报告 | 适用边界 |
|---|---|---|
| Llama3.2-1B-Instruct draft + Llama3.1-8B-Instruct target，Spec-Bench 六类任务；chain、binary tree 深度 5 | T=1 时平均 acceptance length：chain +2.8%、binary tree +2.2%、EAGLE sparse tree +2.4%；对应平均 tokens/s：+2.5%、+1.7%、+2.1%。[Table 2] | 单张 RTX A6000、PyTorch，EAGLE 树结构与 token-level baseline 固定；接受长度改善不是纯粹的算子加速。 |
| Llama-68M draft + Llama2-7B target，同类 Spec-Bench 设置 | T=1 时平均 acceptance length：chain +5.7%、binary tree +4.9%、EAGLE sparse tree +3.8%；tokens/s 分别 +4.8%、+3.7%、+3.0%。[Table 3] | 不同模型容量差和树结构改变了收益；不能从此推断所有 target/draft 组合都在同一范围。 |
| Llama3.2-1B / Llama3.1-8B，链、binary tree 与 EAGLE tree 深度 5，temperature 0.2–1.0 | acceptance-length 相对提升随温度增加而扩大：低温约 1.0–1.5%，T=1 时约 2.2–2.8%。[Table 4] | 支持其主要收益来自随机树路径的序列级接受；论文不支持把该收益外推到 greedy T=0。 |

这些是作者报告在对应任务和运行栈上的结果，不是独立 kernel 基准。报告时应将三种量分开：树中可接受路径的平均长度、target 前向数、以及扣除 verifier 遍历开销后的 wall-clock throughput。

## 放回树验证研究路线

| 研究问题 | 代表工作 | 两者的分工 |
|---|---|---|
| 候选树如何生成和存储，如何在一次 target 前向中验证？ | [SpecInfer](2305.09781-specinfer.md) | 多路 SSM 候选、树形 KV 与 topology-aware mask 建立了树验证的系统基础。 |
| 在给定预算下，哪种树形更适合模型和硬件？ | [Sequoia](2402.12374-sequoia.md) | 动态规划优化拓扑，并加入面向温度的鲁棒采样/验证和硬件成本选择。 |
| 评分已完成后，按什么顺序和粒度检查分支？ | Traversal Verification | 叶到根遍历与整条路径接受，复用已有 tree logits；不负责建树。 |
| 多路径上的剩余概率质量如何精确回补？ | [HSD](2601.05724-hsd.md)、[RheoSampling](2609.21827-rheosampling.md) | 分别研究分层 excess/deficit 平衡，以及动态树上的 proxy / target 概率职责分离。 |
| 什么情况下明确接受偏离 target greedy 的候选？ | [Approximate Speculative Decoding](2608.03447-approximate-sd.md) | 以 regret、block cap 和 request budget 控制近似；不具备 Traversal 的严格分布保证。 |

因此，“树验证”不是一个单独 kernel 的名字：树拓扑决定 target 一次前向要容纳哪些节点；mask / KV layout 决定怎么算；遍历与接受规则决定能提交什么；剩余质量修正决定能否证明输出分布不变。

## 阅读路径

1. 先读 §2.2 的 Recursive Rejection Sampling，确认树节点的候选与回退分布来自哪里。
2. 读 §3.1、Algorithm 3 与 Fig. 2，跟踪一次叶路径拒绝后 sibling 如何保留。
3. 读 §3.3、Theorems 3.3–3.4，区分树级分布等价与单链最优性两个结论。
4. 读 §4.1–4.4 与 §G，查看树深、温度、RTX A6000/PyTorch 及遍历开销边界。
