# SpecInfer：token tree 验证与多步投机采样（Miao et al., 2023–2024）

> **一手来源**：arXiv:2305.09781 **v4**（2024-04-01），正文 HTML 逐节读取；license = **CC BY 4.0**。｜ **主等级**：`[精读原文]`
> **一句话定位**：把“多个 SSM 的多条草稿”合并成一棵 **token tree**，用 target 的**一次树形并行解码**验证整棵树——这是“树验证”成为投机解码公共基础设施的起点。
> **亮点与差异四行**
> - **一句话亮点**：不要求单个 draft 序列足够准；用**树的覆盖率**弥补单个 SSM 与 target 的容量差（SSM 比 LLM 小 **100–1000×**）。
> - **新在哪**：① **expansion-based**（单 SSM 内多分支）与 **merge-based**（多 SSM 间合并）两种建树；② **multi-step speculative sampling**：在不破坏分布等价的前提下，让 SSM 一次产出可验证的多步 token；③ 树形 KV cache + topology-aware causal mask，把整棵树塞进**一次** target 前向。
> - **证据强度**：强（系统论文）。LLaMA-7B / OPT-13B / OPT-30B / LLaMA-65B，SSM 用 LLaMA-68M / OPT-125M；单机多卡、多机多卡、单卡 offloading 三种部署；有树宽、batch、树 vs 序列的消融；**输出序列与增量解码逐 token 相同**。
> - **值不值得引用**：**值得作为“树验证/多 SSM”的系统基线引用**；引用加速比必须说明是 distributed 还是 offloading、batch 多大、树宽多少。

## 1. 问题：单个 SSM 的“容量差”无法靠训练消除

论文的出发点（§1、§3）：

- SSM（small speculative model）通常比 LLM 小 **100–1000×**；这个容量差是**固有的**，不是训练技巧能完全消除的。
- 序列式投机只让一个 SSM 产出一条草稿链；一旦这条链偏离 target，整条被拒，验证算力白花。
- 但 target 的一次前向**可以并行验证多个 token**——只要这些 token 组织得好。

SpecInfer 的判断：**不要追求“一条很准的草稿”，而要追求“一棵覆盖 target 可能输出的树”**。树越宽，命中 target 实际路径的概率越高；代价是验证 token 数增加。

## 2. 方法：树从哪来、怎么验证、怎么采样

### 2.1 两种建树（§3.2）

| 方式 | 做法 | 利用的多样性 |
| :-- | :-- | :-- |
| **Expansion-based** | 单个 SSM 在每个位置保留 top-k 分支，逐层展开 | **单模型内**的候选多样性 |
| **Merge-based** | 多个 SSM 各自出草稿，把它们的候选合并成一棵树 | **跨模型**的多样性（不同蒸馏/量化/剪枝变体） |

- 树节点 = 一个候选 token 序列；根 = 当前已生成前缀。
- 树不是越宽越好：树宽 `w` 决定验证 token 数；论文把它作为核心超参扫描（§6.6）。

### 2.2 树形 KV cache 与 topology-aware mask（§4）

- 普通 KV cache 按序列位置索引；树有多个分支，同一层不同分支共享前缀但不共享后缀。
- SpecInfer 用**树拓扑**存 KV：每个节点只保留“根到它”的路径；attention 时用 **topology-aware causal mask**，让每个 token 只能看见自己的祖先。
- 效果：整棵树在**一次** target 前向里验证；同一前缀的 KV 只算一次，避免序列式验证的重复计算。

### 2.3 Multi-step speculative sampling（§3.3）

- 经典投机采样要求草稿来自某个已知分布 `q`；树里多条路径的 `q` 不同，逐条算很贵。
- MSS 的做法：让 SSM 一次产出**多步**候选，并设计一种采样/验证流程，使得**最终输出分布仍等价于 target**；证明在附录。
- 这是“树 + 采样”能同时成立的关键；没有 MSS，树验证只能安全地用于贪心。

### 2.3.1 为什么树验证能保持无损（证明思路）

树验证的无损性不是“显然”的：一棵树上有多个分支，每个分支的草稿分布不同。SpecInfer 的证明把“从树里选一条路径”看成一次**分层采样**：

1. 从根开始，对每个候选子节点用其草稿概率 `q` 与 target 概率 `p` 做标准接受/拒绝；
2. 若某个节点被拒，就在该节点的**残差分布** `norm(max(0, p−q))` 上重采样，后续路径作废；
3. 因为每一步的接受/拒绝都满足“输出边缘分布 = p”，整条路径的输出分布仍是 target 分布。

树的作用只是**并行地尝试多条路径**，不改变每一步的接受规则；MSS 则保证“草稿 q”在多步/多分支下仍可计算。理解了这一点，就能理解后面 EAGLE/Medusa 的树验证为什么可以共用同一套“tree mask + 逐节点接受”的机制。

### 2.4 与 continuous batching 的结合（§5）

- SpecInfer 按**迭代**（iteration）而不是请求调度：每轮解码检查所有请求状态，完成的返回、新到的插入。
- 这使“树验证”能与其他请求的增量解码共享 batch；也是它能在 serving 场景与 Orca 类系统对比的前提。

### 2.5 一个请求的完整路径

把 SpecInfer 的一次迭代按顺序拆开：

1. **Speculate**：当前请求的前缀送给一个或多个 SSM，按 expansion/merge 生成 token tree。
2. **Flatten**：把树按拓扑展平成一维 token 序列，为每个节点记录祖先链（用于 mask 与位置）。
3. **Verify**：把展平后的树拼进当前 decoding batch，target 做一次前向；topology-aware mask 保证每个节点只看祖先。
4. **Accept**：从根开始按投机规则逐节点判接受，取最长被接受路径；被拒节点的 KV 丢弃。
5. **Commit**：把接受路径写入序列与 KV cache；未接受的位置由 target 采样补一个 token；进入下一轮。

这五步里，**只有第 3 步是 target 的前向**——树越宽，第 3 步的 token 数越多，但前向次数不变。这是 SpecInfer“用并行度换延迟”的成本结构，也是它在 batch 大时收益下降的原因：第 3 步的 token 变多后，单次前向本身变慢。

## 3. 实验设置（带条件）

| 维度 | 设置 |
| :-- | :-- |
| LLM | LLaMA-7B、OPT-13B、OPT-30B、LLaMA-65B |
| SSM | LLaMA-68M、OPT-125M（同族小模型） |
| 部署 A：单机多卡 | 多 GPU tensor parallel |
| 部署 B：多机多卡 | 跨节点分布式 |
| 部署 C：offloading | 单张 **24GB A10**，OPT-13B/30B 权重放 CPU DRAM，按需换入 |
| 对照 | 增量解码系统、序列式投机、FlexGen（offloading） |
| 指标 | 端到端延迟 / 每 token 延迟；输出与增量解码**逐 token 相同** |
| 树宽 | 扫描；batch≥4 时 2–3 最优 |
| 输入 | 五个公开数据集的 prompt（对话/指令类），生成上限 **128 token** |
| 硬件（分布式） | AWS g5.12xlarge；单机 1 卡或 4 卡，多机 2 节点 × 4 卡 |
| 硬件（offloading） | 单张 **24GB A10** + CPU DRAM |
| 指标 | 平均每 token 延迟 / 端到端延迟；输出与增量解码**逐 token 相同** |

## 4. 结果（带条件）

| 条件 | 结果 | 对照/说明 |
| :-- | :-- | :-- |
| 单机多卡分布式 | **1.5–2.5×** | 相对增量解码系统 |
| 多机多卡分布式 | **2.4–2.8×** | 同上；摘要合并为 1.5–2.8× |
| offloading（OPT-13B/30B、单 A10 24GB） | **2.6–3.5×** 每 token 延迟 | 对照 FlexGen |
| 树 vs 序列式投机（贪心） | **1.2–1.5×** | 树宽 > 1 的收益 |
| 树 vs 序列式投机（采样） | **1.3–1.4×** | MSS 的收益 |
| 树形并行解码 vs 序列解码（大 batch） | 最高 **1.8×** | 共享前缀 + mask 融合 |
| batch 增大 | 相对收益**下降** | 增量解码可利用的并行算力变多，SpecInfer 的“剩余算力”变少 |
| MSS 对验证 token 数 | 平均 **1.2–1.3×** | 跨五个 prompt 数据集；与 naive sampling 对照，输出分布不变 |

> **读法**：1.5–2.8× 是“分布式 + 增量解码基线”的区间；2.6–3.5× 是“单卡 offloading + FlexGen 基线”的区间。两者**基线不同、部署不同**，不能合成一个“最高 3.5×”的通用结论。

## 5. 消融：树宽、树 vs 序列、MSS

| 变量 | 对照 | 结论 |
| :-- | :-- | :-- |
| 树宽 `w` | BS=1/2 vs BS≥4 | 小 batch：**越大越好**（剩余算力多，验证更多 token 几乎免费）；大 batch：**w=2–3 最优**（算力饱和，宽树拖慢每步） |
| 树 vs 序列 | tree width=1 vs >1 | 贪心 1.2–1.5×、采样 1.3–1.4× |
| 树形并行解码 | 序列式解码 | 小 batch 持平；大 batch 最高 **1.8×**（消除共享前缀的重复 attention） |
| MSS | 有/无 | 采样场景下是“树能无损工作”的前提；具体增益见 §6.5 |
| batch | 1→更大 | 收益单调下降（图 7） |

### 5.1 为什么 MSS 的收益只有 1.2–1.3×

MSS 的作用是让“树的多个分支”在一次采样里都能被验证，而不是只验证贪心路径。它能提高每次验证的**有效 token 数**，但不改变 target 前向的次数——所以收益是“同一前向内多验证一点”，不是“少做几次前向”。论文报告 **1.2–1.3×** 的验证 token 数提升，正好对应这个量级。

**消融读法**：SpecInfer 的核心不是“树越大越好”，而是**树宽要匹配 batch 的算力余量**。这条结论后来在 EAGLE-2 的动态树、CAST 的成本感知建树、vLLM 的 adaptive verification 里反复出现——**“草稿 token 数”必须与负载一起调**。

---

## 6. 失效边界（独立段）

1. **batch 越大收益越小**：论文明确写“performance improvement reduces as batch size increases”；大 batch 下增量解码本身已把 GPU 喂饱，SpecInfer 没有“剩余算力”可换。
2. **树宽过大的反噬**：BS≥4 时宽树增加验证延迟；树宽必须按 batch 调，不存在通用最优。
3. **SSM 容量差是硬约束**：SSM 比 LLM 小 100–1000×，树只能提高“覆盖概率”，不能保证覆盖；target 路径不在树里时仍然退回增量解码。
4. **offloading 受带宽限制**：单 A10 + CPU DRAM 的场景里，权重换入换出是瓶颈；SpecInfer 的收益来自“一次验证多个 token、减少换入次数”，而不是无限加速。
5. **树形 KV cache 的内存开销**：树节点越多，KV 占用越大；长上下文 + 宽树的组合会撞显存墙。
6. **实现复杂度**：topology-aware mask、树形 KV、MSS 都需要改推理引擎；这不是“加个开关”能落地的方案（这也解释了为什么后来 EAGLE/Medusa 的“轻量草稿头”更容易进生产）。
7. **输出等价的前提**：论文声明与增量解码逐 token 相同；这个保证依赖 MSS 的正确实现与验证逻辑，工程实现偏差会破坏它。

## 7. 与同类系统的可判定差异

| 维度 | SpecInfer | 序列式投机（Leviathan/Chen） | EAGLE-1/2/3 | Medusa | Lookahead |
| :-- | :-- | :-- | :-- | :-- | :-- |
| 草稿来源 | 多个 SSM（蒸馏/量化/剪枝变体） | 单个 draft 模型 | target 特征自回归 | target 隐藏态 + 并行头 | Jacobi 轨迹 |
| 多分支 | **树（expansion/merge）** | 单链 | 树（静态→动态） | 树（笛卡尔积/搜索） | disjoint n-gram |
| 验证 | **一次树形前向 + MSS** | 链式验证 | 树注意 | 树注意 | 并行 n-gram 验证 |
| 是否训练 | 用现成 SSM（可蒸馏） | 需 draft | 需训草稿头 | 需训头 | 免训练 |
| 典型加速（条件） | 1.5–2.8×（分布式）；2.6–3.5×（offloading） | 2–3× | 3.0–6.5× | 2.3–2.8× | 1.5–2.3× |
| 主要贡献 | **系统/验证框架** | 算法范式 | 草稿质量 | 轻量自投机 | 免训练 |

**可判定差异一句话**：SpecInfer 是“**验证侧**的系统创新”（树 + mask + MSS），草稿侧可以接任意 SSM；EAGLE/Medusa 是“**草稿侧**的模型创新”，验证侧直接复用树验证。两者是正交的，后来的系统（vLLM/SGLang）同时吸收了两边。

## 8. 对本条目结论的影响

- **树验证成为公共基础设施**：SpecInfer 的 topology-aware mask 与树形 KV 是后续 EAGLE-2/3、Medusa、Sequoia 树验证的共同祖先。
- **“覆盖率”与“准确率”是两条轴**：SpecInfer 用树提高覆盖率，EAGLE 用特征级草稿提高准确率；两者可以叠加（EAGLE 的树验证就是例子）。
- **batch 依赖第一次被系统化**：SpecInfer 的“树宽随 batch 反向”是 [topics/systems-throughput-latency.md](../topics/systems-throughput-latency.md) 里“不存在静态最优草稿数”的最早系统证据之一。

---

### 8.1 与后续系统的接口

- **验证层**：SpecInfer 的 topology-aware mask 与树形 KV，在后续系统里演化为 `tree attention`/`tree mask`；SGLang 的 `build_tree_kernel_efficient`（`eagle_utils.py:157`）与 vLLM 的 spec-decode 树验证都在同一抽象上。
- **调度层**：SpecInfer 的 iteration 级 continuous batching 与 Orca 同源；今天 vLLM/SGLang 的调度器已把这层吃进主干，SpecInfer 的“树验证”则变成可选后端。
- **草稿层**：SpecInfer 不规定草稿必须来自 SSM；EAGLE/Medusa 的草稿头可以直接接到“树验证”上——这也是为什么 SpecInfer 的贡献更适合被引用为“验证框架”，而不是“某个草稿方法”。

---

## 9. 引用注意（何时不该引它）

- 不要把 2.6–3.5× 当成“SpecInfer 相对所有系统的加速”——它只对 **FlexGen offloading** 基线成立。
- 不要把 1.5–2.8× 与 EAGLE-3 的 6.5× 并列——前者是 **2023 年的 SSM + 树验证系统**，后者是 2025 年的特征级草稿 + 动态树；模型、基线、硬件都不同。
- 引用树宽结论时写清 batch：**BS=1/2 宽树更好，BS≥4 用 2–3**；不要简化成“树越宽越好”。
- 不要说 SpecInfer “无损且无额外成本”——树形 KV 与 mask 有显存/实现成本，offloading 场景还受带宽限制。
