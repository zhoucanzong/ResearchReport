# Sequoia：把树形草稿、采样鲁棒性和硬件预算放进同一个优化问题

> 原文：Chen et al., [*Sequoia: Scalable, Robust, and Hardware-aware Speculative Decoding*](https://arxiv.org/abs/2402.12374v3)，arXiv v3，2025-07-05。重点阅读 §§2–4、Appendix B/F，尤其是 §3.1、§3.2、Fig. 2–4、Tables 1–2。本文数字为作者报告，没有独立运行或复现。

## 它在树验证路线中的位置

树状 speculative decoding 把一个草稿扩成多条候选路径，再让 target 并行验证。直觉上，树越大，越容易包含 target 会走的路径；但更大的树也意味着更多验证 token、更高内存占用和更长的一次 target 前向。因此问题不是“怎样造最大树”，而是：**给定一个节点预算和 target 的接受行为，树应当如何分配分支与深度？**

Sequoia 的主要贡献是将这个问题分成两个相连、但可分别理解的部分：

1. 用动态规划选择“给定大小下期望接受长度更高”的树形；
2. 用不放回采样与验证改善候选被逐个拒绝的情况，再按具体硬件实测的 draft/verify 成本选择树大小和深度。

这让它不只是 SpecInfer 的另一个多分支候选构造器，也不只是 MagicDec 的另一个硬件负载分析：SpecInfer 证明并实现“把多路草稿组织为树并一次验证”的系统范式；MagicDec 主要分析长上下文、大 batch 与 KV 带宽；Sequoia 则把**树的拓扑和温度相关的验证规则**本身作为可优化对象。

## 机制一：根据位置接受率做树形动态规划

设某层第 $k$ 个子节点被接受的概率为 $P_k$。Sequoia 的 closed-form score 为树中每个节点的路径接受概率之和：

\[
F(T)=\sum_{v\in T} f(v),\qquad f(v)=\prod_{k\in\mathrm{Path}(v)}P_k.
\]

这正是验证该树后期望生成 token 数的模型。随后算法在节点数 $N$ 与最大分支数 $B$ 的约束下，用动态规划搜索各层如何分配节点预算；论文在 Appendix F 还给出带深度上限的扩展，也可输入随深度变化的位置接受率，用于自投机方法中“离当前前缀越远，接受率越低”的情形。[§3.1.1、Algorithm 1、Fig. 2、Appendix F.1]

这里的“最优树”有明确前提。理论分析采用 **positional acceptance assumption**：接受概率主要由节点在父节点下的子序位置决定，而不是由每个具体前缀、置信度或语义上下文独立决定。要推出随树大小近似对数增长，还需树验证算法的全拒绝概率满足论文定义的幂律上界。作者在实验里观察到 Sequoia 的拒绝率接近幂律，但这不是对任意 drafter/target 都成立的定理。[§3.1.2、Definition 3.1、Definition 3.5、Theorem 3.6、Fig. 3、Appendix B]

**设计取舍**：DP 不在线重新解树形，因此推理时成本低；但位置接受率需要从某个模型、数据和解码设置估计。模型、温度、任务或硬件变化后，既可能改变接受向量，也可能改变最合适的树。论文在 Appendix B 将这种配置敏感性列为实际限制。

## 机制二：通过不放回候选减少重复拒绝

常规树采样可能多次提出同一个低质量 token，并在不同分支上重复被拒。Sequoia 在 SpecInfer 式采样/验证中加入两条规则：被拒的 draft token 从提议分布支持集中移除；若所有原本有正概率的候选都试过且被拒，则改为在尚未提出的词表 token 间均匀采样。每次拒绝仍按 residual 更新 target 分布，因而这不是“跳过残差、直接接受更像的节点”。作者在 Appendix F.2 证明该规则仍保持 target 输出分布。[§3.2.1–3.2.2、Algorithm 2、Appendix F.2]

它主张的 **robustness** 由两个可判定性质表达：单个候选的接受率达到最优传输给定的重叠量；当 draft 支持集覆盖 target 的支持集时，不超过相应候选数即可获得接受；全词表候选的极限情形下可达到接受率 1。论文图 3 将 Sequoia、SpecInfer、SpecTr 与 top-k sampling 在不同温度下比较：Sequoia 在所测温度范围内拒绝率下降更快；这支持其构造在该实验里的鲁棒性，不意味着它对所有树或所有 target 都逐点支配其他方法。[Theorem 3.7、Fig. 3、§3.2.3]

## 机制三：把树大小和硬件成本联合选择

硬件优化器不把 token 数直接当吞吐。论文把 DP 得到的预期生成长度 `G(n,d)`、树大小 `n`/深度 `d`、target 验证 `n` 个 token 的实测时间，以及草稿生成时间代入成本模型，选择使预期 wall-clock speedup 最大的配置。作者先针对模型、温度和硬件 profile，再在候选树规模中搜索；论文使用 PyTorch CUDA Graph 减少 launch 开销，并用 exponential-sort 算法实现不放回采样。[§4.1, “Hardware-Aware Optimization”]

|---|---|
| A100 on-device，Llama2-7B + Llama-68M，C4、T=0、树大小 128 / 深度 10：相对 Hugging Face 增量解码 4.04×；相对 SpecInfer 对照 1.17× | Table 1；两列基线不同，不能把 4.04×写成相对 SpecInfer 的增益。 |
| L40 offloading，Llama3-70B-Instruct + Llama3-8B-Instruct，MT-Bench、T=0、树大小 768 / 深度 18：相对 DeepSpeed-Zero-Inference 9.5×，约 0.60 s/token；相对 SpecInfer 配置 1.36× | Table 2；大树带来的收益依赖 CPU/GPU 权重换入瓶颈和具体 offloading 系统。 |
| 固定树形后，Llama2-7B + Llama-68M、CNN/DailyMail 的温度扫描中，作者报告 Sequoia 对 SpecInfer 的 speedup 最高 1.65×、对 top-k sampling 最高 1.27× | §4.2.2、Fig. 4；这是单独比较验证/采样算法的实验，不是上两行端到端硬件结果。 |

论文测试用不同温度、draft/target 配对、C4/OpenWebText/CNN-DailyMail/MT-Bench 等数据和单卡 A100/L40 offloading。它没有证明一棵 profile 出来的树可在任意线上负载中保持最优，也没有独立 CUDA kernel 基准。**硬件感知**在这里指按设备实测运行成本选树形与预算；不等于提出了新的 fused tree-attention 算子。[§4.1–4.2、Tables 1–2、Appendix B]

## 与相邻树方法的区别

| 方法 | 优化对象 | 验证层的关键点 |
|---|---|---|
| SpecInfer | 扩展/合并多条草稿，构成可并行验证的 token tree | topology-aware mask 与多步投机采样构成树验证底座；树宽需按 batch 调整。 |
| EAGLE-2/3 | 依据上下文和草稿不确定性形成动态树 | 树形跟随模型特征；不等于 Sequoia 的“用位置接受率和目标硬件成本解树”。 |
| Sequoia | 节点预算下的树拓扑 + 不放回候选验证 + 硬件成本 | 结构目标与验证/采样机制一并改动；作者为该特定方法给出分布保持证明。 |
| Traversal Verification | 给定树上的遍历顺序与路径接受判据 | 叶到根、序列级接受；不负责优化建树。 |
| CaDDTree / Delayed Tree | 预算如何投放、何时分枝 | 目标函数和候选类型与 Sequoia 不同，不能只凭“都按预算建树”视作同一算法。 |

因此，树验证至少要分开问：候选树怎样生成、验证按何种顺序遍历、接受/拒绝怎样保持概率分布、树规模怎样匹配硬件成本。把它们压成“树越大接受率越高”会漏掉错误概率、拒绝采样开销和 target 单次前向成本。

## 失效边界与开放问题

- **位置接受率假设**忽略前缀内容和节点置信度差异；在真实树中，同一深度/兄弟位置可能有不同接受概率。
- **幂律拒绝假设**支撑树规模扩张的渐近结论；论文报告实验里接近这一形态，但定理不对所有模型分布无条件成立。
- **硬件优化需要重新测量**：draft 代价、target token 并行验证代价及 batch 会改变最佳树大小；作者说明接受向量的采集与树搜索需要按设置运行。
- **树搜索的目标是预期接受 token，不是普适 wall-clock**；硬件 optimizer 才将实测成本加入选择，且实测配置之外的适用性仍需评估。
- **该论文并非低层 kernel 论文**：其 PyTorch + CUDA Graph 实现用于端到端验证，但未对 tree attention、mask packing、KV 写回等算子做独立的跨实现基准。
