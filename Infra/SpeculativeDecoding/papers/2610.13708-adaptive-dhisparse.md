# Adaptive DHiSparse：稀疏 KV 层级怎样与投机验证共用内存

来源：Alazhar & Alazhar, [*Adaptive DHiSparse: Speculative Decoding over a Load-Adaptive KV Hierarchy*](https://arxiv.org/html/2610.13708v1)，固定版本 v1（2026-10-09），CC BY 4.0。重点阅读 §2–§3.5、§4.2–§4.3、§5。

## 它解决的是三种省资源方法组合后的共同瓶颈

稀疏注意力只读取当前 query 选中的部分历史 KV，减少计算；层级 KV 将冷历史放到主机内存，减轻 GPU HBM 容量压力；投机解码让一次 target 前向验证多个候选，减少串行 target 轮数。三者分别减少“算哪些历史行”“把历史放在哪里”“target 要跑几轮”，但组合时会争用同一份显存：一轮验证有多个 query，草稿器也可能需要额外 KV，批内请求越多，工作集越大。

HiSparse 已把稀疏选择与 host-resident history 结合，但原设计的 GPU cache budget 固定，且每个 request 每轮只处理单 query，没有覆盖多候选验证时的共享检索和临时状态。Adaptive DHiSparse 的问题是：**如何在负载变化时使用空闲 HBM，又在压力到来时回收这部分“可选历史”，并让树/块验证不重复搬同一批行？**[原文 §1–§2.3](https://arxiv.org/html/2610.13708v1)

## 机制一：必需工作集与可回收历史分开管理

每个请求、每个 KV source 保留固定热缓存（hot cache）、最近新增的尾部状态（tail）和选择元数据；此外，系统可把更多已导入历史暂存在 GPU 的可回收页面中。空闲 HBM 多时，这些 optional history 减少后续主机读取；新请求到来、必需分配变大时，runtime 按请求回收可选页。无法及时回收时，新请求等待，不挪走仍需要的 hot cache 或未完成写入。[§3.1](https://arxiv.org/html/2610.13708v1)

这与扩大固定 GPU KV cache 不同：固定 cache 把容量预算预留给每个请求，即使负载较轻也可能挤掉新会话；负载自适应 residency 把空闲容量暂借给历史页，负载升高时归还。注意，**这改变 KV 在 GPU/host 的位置，不改变模型对历史的选择集合**：indexer 仍给出有序的 sparse selection，resolver 负责把对应行恢复到可供 attention 读取的位置。[§2.1–§3.2](https://arxiv.org/html/2610.13708v1)

## 机制二：一轮多个 query 共享缺失 KV 的搬运

投机验证会同时评估多个 query/候选路径。若各 query 分开从主机取 KV，同一轮里共同选择的历史行会被反复读取；若把每个 query 的整套选择状态各自保留，临时 staging 又会随候选数增长。

Adaptive DHiSparse 先合并同一请求、同一 payload source 下各 query 选择行的并集；已经在 tail、optional history 或 hot cache 的行直接复用，缺失行只从 host copy 一次，再把该物理位置供所有选择它的 query 读取。每个 query 仍保留自己的选择顺序、因果 mask 和 attention 语义；这里共享的是字节搬运与物理位置，不是把不同 query 的注意力输入合并。[§3.2–§3.3](https://arxiv.org/html/2610.13708v1)

草稿 KV 用有界窗口 ring 存储；target verification 的 staging 按 layer groups 复用，等该组消费者读完再释放。只有被 target 接受的前缀才成为已提交历史，拒绝和未验证分支不发布；论文声称其层级只改存放位置与读取路径，不改 target query selection、proposal/acceptance rule 或 committed prefix。[§3.4–§3.5](https://arxiv.org/html/2610.13708v1)

## 与 SpecStream、H-Spec 的区别

| 系统 | 主要在减少什么 | 历史 KV / 草稿状态怎么处理 | 适用问题 |
| :-- | :-- | :-- | :-- |
| [SpecStream](2609.33184-specstream.md) | CPU↔GPU 搬运历史 KV 等待时的空泡 | 流式恢复 full-attention 所需的完整历史，并利用传输等待并发运行 draft | dense/full-history attention 的 offload 与 overlap |
| Adaptive DHiSparse | sparse selected rows 的 host miss 与固定驻留预算 | 只恢复 sparse indexer 实际选中的行；多 query 合并 miss；load 高时回收 optional history | 本来就使用 sparse attention/KV selection 的长上下文 serving |
| [H-Spec](2609.24197-hspec.md) | 块式 drafter 自己保存的一份 target-context KV 副本 | 草稿器 attention 原位读 target KV，Mamba state 接收末位 hidden-state 摘要 | block drafter 的目标上下文注入与并发缓存成本 |

三者层级不同：SpecStream 优化 **full-history transfer 与共卡调度**；Adaptive DHiSparse 优化 **稀疏 KV 行的驻留和多 query 读取**；H-Spec 优化 **drafter 侧上下文表示/缓存**。它们都谈 KV，但分别优化传输、草稿缓存和稀疏历史驻留，不能合并成“KV offload”，也不能把系统吞吐数字跨论文横向排序。

## 论文报告的结果揭示了什么取舍

论文在 8×B300 系统上测试 GLM-5.3 100K context 与 DeepSeek-V4.1-Flash 500K context，并与相同 KV 设定的 resident serving、HiSparse、非投机 adaptive serving 比较。[§4.1](https://arxiv.org/html/2610.13708v1)

- 在 GLM-5.3、100K context、offered concurrency 128、DFlash2 配置下，作者报告每个 decode GPU 约 793 output tokens/s，分别是 HiSparse 的 1.45×、非投机 adaptive serving 的 1.27×。这是特定模型、稀疏 KV 方案、8×B300 角色切分、输出预算和闭环并发负载下的系统结果。[Abstract、§4.2.1、Table 2](https://arxiv.org/html/2610.13708v1)
- 重要反例出现在 concurrency 256：自适应非投机系统输出约 823 tokens/s/GPU，DFlash2 版约 826，吞吐几乎相同，但投机版只维持 140 个 session、非投机版维持 208 个，平均 TTFT 更高。草稿使单个活跃 session 的 TPOT 更低，却用更多 memory/verification staging 减少了 admission capacity；低 token latency 不保证相同服务约束下吞吐更高。[§4.2.1](https://arxiv.org/html/2610.13708v1)
- 在 DeepSeek-V4.1-Flash、500K context、concurrency 512、DSpark 配置下，作者报告 adaptive hierarchy 的输出吞吐为配套 resident+DSpark 的 1.85×。这与 GLM-5.3 的 100K 结果属于不同模型、KV selection 密度和并行配置，不能将 1.45×、1.85×并为“投机+稀疏KV的一般加速”。[§4.2.2](https://arxiv.org/html/2610.13708v1)

关键读法是驻留预算要随负载理解：低并发时所有历史都能留在 HBM，resident serving 不必付 host miss，层级方案可能多出 resolver 成本；超过容量后，optional history 让热数据先留在 GPU、冷数据按需恢复，收益才显现。若投机所需 staging 进一步挤掉 session slots，就可能出现“单会话更快、总服务输出没增加”的区间。[§4.3.1、§4.3.4、§5](https://arxiv.org/html/2610.13708v1)

## 证据边界

- 论文针对 GLM-5.3 与 DeepSeek-V4.1-Flash 这两类 sparse KV 结构；selected-row resolver 不能直接外推到不做 sparse selection 的普通 dense attention。
- 论文的 exactness 论证以模型 state、ordered selection、payload/scales、causal mask 和接受前缀都一致为条件；它不是新的概率接受证明，而是系统存储层保持现有 attention/verifier 输入的论证。[§3.5](https://arxiv.org/html/2610.13708v1)
- Serving 数值是作者在 B300、指定 context/concurrency、闭环请求和特定 DFlash2/DSpark 配置下报告的结果。本专题未运行源码、未做 GPU 测试，也不据这些数字推断其他 GPU/NVLink/PCIe 架构的收益。
- 论文说明 speculation 在高负载时可能因减少 active sessions 而不再提高总输出；部署判断须同时看 TTFT、TPOT、admitted sessions、吞吐和 latency bound。

**带走的区别**：Adaptive DHiSparse 不只是“把 KV offload 到 CPU”。它把 sparse selection、候选验证时的多 query shared miss、load-adaptive residency、draft ring 和 accepted-prefix commit 当成一个联合内存/执行问题；研究者应先确认 target 是否确实按稀疏 index 选择历史，再讨论这类层级设计是否适用。
