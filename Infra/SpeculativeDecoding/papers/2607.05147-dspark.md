# DSpark：并行草稿补上块内依赖，再按负载决定验证多长

来源：Cheng et al., [*DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation*](https://arxiv.org/html/2607.05147v1)，arXiv v1（2026-07-06，CC BY 4.0）。重点读 §3.1–§3.3、§4.3、§5.2–§5.4，尤其 Figure 2、Algorithm 1 与 Appendix A。

## 两个瓶颈不能靠同一个“多 draft 几个 token”解决

并行 drafter 的一次前向很快，但每个位置独立预测时会把多种可能后续平均在一起。真实生成一旦选定前缀，块内后续位置却应条件化于这个已选前缀；因此可能出现局部 token 都看似合理、拼起来却不连贯的组合，接受率在 block 后缀下降。相反，自回归 drafter 逐 token 用前一 token 条件化，但 drafting latency 随块长增加，难以提出足够长的候选。[§2.2、§3.1、§4.3.1](https://arxiv.org/html/2607.05147v1)

DSpark 把两者组合成**半自回归 draft**：

1. 平行 backbone 一次生成整个 block 的 hidden states 与 base logits，保留块级并行速度。
2. 轻量 sequential module 逐 token 给 base logits 加入前缀条件的转移偏置，使块内第 $k$ 个候选能利用已采样的 $x_{<k}$。作者实现了低秩 Markov head 与 RNN head；前者看上一 token，后者在块内维护递归状态。

这不是把完整大模型再跑一遍，而是在较贵的 parallel backbone 上附一段较轻的局部因果修正。目标是同时保留较强的首位预测与后缀连贯性。它与 [HCSpec](2026.acl-long.353-hcspec.md) 改变 drafter 前后位置所用容量相关，但机制不同：HCSpec 把前段双路 MH 与后段轻量 ML 分段级联；DSpark 在块式并行骨干后，为每个后续位置追加轻量前缀依赖。[§3.1](https://arxiv.org/html/2607.05147v1#S3)

训练时 target 冻结，共享 embedding 和 LM head 也冻结，只更新 draft backbone、顺序头与 confidence head；目标由 token CE、draft/target TV 匹配和 confidence loss 组成，沿用按位置指数衰减权重。[§3.3](https://arxiv.org/html/2607.05147v1#S3)

## 置信度调度：决定每条请求的验证前缀，并把 batch capacity 用在更值的位置

即使 draft 一次能提出长 block，target 也不必把整块送去验证：低置信后缀很可能会被拒绝，且在高并发下验证 token 会占 target batch capacity。DSpark 的 confidence head 为各位置预测条件接受概率 $c_k$；前缀生存概率为 $a_k=\prod_{i\leq k}c_i$。由于 scheduler 要用 $a_k$ 估计吞吐的绝对值而不只是排序，作者在 held-out 验证集上逐位置做 Sequential Temperature Scaling，校准累计前缀概率。[§3.2.1](https://arxiv.org/html/2607.05147v1#S3)

调度器结合当前活动请求的这些前缀概率，以及运行时 target engine 的 step-per-second 曲线 $\mathrm{SPS}(B)$。它不断把下一段最可能成功的前缀扩展加入 batch，观察增加验证 token 后预期接收量与当前 batch 执行速度的乘积是否提高；若下降便停止扩展。**调度对象是整个活动 batch 中每条请求的验证前缀长度**，并非简单按某个置信阈值逐候选等比例分配算力。[Algorithm 1、§3.2.2](https://arxiv.org/html/2607.05147v1#S3)

这里有两个关键正确性条件：一是接受决策不能偷看尚未纳入决定的后续候选，否则会有 selection bias；论文以按概率顺序扩展、首次吞吐目标下降即早停来维持非预见性。二是这个早停路径只有在吞吐目标沿扩展路径单峰时才等于全局最优，作者将其联系到硬件容量曲线平滑衰减的假设，并讨论真实曲线不平滑时的工程适配。标准 target rejection sampling 仍是最终输出保证来源；DSpark 的预测头本身不是新的 verifier 定理。[§3.2.2、Appendix A](https://arxiv.org/html/2607.05147v1#S3)

## 论文证据分别支撑“draft 更好”和“系统更会分配”

作者将两类效果分开：离线固定块比较时关闭 confidence scheduler，以隔离 semi-AR draft 的质量；结果覆盖 Qwen3-4B/8B/14B 与 Gemma 4-12B、数学/代码/聊天 benchmark、$T=1$，并在相同训练框架和数据上比较 DFlash 与 EAGLE-3。Qwen3-4B 的 macro-average accepted length，DSpark 比 EAGLE-3 高 30.9%，比 DFlash 高 16.3%。这些是论文报告的离线接受长度结果，并不含硬件 scheduler 的端到端吞吐收益。[§4.1–§4.2、Table 1](https://arxiv.org/html/2607.05147v1#S4)

线上 DeepSeek-V4 部署再报告 scheduler 在 live traffic 和匹配 aggregate throughput 下提高 per-user generation speed。它支持“工作负载相关的验证预算会改变系统 Pareto frontier”，但属于作者特定 serving stack、硬件与流量配置下的部署证据；不能把线上结果归到半自回归结构单独一项，也不等于其他引擎可复现同一收益。[§5.2–§5.4](https://arxiv.org/html/2607.05147v1#S5)

## 与 D-PACE / D-PAL / HeteroSpec 分别比较

| 工作 | 预算或信号的作用点 | 和 DSpark 的区别 |
|---|---|---|
| [D-PACE](2605.18810-dpace.md) / [D-PAL](2610.28355-dpal.md) | 离线训练时分配 block 内位置梯度；D-PAL 以完整分布 overlap 取代单点 token confidence | 训练 loss 轴；DSpark 的 Markov/RNN head 改推理时位置依赖，confidence scheduler 再改验证前缀，而训练仍用固定位置衰减。 |
| [HCSpec](2026.acl-long.353-hcspec.md) | 早段用高容量双路 draft、后段切轻量模块 | 改 draft 模块按位置的容量分工；DSpark 则在平行 backbone 后用小型顺序头恢复局部依赖。 |
| [HeteroSpec](2026.acl-long.589-heterospec.md) | 以累计路径 Top-K 熵把上下文分层，并选 draft depth / Top-N / graph 配置 | 改上下文对应的 EAGLE-3 树策略；DSpark 的 survival-confidence 列表和硬件 SPS curve 显式参与跨请求 batch 的吞吐目标。 |
| [TTS](2605.09329-test-time-speculation.md) | 每轮 target 反馈在线更新 draft 权重 | 改 draft 权重适应时间；DSpark 的置信 head 与块内顺序 head 是离线学得，scheduler 在推理时作选择。 |

它们都可能影响接受长度或验证成本，但分别改 loss、drafter capacity、局部条件化、上下文级树策略、batch 预算或在线参数；不能因为都叫 confidence/heterogeneity 就视为一个方法家族。

## 失效边界

- 半自回归尾部仍要逐 token 运行轻量模块；模块太重会吃掉 parallel backbone 节省的 drafting latency。
- scheduler 需要置信头对**累计接受概率**校准，而不只是会排序；calibration domain 与 live traffic 不匹配会误估吞吐回报。
- scheduler 依赖测得的 engine capacity curve，早停获得全局最优还依赖扩展路径上目标单峰。负载曲线、多卡调度或 context-length variation 若偏离其假设，需要重新验证。
- 论文主文把动态预算运行时算法与 live DeepSeek-V4 serving 结合报告；二者不可混为同一项 offline algorithm speedup。精读未独立复现、审计 DeepSpec 代码或运行 serving benchmark。

**带走的判断**：DSpark 不是简单“DFlash 加置信度阈值”。它一边以轻量因果头修复并行块的后缀失配，一边把各请求 prefix-survival 的预期收益映射到引擎的实测 batch 吞吐曲线。只有 draft latency、概率校准、scheduler 因果性和当前负载成本曲线都对上，两个环节才会一起带来系统收益。
