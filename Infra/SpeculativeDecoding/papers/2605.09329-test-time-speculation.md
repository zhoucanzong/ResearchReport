# Test-Time Speculation：把每轮 target 验证变成草稿器的在线学习信号

来源：Kumar, Sanghavi & Das, [*Test-Time Speculation*](https://arxiv.org/html/2605.09329v1)，arXiv v1（2026-05-10，CC BY 4.0）。重点读 §2–§4、§6.2–§6.6、Appendix C，尤其 Figure 4–7 与 Table 3、8。

## 问题：离线学会了短上下文，推理却要追上不断变长的轨迹

EAGLE-3、DFlash 等 speculator 在离线 target-generated 短序列上训练，实际推理却可能沿着数千至数万 token 的 target 轨迹继续预测。论文观察到某些长推理任务里 mean acceptance length（每次验证轮平均提交的草稿 token 数，按论文口径含 bonus token）随生成长度下降；作者把它归因于草稿训练前缀与长推理前缀的分布失配，而不是简单的“位置越后越难”。[§2–§3](https://arxiv.org/html/2605.09329v1)

这个解释与块内位置效应是两个尺度：同一 draft block 内，越靠后的候选必须等前缀通过才能提交；而跨生成位置的问题是草稿器在长 CoT 后是否逐渐偏离 target。前者是 D-PACE / D-PAL 的训练权重问题，后者是 Test-Time Speculation（TTS）所要修复的在线失配问题。本文的长 CoT 独立 draft 诊断进一步显示，后者不能脱离“是否经过 target 输出训练”来讨论。[长 CoT 位置诊断](2610.30644-long-position-acceptance.md)

## 机制：复用 target 已算出的概率，但要额外更新 draft

每个标准 speculative round 都已经包含一段 draft canvas 及 target 对这些位置的条件分布。TTS 把这轮验证轨迹当成 on-policy 蒸馏样本：target 是 teacher，draft 是 student；target 对同一已验证前缀计算的分布监督当前 draft，随后对 draft 做一次梯度更新，再用更新后的 draft 开始后续轮次。[§4.1、Algorithm 1](https://arxiv.org/html/2605.09329v1#S4)

作者的目标可直观分成两项：

1. **向当前 target 分布靠近**：对 draft canvas 中各位置的 target / draft 分布做加权 KL；位置权重沿用原 drafter 的块内训练配方。
2. **限制单轮过拟合**：对更新后的 draft 加入相对上一版 draft 的正则项，避免一份 canvas 的梯度把模型推得过远。

一次验证 round 的 draft token 已由 q 提出，target pass 产生按前缀条件化的 p，因此无需为了拿这些监督而额外调用 target；但“监督信号不增加 target forward”并不等于在线更新没有成本。TTS 仍要算 draft 的 backward 与 optimizer step，如何把更新放到非关键路径，是方法可否真正提速的系统条件。

更新后 draft 分布改变，未来候选及接受率会变；只要每轮仍由原 target 按标准 speculative rejection sampling 验收，最终输出分布由 target 与验收规则保证。TTS 改的是 proposal 的质量，不把 draft 训练结果直接当作答案。[§4.1、§6.4](https://arxiv.org/html/2605.09329v1)

## 为什么 online update 有帮助，又为什么它不免费

在目标与任务覆盖方面，作者报告 TTS 接到 DFlash 和 EAGLE-3 上评估，覆盖 Qwen3、Qwen3.5、Llama 3.1 的多种尺寸，以及数学、代码、科学问答等长输出任务。论文报告的接受长度改善会随输出变长而扩大；这支持“每轮 target 反馈可以纠正当前 trajectory mismatch”，但不是不计更新成本的端到端速度结论。[§6.1–§6.3、Tables 1–2、Figure 5](https://arxiv.org/html/2605.09329v1#S6)

更新频率体现了主要取舍：每轮都更新通常得到较高 acceptance length，但训练会占用 GPU；把更新改为每 \(S\) 轮一次，能摊薄开销，却会减弱适应速度。作者还用独立 CUDA stream 与后续推理重叠反向更新。论文指出这种 overlap 不能消除资源竞争；同步边界和 SGLang CUDA-graph 流行为也需要专门处理。[§6.4、Appendix C.1–C.3](https://arxiv.org/html/2605.09329v1#S6)

因此要分开看三件事：**mean acceptance length** 表示草稿和 target 的贴合度；**TTS 的更新频率/梯度耗时**决定增加多少在线训练成本；**wall-clock throughput**才回答该系统配置是否更快。只报接受长度提升不能替代端到端收益，反过来系统吞吐也不能告诉我们草稿为何变好。

## 与 D-PACE / D-PAL / TLT 的研究关系

| 路线 | 何时改变 draft | 它对准的失配 |
|---|---|---|
| [D-PACE](2605.18810-dpace.md) / [D-PAL](2610.28355-dpal.md) | 离线训练时改变 block 内各位置的 loss 权重与拟合分布 | 一个 draft block 中哪些位置最影响可提交前缀，以及点质量置信是否足够表示 target–draft 接受重叠 |
| **TTS** | 单条序列的推理期间，按 target 验证样本更新 draft | 当前生成轨迹逐渐离开离线训练前缀分布后的 draft–target mismatch |
| [TLT / Adaptive Drafter](2511.16665-tlt-adaptive-drafter.md) | RL rollout 的长尾空档并行更新 drafter | target policy 在持续训练中改变后，draft 与当前 policy 的失配及 GPU 调度 |

三者分别改变**离线目标、单请求在线适应、跨训练 rollout 的更新时机**，不是一组同条件的性能排名。TTS 不声称静态 draft 训练变得不再重要：它从已有 checkpoint 开始，仍依赖模型可训练、target logits 可取、在线更新能及时执行。若适配产生的反向传播抵消了省下的 target 调用，接受长度改善就不能转成速度收益。

## 适用边界与下一步问题

- 论文最强的适用动机是**长输出、且 speculator 离线训练 context 明显短于目标推理轨迹**。如果 draft 已覆盖 target 的上下文范围，改善幅度可能小一些；短回答也未必留出足够轮次摊销更新。
- TTS 每轮使用最近 canvas 的监督；update stride 越大，历史轮次监督不会自动累积。频繁在线适应可能更贴近当前轨迹，但需要算力、可微训练路径与同步。
- 长 CoT 位置诊断并未研究已训练 draft；TTS 的确研究了已训练 DFlash / EAGLE-3 的长输出退化。两篇分别提供**独立 draft 基线**与**训练长度失配/在线修复路线**，合起来仍缺同一模型、同一 verifier、同一长序列指标口径下的因果复测。
- TTS 面对的是当前请求的一条轨迹；跨请求复用、用户数据隔离、并发请求间共享 draft 状态等属于另一类系统和治理问题，不能从单请求实验证明。

**带走的判断**：TTS 最重要的不是“边推理边微调”这个标签，而是把标准验证步骤已有的 target 分布转成当前轨迹的 on-policy 训练样本。要判断是否有效，需同时问：长输出的失配是否真的来自训练前缀不足、更新是否获得足够反馈、更新开销能否被后续验证节省覆盖，以及严格 target verification 是否保持不变。
