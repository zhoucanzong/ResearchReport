# H-Spec：用目标 KV 与末位摘要，去掉独立草稿 KV 缓存

来源：[H-Spec: Parallel Speculative Decoding Without a Drafter-Side KV Cache](https://arxiv.org/html/2609.24197v1)，固定版本 v1（2026-09-21）。重点阅读 §3.1–§3.3、§4.1–§4.4、§5 和 Appendix B–D。

## 问题：块扩散草稿并行了，为什么每个请求还要存一份草稿 KV？

DFlash 一类块扩散 drafter 在一次前向中并行预测一个 token block。为了充分利用 target 上下文，它把多个 target 层的 hidden states 投影成**单独的 drafter-side KV**，再让草稿位置读取这份前缀信息。候选能直接受 target 表征条件化，但每条并发请求都要多存一份 KV、额外写入并访问它。

H-Spec 先测试一个直觉方案：让 drafter 直接读取 target 已保存的 KV。这样免去了缓存副本，却丢掉了末位 target hidden state 所含的**整段前缀摘要**；论文在 Qwen3-8B 等设置中观察到，直接复用 KV 对早期草稿位置的接受影响较小，后续位置的条件接受率下降更明显。这个结果提示，逐位置检索与全局上下文摘要不是可互换的表示。[§3.1、Figure 4](https://arxiv.org/html/2609.24197v1#S3)

## 方法：把两种上下文来源分配给不同模块

H-Spec 将最后输入位置的 target hidden states 与 target 原有 KV 结合：

- **最后位置 hidden-state 摘要**：从选定 target 层取末位 hidden states，融合并投影为 Mamba-2 的初始状态。因果 target 的末位状态已汇总完整历史，表示大小不随输入 token 数线性增长。
- **逐位置上下文**：drafter 的 attention modules 直接读取 target KV cache，不再为全部前缀位置另建一份 drafter KV。
- **块内并行**：Mamba 使用 parallel scan 计算草稿 block 内状态，因此虽然是 recurrent state-space 模块，仍可并行产生一个 block；attention 再提供位置级上下文。

两类上下文并不重复：Mamba 初态给“整段历史”的压缩摘要，target KV 让草稿查看“历史中的具体位置”。H-Spec 的核心不是“只保留最后一个 token 就够了”，而是用末位 hidden-state 摘要补齐直接 KV 复用缺少的全局信息。[§3.2–§3.3](https://arxiv.org/html/2609.24197v1#S3)

H-Spec 还在混合骨干之后采用 DSpark 的 Markov causal correction，让后续位置依赖前一草稿 token。作者明确说这是沿用组件，不是 H-Spec 的核心新贡献；它与 Mamba/attention 的上下文分工应分开理解。[§3.3.3](https://arxiv.org/html/2609.24197v1#S3)

## 与 DFlash、DLite 和 Component-Aware 的差别

| 方法 | target 上下文怎样进入 drafter | 额外状态的关键位置 | 主要试图解决什么 |
| :-- | :-- | :-- | :-- |
| DFlash | 将多个位置的 target hidden states 投影成 drafter prefix KV | 另存 drafter-side KV | 并行生成且充分利用 target 条件，但增加每请求缓存与写入 |
| DLite | 抽取 target hidden states，草稿器不保留长历史 KV；用顺序头恢复草稿块内依赖 | 无历史 drafter KV；保留块内小状态 | 降低 draft 历史 KV 与重复历史编码成本 |
| Component-Aware Self-Speculation | 从 hybrid target 子图抽取内部组件作 drafter | 复用/裁剪 target 架构组件 | 检查目标架构中并/串模块是否能构成有效内部草稿 |
| H-Spec | 最后位置 hidden states 初始化 Mamba，attention 原位读 target KV | 不建独立 drafter-side KV；仍使用 target KV 与 Mamba state | 用压缩全局摘要 + 逐位置检索兼顾条件质量与并发内存 |

因此 H-Spec 的差异不是泛泛的“无 KV 缓存”。DLite 也减少草稿器历史 KV，但以 target hidden states 驱动不保留长历史的草稿器；H-Spec 针对 DFlash 式 target-context 投影副本，组合原位 target-KV 复用和摘要补偿。两者的 drafter 结构、上下文路径和计算代价不同。[DLite 对照](2610.23787-dlite.md) · [Component-Aware 对照](2605.01106-component-aware-self-spec.md)

## 论文结果支持什么？

论文在 Llama3.1-8B-IT、Qwen3-4B 和 Qwen3-8B 三类 target、八个任务上比较 H-Spec 与 P-Eagle、DFlash、DSpark；训练统一使用 Speculators，采样设置与 7-token draft length 按原文固定。作者报告，在单请求设置中，H-Spec 相对最强基线的平均接受长度提高约 5.0–13.3%，batch 1 的 ITL speedup 提高约 5.3–12.6%。

在 vLLM serving 评测里，论文报告并发 8–128 时 H-Spec 在所测模型/负载上具有更高吞吐和更低 KV cache 使用率。DFlash 官方配置使每 token KV 容量相较 target-only 增加约 1.14–1.8 倍（论文选定 target/ drafter 配置、BF16 cache）。这些结果说明它瞄准的是**上下文和并发下独立草稿缓存如何累积**，不能外推为所有 serving 环境有相同吞吐收益。[§4.1–§4.2、Table 1–2、Figure 6](https://arxiv.org/html/2609.24197v1#S4)

## 边界：省掉副本不等于没有成本

- H-Spec 的 attention KV 维度需与 target 匹配，才能原位消费 target K/V；这增加了跨 target 架构迁移时的接口约束。[§5](https://arxiv.org/html/2609.24197v1#S5)
- Drafter 仍运行 attention 与 Mamba 计算，并读取 target KV；“没有 drafter-side KV”不等于没有 KV、零额外状态或零 drafting overhead。
- 论文指出，短上下文或低并发时，混合 drafter 更深的计算图可能慢于较简单基线；高并发/长输入时更容易显现其内存与运行时优势。[§5、Figure 8](https://arxiv.org/html/2609.24197v1#S5)
- 结果依赖三个 target、论文给定训练集、vLLM serving 工作负载和 A100 测量设置；本文未运行模型或 kernel，不能从论文结果推断其它后端/硬件的表现。

**带走的区别**：H-Spec 是针对块扩散 drafter 上下文注入和并发 KV 占用的架构研究。判断它是否有用，要同时看草稿接受能力是否保持、draft 计算是否变重，以及目标模型是否满足原位 KV 接口要求。
