# DLite：面向 Agent 的无历史草稿器

## 1. 它要解决的不是“草稿不够小”

常规对话基准上效果好的 drafter，到 AgentLongBench / SWE-Bench 一类长、持续增长的历史里，接受长度可能降至 1–2 token；draft KV 的更新与保留也会加重多轮执行成本。DLite 的中心观察是：target 已经编码过全上下文，轻量 draft 再独立重建并保有这段历史，既增加 KV 管理，又让小模型越来越难追上 target。[论文 §1、§3.1]

DLite 将“全局上下文建模”留给 target：草稿器每轮读取 target 在若干层产生的上下文隐藏状态，围绕当前 anchor 做局部块预测；它不保留自己的历史 KV。因果关系只需在当前草稿块内部补回，因此作者以低秩 RNN 式 sequential head 汇总前一个草稿 token 的状态。实现上，主干先并行生成整块位置的 hidden state，顺序头再逐位把前 token 信息注入 hidden space，最后才投影到词表，避免每个位置先做一次昂贵的完整词表投影。[论文 §4.1；代码 `dlite/modeling/dlite.py:345–461`、`dlite/modeling/sequential_head.py:72–87,169–181`]

这不是“没有历史状态”：target 仍持有并更新自己的 KV，且 DLite 的草稿能力依赖 target hidden states。更准确的名字是**无历史 draft KV**，而不是无上下文推理。[代码 `dlite/modeling/dlite.py:562–585,638–713`]

## 2. 为什么训练分两段

DLite 的并行主干和自回归 target 的条件结构不一样，直接用 target 分布做 KL 蒸馏会训练不稳。作者先训练一个结构同构、仍可读历史的 teacher，再以 teacher 的分布做 warm-up；随后丢弃 teacher，直接用 target 监督 DLite，目标由 token 交叉熵和目标/草稿分布的总变差项组成。位置权重按距离衰减，让块开头的接受更受重视。[论文 §4.2]

最终 Qwen3-4B/8B drafter 使用 5 层并行 backbone、分别抽取 target 的 12/14 层 hidden states、sequential-head rank 320/512，块长 `K=7`。训练数据约 1.9M prompts（Open-PerfectBlend 1.3M + Nemotron Post-Training Dataset V2 600K），响应由 target 生成；最大训练序列长 4096、32 张 H800、warm-up teacher 8 epoch、DLite warm-up 2 epoch、stable stage 6 epoch。[论文 §5.1、Appendix A.1]

## 3. 结果要按负载读

Serving 使用 H800、Qwen3-4B/8B，比较 vanilla AR、EAGLE-3、DFlash、DSpark 等；所有方法设 `K=7`。在 LongBench v2 四类任务中，DLite 相比 DSpark 报告更高接受长度与端到端解码加速：例如 Qwen3-4B 的 code-repository understanding 为 `τ=3.14`、`2.66×`，DSpark 为 `2.44`、`2.02×`；long-dialogue-history 为 `τ=4.62`、`3.88×`，DSpark 为 `3.93`、`3.16×`。[Table 2]

Agent 基准上 Qwen3-8B / SWE-Bench：DLite `τ=3.19`、`2.74×`，DSpark `τ=1.94`、`1.60×`。这比作者抽象所说“最高提升 70%”更可读：它是特定模型、任务、实现与 AR 分母下的速度比差异，不是通用解码速度承诺。[Table 3]

消融提供了两个机制证据：两阶段训练优于单阶段直接训练；训练充分后，无历史 draft KV 版本在所测 GSM8K、MBPP、MT-Bench 上接受长度接近带 128/512-token 滑窗 KV 的版本。该结果支持“target 表征可替代 draft 对长历史的重复编码”，但只覆盖这些配置与任务。[§5.3]

## 4. 正确性与工程边界

方法改变的是 q（draft 分布），不是 target；target 仍做标准验证。官方代码的 T>0 `rejection` 路径按 `min(1,p/q)` 接受，并用正残差 `max(p-q,0)` 重采，T=0 路径比较 target greedy posterior。故无损性来自标准验证规则，不来自“hidden state 草稿更像 target”的经验优势。[代码 `dlite/utils/sampling.py:73–125`、`dlite/modeling/dlite.py:646–665`]

推理仓库的公开 `DLiteEngine` 追踪路径是：chat template → tokenizer → `spec_generate`；解码循环先取 target hidden states，再并行 draft、target 一次验证、修剪 target cache 并更新下一轮 anchor。[代码 `dlite/engine.py:67–106`、`dlite/modeling/dlite.py:562–713`]

读论文数字时要留意四个限制：

- 论文覆盖 Qwen3-4B/8B 和作者选定的 benchmark；尚未证明其它 target 家族或更大尺寸同样受益。
- 高并发测试只比较 DLite 与 DSpark；外部报告的 DFlash2/DFlow 数字不属于同一套实验。
- HF 仓库最新代码 README 明确说明其 benchmark 不对比 target 与 DLite 的输出 token；该推理包也不含论文所述完整训练栈，训练/全方法对照在 LiteSpec 仓库。当前 README 还列出 SGLang/vLLM 集成仍在 roadmap，因此不能把单卡 HF 推理包等同于生产 serving 部署。[代码 `README.md:37,101–107,181–183`]
- 报告的接受长度、throughput 和 speedup 都是作者结果；本文未下载权重或运行代码。
