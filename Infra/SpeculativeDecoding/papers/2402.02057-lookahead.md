# Lookahead Decoding：用 Jacobi 轨迹换解码步数（Fu et al., 2024）

> **一手来源**：arXiv:2402.02057 **v1**（2024-02-03），正文 HTML 逐节读取；license = **arXiv.org perpetual non-exclusive license**。｜ **主等级**：`[精读原文]`
> **一句话定位**：把自回归解码改写成**非线性方程组的 Jacobi 迭代**，用一条二维窗口同时生成多个不相交 n-gram，再用一次 target 前向并行验证——**不需要 draft 模型、不需要训练、不改变输出分布**。
> **亮点与差异四行**
> - **一句话亮点**：完全免训练的自投机：用 decoder 自己迭代过程中的“未来 token 残影”当草稿，把闲置 FLOPs 换成更少的解码步。
> - **新在哪**：① 用 **2D 窗口（序列轴 × 时间轴）** 从 Jacobi 轨迹里抽取 n-gram，而不是等固定点收敛；② 用 **n-gram 池**缓存历史轨迹，跨步复用；③ 证明**贪心草稿 + 一次并行验证**仍保持输出分布。
> - **证据强度**：中上。LLaMA-2-Chat 7B/13B/34B/70B 与 CodeLlama，MT-Bench / GSM8K / HumanEval / MBPP / ClassEval；有 W/N/G 消融、lookahead vs prompt-lookup、验证分支消融、单卡 vs 8 卡强扩展；但**加速比强依赖剩余算力**，在高 batch / 小 GPU 上会退化甚至变慢。
> - **值不值得引用**：**值得作为“免训练自投机”的代表引用**；引用时必须给 W/N/G、GPU 型号与 batch，否则 1.8× 与 4× 会被误读成通用值。

## 1. 问题：Jacobi 解码为什么“并行但不快”

论文从“自回归 = 解非线性方程组”出发（§2）：

- 给定已生成前缀，自回归解码是在求一个不动点；**Jacobi 迭代**可以一次更新所有位置，理论上最多 m 步收敛到 m 个 token。
- 但实测中 Jacobi 解码**几乎不减少解码步数**：它生成的 token 常常落在**错误的位置**，正确位置的 token 又会在下一轮被替换掉——并行了，但 wall-clock 没省。
- 另一方面，经典投机解码需要 draft 模型：**训不起、拿不到、跨模型不通用**。

Lookahead 的洞察：**不要等 Jacobi 收敛，而是把它沿途生成的“未来 token 残影”当作草稿候选**——这些残影可能出现在未来序列的正确位置，只要用 target 验证即可。

## 2. 方法：2D 窗口、n-gram 池、验证分支

### 2.1 Lookahead 分支（§3.1）

维护一个固定大小的 **2D 窗口**：

| 参数 | 含义 | 作用 |
| :-- | :-- | :-- |
| `W` | 向未来看多少个 token 位置 | 决定并行解码的宽度 |
| `N` | 向过去回看多少步 Jacobi 轨迹 | 决定能抽取多长的 n-gram（n = N） |
| `G` | 验证分支最多并行多少条 n-gram 候选 | 控制验证成本（实践 **G = W**） |

- 示例（图 1）：`W=5, N=3, G=2`；每一步在 5 个未来位置各生成一个 token，并从 3 步轨迹里抽 3-gram。
- 窗口每步“左移/上移”：丢掉最旧的时间列与序列行，把新生成的 token 追加进来，保持固定大小。
- 抽出的 n-gram 进入 **n-gram 池**（按起始 token 索引），供后续步骤检索。

### 2.2 验证分支（§3.2）

- 从池里找“**起始 token = 当前序列最后一个 token**”的 n-gram 作为候选，最多 `G` 条。
- 把候选拼进一次 target 前向，按投机采样规则**逐 token 验证**；n-gram 前缀不匹配就丢弃。
- 被接受的 n-gram 拼接到序列，未接受部分按 target 分布重采样。

### 2.3 关键工程：为什么可以“贪心草稿”

这是 Lookahead 最容易被忽略、但对无损性最关键的一步（§3.2 末）：

> 经典投机验证在拒绝时需要知道**草稿采样分布 q** 才能从 `max(0, p−q)` 重采样。但 n-gram 池会存很多候选，为每条候选存整个词表分布不现实。
>
> Lookahead 的解法：**强制草稿阶段用贪心采样**，于是 `q` 退化为 **one-hot**——只需要存“选了哪个 token”。验证时用 target 的 p 与 one-hot q 做标准拒绝采样，输出分布仍严格等于 p。

这条设计把“存储 q”的成本从 `O(候选数 × 词表)` 降到 `O(候选数)`，是 Lookahead 能实用化的前提。

### 2.4 注意力 mask 与 FlashAttention

- Lookahead 的 mask 不是标准因果 mask：lookahead 分支内部、验证分支内部、以及两分支之间都要按“位置更大者可见”的规则定制（图 2b）。
- 原生 FlashAttention 只支持因果 mask；论文**把 Lookahead 的 mask 模式硬编码进 FlashAttention**，带来约 **20%** 端到端加速（§5.2）。

### 2.5 多 GPU：Lookahead Parallelism（LP）

- lookahead 分支与验证分支都可切分：验证候选彼此独立，可分到不同设备，**前向过程无需通信**，只在每步结束后同步生成的 token。
- 因此可以用“更多 GPU = 更多每步 FLOPs”换更低延迟；论文在 8 卡上做 ClassEval 强扩展，报告 **4×**。

### 2.6 一步到底发生了什么（W=5, N=3, G=2 的具体走法）

以论文图 1 的设置为例子，把一步拆成四个动作：

| 动作 | 具体内容 |
| :-- | :-- |
| ① 生成 | 在当前序列末尾的 **5 个未来位置**各做一次“修改版 Jacobi”更新，得到 5 个新 token |
| ② 验证 | 从 n-gram 池里找“以当前末 token 开头”的 3-gram，最多取 **2** 条，和①的新 token 一起送 target 一次前向 |
| ③ 接受 | 按投机采样逐 token 判接受；被接受的 n-gram 直接拼到序列尾部 |
| ④ 维护 | 把①产生的新 3-gram 写回池；窗口左移一格、丢掉最旧列，保持 W=5、N=3 |

关键在第①步：这 5 个 token 不是“猜下一个”，而是**在 5 个不同未来位置同时猜**；其中大部分会被丢弃，但只要有一条 n-gram 命中，就能一步吃掉多个 token。这也是它“用 FLOPs 换步数”的字面含义。

### 2.7 与投机解码的 scaling 差异（§4）

论文给了一个重要的理论对照：

| 范式 | 每步能验证多少 | 加速上界 |
| :-- | :-- | :-- |
| 经典投机解码 | `γ` 个草稿 token（`γ` 固定时） | 受接受率 `α` 限制，存在上界；同时增大 `γ` 与草稿数 `b` 才能突破 |
| **Lookahead** | `G` 条 n-gram，每条长 `N−1` | 同时增大 `b` 与 `γ` **不会**撞到投机解码那个上界；步数随 `log(每步 FLOPs)` 线性下降（在 `N` 足够大时） |

这条差异解释了为什么 Lookahead 在“算力富余”时能持续换到收益，而在算力紧张时反噬——它不是免费午餐，而是**把算力曲线当输入**的算法。

## 3. 关键超参与实验设置

| 项 | 值/范围 | 说明 |
| :-- | :-- | :-- |
| 窗口 `W` | 示例 5；消融含 W=1 | 越大并行越宽，每步 FLOPs 越高 |

| 模型 | LLaMA-2-Chat 7B/13B/34B/70B、CodeLlama | — |
| 数据集 | MT-Bench、GSM8K（前 1k）、HumanEval、MBPP、ClassEval | 代码任务 max len 512 / 2048 |
| 硬件 | A100（主实验）、RTX 3090（对照）、8 卡（LP） | — |
| 解码 | 贪心为主；采样实验见 §5.3 | 采样会降低接受率 |

## 4. 结果（带条件）

| 条件 | 结果 | 备注 |
| :-- | :-- | :-- |
| 跨数据集总体 | **1.5–2.3×** | LLaMA-2-Chat；代码任务更高 |
| 代码补全 | 最高 **2.3×** | 重复 token 多，n-gram 命中率高 |
| MT-Bench、7B、A100、FlashAttention | **1.8×** | 相对带 FlashAttention 的自回归 |
| 8 卡强扩展、ClassEval | **4×** | Lookahead Parallelism；TP/PP 基线反而 0.75–0.82× |
| 摘要任务、采样开启 | **1.46–1.60×** | 采样接受率低于贪心 |
| RTX 3090、MT-Bench | **~30%** | 算力上限低，收益缩水 |
| A100、MT-Bench | **>50%** | 同设置下比 3090 高 |

> **读法**：1.8× 与 4× 不是同一件事——前者是**单卡、7B、MT-Bench、贪心**；后者是**8 卡、代码任务、强扩展**。把两者并列成“Lookahead 能到 4×”会误导。

## 5. 消融：每个分支值多少

| 变量 | 对照 | 结论 |
| :-- | :-- | :-- |
| lookahead 分支 | W=1（只用 prompt/历史） vs 均衡 W/N | W=1 也能加速，但**不如均衡分支**（表 3 的 ③④⑤⑥ vs ⑧） |
| prompt-lookup 基线 | transformers v4.37 prompt lookup（10 tokens） | prompt lookup 在“多起始 token”上更宽，某些设置超过 W=1 的 Lookahead；但均衡 Lookahead 仍最好 |
| 验证分支 | `G=1` vs `G=W` | G=1 接受潜力不足，收益下降（表 3 的 ⑦ vs ⑧） |
| FlashAttention | PyTorch 原生 vs 定制 mask | **~20%** 端到端提升 |
| 采样 vs 贪心 | T=0 vs T>0 | 采样接受率更低、加速更小（1.46–1.60×） |

**消融读法**：Lookahead 的收益来自**两个分支的平衡**——只放大 lookahead（W 大、G 小）或只放大验证（G 大、W 小）都不如两者匹配。这与“堆草稿 token 越多越好”的直觉相反。

## 6. 失效边界（独立段）

1. **必须有富余算力**：Lookahead 用“每步更多 FLOPs”换“更少步数”；在 compute-bound 环境（大 batch 服务、小 GPU）会**变慢**。论文明确写“running in compute-bound environments may cause slowdowns”。
2. **步数线性下降需要指数级 FLOPs**：§4 的 scaling law 是 `步数 ∝ 1/log(每步 FLOPs)`；想线性减少步数，就要指数级加算力，存在边际收益递减。
3. **n-gram 命中率决定上限**：高熵、长唯一文本（MT-Bench 的多轮对话）命中率低，收益明显小于代码补全；这是“免训练”的代价。
4. **池的内存与检索开销**：n-gram 池随解码增长；候选检索与 mask 构造都有成本，长序列下更明显。
5. **采样下收益缩水**：贪心草稿是 one-hot 存储的前提；T>0 时草稿仍贪心、target 采样，接受率下降，加速比从 1.8× 降到 1.46–1.60×（摘要任务）。
6. **多卡并非自动加速**：TP/PP 基线在多卡上反而 0.75–0.82×；只有 Lookahead Parallelism 这种“把候选分到设备”的方式才能吃到强扩展。
7. **小 GPU 上限低**：RTX 3090 上只有 ~30%，因为可用的剩余 FLOPs 少；这与“免训练所以到处能用”的印象相反。

## 7. 与同类系统的可判定差异

| 维度 | Lookahead | EAGLE-1/2/3 | Medusa | 独立 draft（Leviathan/Chen） | PLD / REST |
| :-- | :-- | :-- | :-- | :-- | :-- |
| 草稿来源 | Jacobi 轨迹 + n-gram 池 | target 特征自回归 | target 隐藏态 + 并行头 | 独立小模型 | prompt/语料 n-gram |
| 是否训练 | **免训练** | 需训练 | 需训头 | 需预训练 draft | 免训练 |
| 额外权重 | **无** | ~7% 草稿头 | K 个头 | 一个 draft 模型 | 无 |
| 输出分布 | 严格保持（贪心草稿 + 验证） | 严格（greedy 主结果） | 拒绝采样时严格；typical acceptance 有损 | 严格 | 严格 |
| 典型加速（条件） | 1.5–2.3×（单卡）；4×（8 卡代码） | 3.0–6.5×（带条件） | 2.3–2.8×（batch=1） | 2–3×（同族 draft） | 1.5–2.5×（重复文本） |
| 主要成本 | 每步 FLOPs、池 | 训练 + 树验证 | 训头 + 树验证 | 预训练 + 双模型服务 | 检索/覆盖度 |

**可判定差异一句话**：Lookahead 与 EAGLE/Medusa 都能“一次验证多个 token”，但 Lookahead 的候选来自**模型自身的迭代轨迹**，不需要任何额外参数；代价是候选质量受 n-gram 命中率限制，且必须消耗剩余算力。

## 8. 对本条目结论的影响

- **“免训练”不是没有代价**：Lookahead 证明了不需要 draft 模型也能无损加速，但把成本转移到“每步 FLOPs”与“n-gram 命中率”上——这直接支撑 [topics/algorithm-families.md](../topics/algorithm-families.md) 里“免训练 vs 训练”的取舍轴。
- **one-hot 草稿的合法性**：Lookahead 明确论证“贪心草稿 = one-hot 提议，验证仍无损”，这是理解后续 SGLang/vLLM 中 `draft_probs` 与 `qx=1.0` 处理的关键背景（见 [papers/sglang-implementation.md](sglang-implementation.md)、[papers/vllm-implementation.md](vllm-implementation.md)）。
- **算力换步数的边界**：Lookahead 的 scaling law 与 MagicDec 的“临界序列长度”、vLLM 的“batch 决定划算与否”是同一件事的三个视角（见 [topics/systems-throughput-latency.md](../topics/systems-throughput-latency.md)）。

### 8.1 与工程实现的接口

是否为 serving 默认项必须查具体框架、版本和配置，不能由论文加速数字推断。确定性候选可以按 point-mass 提议验证；只有候选实际按随机分布产生时，才必须使用对应随机分布或证明等价的条件化处理。是否保存完整 draft_probs 是实现选择，不是“有草稿模型就必需”的定理。详见 [验证专题 §3.3](../topics/verification-acceptance.md#33-one-hot-草稿也是合法提议)。

## 9. 引用注意（何时不该引它）

- 不要把 4× 当成通用加速——它是 **8 卡、ClassEval、强扩展**的特定结果。
- 不要说 Lookahead “没有额外开销”——它需要 n-gram 池、定制 mask、每步更多 FLOPs；只是没有额外**模型权重**。
- 不要把 Lookahead 的 1.8× 与 EAGLE-3 的 6.5× 放同一张排行榜——前者免训练、后者训了 8× 数据，量纲与前提不同。
- 引用采样结果时写清 T 与数据集；贪心 1.8× 不能外推到 T>0。
