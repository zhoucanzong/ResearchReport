# EAGLE-4 精读：把「这轮草稿多深、多宽」交给实测成本

> **一手来源**：EAGLE-4 Team《EAGLE-4: One Flexible Drafter for All Batch Sizes and Hardware》（Eagle AI，预印本 PDF 12 页，2026）；实现文档 `github.com/eagle-hq/EAGLE-4` 的 `docs/architecture.md`、`docs/known-limits.md`（后者 last_verified 2026-10-23）。**arXiv 用 `all:"EAGLE-4"` 检索返回 0 条**，故不标 arXiv 号，引用按作者自述的 `@misc{eagle4,2026,Preprint}`。
> **证据类型**：论文 PDF §1–§4 与 Algorithm 1 逐节读；官方文档补机制细节与限制。**未独立运行任何 EAGLE-4 实验**，全部数字为论文/官方支持矩阵报告值。
> **一句话**：EAGLE-4 不动草稿架构（单层、特征级、自回归、树验证），只把**「这轮该草稿多深、验证多宽」**变成一个**按本机实测延迟查表**的在线决策——于是同一个 drafter 从 batch=1 到 512、从 GPU 到手机都保持正收益。

---

## 1. 三条核心判断

1. **它解决的问题是"预算"，不是"质量"**。EAGLE-2/3 已经在优化"猜得准"；EAGLE-4 承认**猜准不等于变快**，因为多一层草稿、多验证一个 token 都要花时间，而这个时间随硬件、batch、上下文长度变化。所以它把"接受收益 / 成本"做成可比较的量。
2. **它把"静态超参"换成"标定表 + 运行时查表"**。代价是**每套模型×硬件×形状都要重新标定**（官方明确写了换模型/draft/TP/精度/attention backend/引擎都要重测），收益是同一个 drafter 权重通吃不同负载。
3. **它对"EAGLE 高 batch 会倒退"这条既有结论是收窄，不是推翻**：默认配置下确实会倒退（官方自测单卡 64 并发 0.73×），只有换四卡 high-load recipe 才撑到 512 不被普通解码反超（§6）。

## 2. 背景（论文 §2 的骨架）

- **验证规则**：接受概率 `α_i = min(1, p_i/q_i)`；首个拒绝处从残差 `[p_j − q_j]₊` 归一化后重采样；全接受则额外取一个 target token。**分布保持**来自这套拒绝采样，与树形无关。
- **greedy**：保留与 target argmax 一致的最长前缀，再补一个 target token。
- **EAGLE 系演进**（论文 §2.2 复述，可与本条目 [EAGLE/2/3 分册](2401.15077-eagle-series.md) 对照）：
  - EAGLE-1：用 target hidden state 预测"下一个特征"，再经 LM head 得 logits；训练含特征回归 + token 预测；
  - EAGLE-2：用草稿概率连乘给树节点排序、动态扩张/重排，**不重训**；
  - EAGLE-3：去掉特征回归约束、直接训 token 预测；融合低/中/高多层特征；后续草稿步递归复用自身 hidden state（TTT）。

**EAGLE-4 相对这三者的位置**：草稿侧沿用 EAGLE-3 形态，**新增在两处工程**——EAGLE-Harness（成本感知的树预算）与 Efficient LM Head（降草稿开销）。

## 3. 机制一：EAGLE-Harness 怎么决定"停"

### 3.1 把决策压成一个比较

论文的口径很干净：设候选树 `T`，期望接受长度 `A(T)`；宽/深增加 `A`，但增加草稿与验证开销 `C`。于是每个决策都化成

```
ΔA / ΔC  ≥  τ
```

`ΔA` 由草稿模型自己给（沿用 EAGLE-2：分支上草稿概率连乘 ≈ 该分支被接受的概率），`ΔC` 来自**标定表**。`τ` 是阈值，**且草稿侧阈值 τ_d 随深度上升**——理由论文写得很直白：**深分支的概率估计更不可靠**。

### 3.2 标定：一次 profile，之后查表

针对每套硬件×负载，先跑**成本估计阶段**：在不同 batch size、上下文长度、生成长度下 profile 草稿与 target 的推理延迟，把测得成本存成 lookup table 并缓存。运行时只做查表 + 草稿已有的分数，**不给 target 增加任何工作**。

### 3.3 三个决策点（Algorithm 1）

| 决策 | 规则 | 阈值特点 |
|---|---|---|
| 是否**再深一层** | 每完成一层扩张后比较 `ΔA_d / c_draft < τ_d` 则停 | `τ_d` 随深度上升（深分支不可靠）|
| **验证多少个** | 节点按 `p̂` 降序，逐个加，直到 `p̂_{n+1} / [c_ver(n+1) − c_ver(n)] < τ_v` | 用**边际**验证成本，不是平均成本 |
| 每节点**分支数** | 读当前负载对应的"验证固定 token 数"成本 | **轻载最多 8 分支、重载最多 4 分支** |

产出的效果是：单请求时建**深而宽**的树，重载时自动退回**短链**——**drafter 权重完全不变**。

### 3.4 T>0 的一个细节（容易被忽略但重要）

采样模式下"看本轮已抽的 token 再决定停不停"会**改变输出分布**。论文的处理是：**每个采样轮次的深度在轮次开始前就定死**，取"上一轮本来会停的那个深度"——既保住分布，又仍然跟着成本最优点走。这是这篇里少见的"正确性优先于性能"的地方。

## 4. 机制二：Efficient LM Head（两阶段，但只用于"选候选"）

- **两阶段**：先 `z̃ = A(Bh)`（rank-r）取 `TopK(z̃)` 得候选集 `C`（K∈{128,256,512}），再**用原全 rank 的 `W_C` 精确算 logits**：`z_C = W_C h`。选候选覆盖全词表，候选集随 hidden state 变化。
- **复杂度**：`O(Vd)` → `O(dr + Vr + Kd)`（不计 top-K 与 gather 开销）。
- **与 SlimSpec 的关键区别**（论文明确点出）：SlimSpec 把低秩投影当**最终 LM head**；EAGLE-4 只把它当**检索器**，最终分数仍精确。于是低秩头的近似误差**只要不漏掉候选**就不影响结果，训练目标也据此改成"只把容量花在高概率候选上"。
- **数字**（论文 Fig.2，profiled 配置）：全 LM head 占单次草稿前向 574 µs 的 **65.4%**；rank-512 降到 326 µs（−43.2%，LM head 占比 37.9%）、rank-128 降到 **255 µs（−55.6%**，占比 17.9%）。
- **为什么不直接用 SVD 初始化**：rank-128 的截断 SVD 会让一个 Qwen 3.8 27B drafter **每次验证少 0.48 个接受 token**；改为"只针对候选检索训练、其余冻结"后，训练出的 rank-128 头在 **98.2%** 的草稿步里包含全 rank 头的 top-1（SVD 初始化只有 **91.5%**），且 batch=1 下每次验证的草稿时间由 **9.1 ms 降到 4.8 ms**，接受长度无超出噪声的损失。

## 5. 其余工程点（§3.3–3.4）

- **注意力**：草稿可用 DSA（DeepSeek Sparse Attention）或滑动窗口注意力（SWA）压低长上下文草稿开销。
- **缓存**：草稿阶段采用 **append-only**，不逐出最旧条目，简化 DSA/SWA 下的 daft cache 管理。
- **FFN 选型**：MoE 草稿泛化更好但显存/训练开销更大，论文的取舍是**让 drafter 的 FFN 架构与 target 对齐**。

## 6. 实验：数字与条件（全部为报告值）

**主表（SPEED-Bench 定性集，Qwen 3.8 27B，4×B300 TP4，最大输出 4096）**

| 方法 | T=0 并发 1 | T=0 并发 512 | T=1 并发 1 | T=1 并发 512 |
|---|---|---|---|---|
| EAGLE-4 | **863.8 tok/s（3.59×）** | **28,340（1.34×）** | 608.6（2.59×） | 21,005（1.03×） |
| DFlash 2 | 672.6（2.80×） | 16,641（**0.78×**） | 560.3（2.39×） | 14,217（**0.70×**） |
| DSpark | 618.6（2.57×） | 14,229（**0.67×**） | 519.4（2.21×） | 11,723（**0.58×**） |
| MTP（内置头） | 534.5（2.22×） | 21,518（1.01×） | 369.1（1.57×） | 18,869（0.93×） |
| vanilla | 240.5（1.00×） | 21,203（1.00×） | 234.9（1.00×） | 20,307（1.00×） |

**两个可直接引用的观察**
1. **两个并行草稿在 512 并发时都跌破 vanilla**（DFlash 2 0.78×、DSpark 0.67×）——这正是 EAGLE-4 立论的实证：**固定块长在大 batch 下白算**。
2. **T=1 时 EAGLE-4 的 512 并发优势几乎消失（1.03×）**：采样模式既限制树的动态深度（§3.4 的冻结策略），又让接受率与开销关系变形。**引用"1.7×/1.99×"时必须带 T=0**。

**Nemotron-3.5-Super-VL-120B-A12B（4×B300，15-1-16）**：T=0 并发 1 **647（2.74×）**、并发 512 **33,480（1.69×）**；T=1 为 563（2.40×）/ 29,633（1.51×）。MTP 对应 568 / 31,716。

**并发扩展（HumanEval 闭环，Qwen 3.8 27B）**：C=1 **929 tok/s**（DFlash 2 759、DSpark 701、vanilla 240 → 1.22×/1.33×/3.87×）；C=512 **32,935 tok/s**（DFlash 2 的 1.67×、DSpark 的 1.95×、vanilla 的 1.43×）。**每用户吞吐**：C=512 时 EAGLE-4 **70 tok/s/用户**，vanilla 48、DFlash 2 41、DSpark 35；在"每用户 ≥200 tok/s"约束下聚合 **23,063 tok/s**（DFlash 2 的 1.7×）。

**AMD MI350X（单卡 TP1，SPEED-Bench 117 轮）**：12-4-32 配置并发 1 为 **262.89 tok/s**（12-4-16 为 260.79）。

**CPU（AWS c5.xlarge，4-bit Gemma-4-E2B-it，T=0，单请求）**：四基准平均 **2.71×** vanilla；逐基准 EAGLE-4 vs EAGLE-3：

| 基准 | vanilla | EAGLE-3 | EAGLE-4 |
|---|---|---|---|
| GSM8K | 17.2 | 27.6（1.60×） | **49.3（2.87×）** |
| MATH-500 | 16.7 | 27.5（1.65×） | **48.8（2.92×）** |
| HumanEval | 16.6 | 25.3（1.52×） | **45.8（2.76×）** |
| MT-Bench | 17.2 | 21.5（1.25×） | **39.3（2.28×）** |

CPU 上额外驻留 **0.27 GB**（其中 draft 模型 134 MB，其余为 KV cache 与计算 buffer）。

**手机（Motorola Razr 70 Ultra，Snapdragon 8 Elite，llama.cpp 6 线程，非 root）**：HumanEval **22.8 → 82.6 tok/s（3.62×）**；长文本 **23.3 → 74.7（3.21×）**；TTFT 1.2 s → **0.8 s**；长文本能耗 **356 mJ → 166 mJ/token**（USB 输入实测），同一生成 43 s → **14 s**；额外驻留 0.26 GB。draft-step 延迟 8.7 ms → **3.9 ms**（持久线程池、FP16 向量、小 batch 验证 kernel、NEON BF16 投影 kernel、draft/target 双侧低秩输出头）。

**TokenSpeed 长上下文（单请求，4×B300 TP4，bf16）**：32K/128K/250K 上下文下解码 **759 / 822 / 761 tok/s**，round 5.57–6.04 ms，TTFT **0.55 / 2.1 / 5.7 s**。

## 7. 边界：官方文档承认的"会变慢"场景

| 场景 | 实测（相对同引擎不开投机） | 原因（官方说明） |
|---|---|---|
| SGLang 默认命令，**单卡**并发 64 / 256 | **0.73× / 0.59×** | radix cache 与"切回普通解码"的交互、默认树把运行请求上限压低、单卡按已接纳请求预留验证状态 |
| SGLang 默认命令，**四卡**并发 64/128/256/512 | **0.80× / 0.48× / 0.37× / 0.32×** | 默认树把四卡服务器运行请求上限压到 32；需换 **high-load recipe** |
| high-load recipe（四卡） | 热身期 0.95× / 0.97×；重启后 **1.01× / 1.00×**（64 / 128） | 首次启动要编译 kernel 并现场测成本 |
| **vLLM / TokenSpeed >64 并发** | 可能比不开更慢 | 两者**尚未支持自动回退普通解码** |
| 单卡高负载 | 不支持 | `--disable-radix-cache` 的建议仅对四卡成立 |

**正确性与"批不变性"**：官方用 fp32 规则（2-ULP）校验，并明确说普通解码自身就随 batch 变化——512 并发下有 1–3 条 prompt 超阈值；开 `--enable-deterministic-inference` 后 token 级一致，但**此时 EAGLE-4 在高并发退回普通解码、没有加速**。

**许可证**：**source-available，非 OSI 开源**；商用有年营收 2,000 万美元等条件（README/License）。

## 8. 与并行草稿的关系（论文的论点结构）

- 对手是 **DFlash 2**（块扩散式草稿）与 **DSpark**（并行骨干 + 轻量顺序头）：两者都把 block size 当**预置超参**；
- EAGLE-4 的论点是**最优推测长度随 batch 上升而下降**，固定块长在大并发下产生"草稿了但用不上"的浪费——**上表 512 并发两家的 <1.0× 就是这个论点的实证**；
- 反过来，块草稿在小 batch 的时延上有自己的位置：论文自己也承认 C=4/C=32 时与 DFlash 2"几乎持平"。

## 9. 读后判断（研究推断，非论文主张）

1. **评价指标被迫换代**：论文明确说"只看接受长度（acceptance length）不足以评价 EAGLE-Harness"，因为动态验证的收益不在接受率里。**这意味着我们此前按"接受长度"横向比较各家草稿的做法，对 EAGLE-4 这类系统层工作会系统性低估。**
2. **"成本表"成为新的隐性超参**：复杂性从"训多个 drafter"迁移到"为每种硬件与形状标定成本表"。官方限制里"换模型/draft/TP/精度/attn backend/引擎都要重测"说明：**成本表不匹配时的性能退化，是这套方法的固有脆弱点**。
3. **对本条目既有结论的处理**：§4 的"EAGLE 高 batch 跌破 1.0×"应**收窄为"默认配置 + 未做 high-load 调优时成立"**；同时新增一条反例——**EAGLE-4 在四卡 high-load recipe 下 512 并发不再被普通解码反超（1.34×）**。
4. **可复用的工程模式**：`eagle-harness` **不 patch 引擎**，而是在注册前校验宿主 hook 是否齐全，"缺一个就什么都不注册 + 一条错误日志"。对我们读其他推理框架的插件化设计有参考价值。

## 10. 未能确证

- **无独立第三方复现**：所有数字来自作者团队与官方支持矩阵（AMD/TokenSpeed 团队贡献了各自硬件的测量）。
- **PDF 中未见独立 Limitations 章节**（全文检索未命中），本文 §7 的边界主要来自仓库 `docs/known-limits.md`。
- **与 CAST 的关系未确认**：CAST（arXiv 2510.26577，成本感知动态树）的官方代码路径写作 `EAGLE-Research/sglang-eagle4`，暗示同源；但未找到两者为"论文/工程两面"的明确声明。
- **DFlash 2 / DSpark 的对照是在各自官方 checkpoint + trtllm backend 下**，不是在同一调度器内复现，跨方法比较仍带实现差异。
