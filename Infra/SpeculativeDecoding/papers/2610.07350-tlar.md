## 亮点与差异四行

- **问题**：长 CoT 轨迹里会重复出现相似上下文，但历史检索“命中”不等于带来新 token：小 draft 可能已覆盖候选，或重复文本造成虚高接受。论文用同 prompt 的其他轨迹、打乱历史、unigram 等来源控制拆开考察。[§1、§3、Figure 1–2]
- **方法**：Trajectory-Local Adaptive Retrieval (TLAR) 在当前生成历史中用近似匹配找续写，按新近程度组 prefix-sharing tree，与 SmallDraft 候选合树并交给 target 精确验证；根据先前已验证的检索收益、最近命中和周期 probe，调节是否检索及候选宽度。[§4.1–§4.4、Figure 3]
- **匹配预算结果**：代码调试中，TLAR与最强单一检索 baseline 按每位置相同 distinct-node cap 比较并合并；B=4时，Qwen3-8B、Mistral-24B、Llama-3.1-8B的接受增量分别提高13.7%、11.5%、5.0%；B=8时提高16.8%、14.8%、4.8%。baseline分别为STAND-style（Qwen/Mistral）及SuffixDecoding（Llama）。[§5.3、Figure 5、Appendix B Table 18]
- **精确新意边界**：这不是“首次用已生成文字作草稿”。论文承认STAND利用推理轨迹冗余、SuffixDecoding检索生成/缓存后缀、RASD合并检索与模型树；PLD与REST类方法则分别用prompt或外部文本。TLAR更具体的贡献是以来源控制检验当前轨迹的特殊性，量化超出同一 SmallDraft 的增量、在共享节点预算下与强 retrieval baseline 作组合，并用已发生验证结果反馈控制后续检索。[§6、Appendix A.5、Table 3]

## 1. 先分清“历史里能找到”与“系统因此多接受”

作者将评估拆成来源、增量和开销三个问题。固定一批 target 已生成的轨迹和 SmallDraft预测后，`E_exact` 衡量某来源在目标未来 token 中能精确匹配多长；`Δ` 才衡量合入检索后相对同一个 SmallDraft 多接受多少 token；节点数或端到端运行时间再衡量这份增量的代价。[§2]

来源实验比较当前轨迹 (Within)、同模型/数据集的其他轨迹 (Cross)、打乱的当前历史 (Shuffled) 和 unigram。代码与数学中 Within普遍较强；开放写作并非如此，Qwen的Within不超过Unigram。进一步对同题不同seed的24组代码问题做配对，Qwen与Mistral更能复用自己的rollout，而Llama偏向另一rollout。作者还排查Llama数学中的循环复读：排除7条长循环轨迹后，来源接受均值从7.03降到2.2378，说明长匹配本身不能证明有用推理复用。[§3、Figures 1–2、Appendix C.2]

TLAR用当前上下文末尾 `c` 个 token 在历史中找汉明距离不超过 `ε` 的位置，提取其后续深度 `d` 的token，按近因优先放进树。控制器先等待历史超过 `τ`，再用历史命中率的指数移动平均、最近一次结果和周期 probe决定启停；活跃时根据命中率选宽度。默认 `c=4, ε=1, τ=512, d=4, k∈[1,4], H=32, P=32`。检索候选与SmallDraft分支合并、去重，target按原始分布验证；无损性来自target验证，而不是检索候选正确率。[§3、§4.1–§4.4、Appendix F]

## 2. 结果：增量、预算和真实运行时间分开看

主要离线集包括100个代码调试问题、24个数学问题、24个开放写作问题（每个target）；轨迹用temperature 0.6、top-p 0.95、最多4096新token生成。代码问题来自SWE-bench Verified issue描述。target/draft配对为Qwen3-8B/Qwen3-0.6B、Mistral-24B/Ministral-8B-Instruct-2410、Llama-3.1-8B/Llama-3.2-1B-Instruct。[§5.1、Appendix B.1]

在固定宽度代码离线回放中，Table 1报告TLAR相对SmallDraft的每位置增量：Qwen 0.171、Mistral 0.025、Llama 0.018；uncapped union分别0.228、0.032、0.026。增量与SmallDraft已接受长度并列报告，因为Mistral尽管检索源自身较强，额外增量仍低于Qwen。共享distinct retrieval-node budget的Table 18显示union相对每模型最强单源baseline多接受4.8%–16.8%；该百分比只是在对应离线代码任务和B=4/8设置下的接受增量，不是tokens/s提升。[§5.2–§5.3、Table 1、Figure 5、Appendix B Table 18]

系统吞吐单独在一张NVIDIA B200测试Qwen和Mistral target-draft pair；包含检索、树构造、前缀去重、验证、控制器、KV更新和采样校正。Appendix G Tables 29–30中，Qwen 1024输出token时batch 1从143.20升到155.09 token/s（+8.3%），batch 32从2405.0升到2587.8（+7.6%）；Mistral为+4.1%/+3.5%。Qwen到4096输出时为+12.4%/+10.8%。Table 2的Qwen 512-token短输出则为−0.6%/−0.7%，说明建索引与控制成本需要足够长的生成来摊销。[§5.3、Appendix G.1–G.3、Tables 2、29–34]

## 3. 同类基线与证据边界

论文在§6/Table 3将贡献界定为几个已存在部件的组合与更严格的评估：STAND已利用推理轨迹冗余，SuffixDecoding使用生成/缓存后缀，RASD把检索与模型候选树融合；PLD和REST代理对应prompt与外部prompt数据检索。其基线实现还包括STAND-style候选和SuffixDecoding共享验证接口。Qwen/Mistral的最强单源基线是STAND-style；Llama是SuffixDecoding。因此不能把论文结果说成优于所有检索算法、独立REST生产系统或任意检索器；REST在此实验是作者共享harness中的proxy。[§6、Appendix A.5、Appendix B.2、Tables 3、6、18]

采纳增量主要通过固定轨迹的离线回放量得，它回答“对这些已采样target token，额外候选覆盖了多少”，并不单独证明自由生成输出质量/总体任务分数提升。作者另做了实时端到端测试，缓和了这一限制，但该测试覆盖面较窄，且B200结果与离线来源比较的统计单位不同。硬件实测显示短输出可能净亏；主要端到端增益只在Qwen/Mistral、B200和代码调试负载验证。论文中补充的因果边界、事件驱动重放和耦合采样审计是作者对实现的内部验证，不等于第三方独立复现。[§5、Appendices F–G]

因此，本专题现有“PLD/REST/DictSpec为免训练检索类”的概括仍可保留，但应把TLAR定位为**轨迹内记忆来源的边际价值与资源调度**：它不是新造retrieval家族，而是把来源归因、与SmallDraft/强检索器互补、verification反馈控制和B200端到端成本接起来。与DARTree/CaDDTree的树结构优化属于不同轴：TLAR改变候选来源与何时加入候选，不提出新的扩散draft树拓扑或树节点成本最优证明。[§4、§6]
